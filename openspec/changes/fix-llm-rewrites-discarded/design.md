# 模型的改写被整批丢掉 · 变更设计

- 变更：openspec/changes/fix-llm-rewrites-discarded
- 性质：**bug 流程**——行为基准在 `openspec/specs/` 里已经写着（`llm-engine`「模型输出的每一条断言 SHALL 能追溯」「不采信指向不存在要点的引用」、`jd-version-generation`「实词须在底稿中出现过」），是实现偏离了规格，不是规格要改。

## Context

**现象**：生成一版之后界面说「模型这次没有用上」，改动对照里原文与版本文本几乎一模一样。

**实测**（用户那份 77 条要点的真实简历，MiniMax-M3.1-Flash）：

| | 修之前 | 修之后 |
| --- | --- | --- |
| 模型改写被采用 | **0 / 15** | 见下面的验收 |
| 被判「没指出依据」 | 13 | 编号滑到别处时不再丢 |
| 被判「底稿里没有的词」 | 2（另有 2 条在规则路径上同样中招） | 0 |
| 版本正文 | 全是规则产出 | 模型与规则混排 |

**三条根因**（都在共享包 `packages/shared`）：

1. `llmPrompt.ts` 的提示词里，每条要点下面写的是「子句 1、子句 2」，编号的**归属没说**。模型把编号当成整份提示词里连续排下去的——给「要点 4」的是 `[4,5,6,7]`，而这条要点自己只有两三个子句。
2. `generator.ts` 按**这条要点自己的事实**查模型给的编号（`entry.facts[index - 1]`），查不到就判成「模型没有指出它依据了哪些事实」并丢掉。**模型的改写被整批丢掉，整版回落规则引擎。**
3. `ledger.ts` 的实词比对**两边口径不一致**：被改写的那句先去掉评级词与动词再切实词，底稿那边的实词没去。

第 3 条的细节值得写下来，因为它是纯逻辑错误，不涉及模型：

```
底稿原文：支持多部门联合演练的分布式协同仿真平台,需同时支撑上千仿真实体…
被改写成：支持多部门联合演练的分布式协同仿真平台，同时支撑上千仿真实体…

模型的实词（去掉动词后）：多部门演练 / 分布式仿真平台 / …
底稿的实词（没去动词）  ：支持多部门联合演练 / 分布式协同仿真平台,需同时支撑…
```

「多部门演练」在「支持多部门联合演练」里**不是连续子串**（中间隔着「联合」），所以双向子串比对判不出来。**只去一边就会误伤凡是动词开头的要点**——用户那份简历里有 2 条在规则路径上也被这样判了异常。

## Goals / Non-Goals

**Goals**

- 模型的改写要真的被采用（被采用的条数要能被测出来）。
- 「模型引用了不存在的事实被换回」这条既有行为不变。
- 事实账本的校验规则（数字、实体、评级、动词）一个字不改。
- 模型正文与规则正文在排版上看起来是同一份。

**Non-Goals**

- 不改「不编造」的底线：模型写的正文仍然要通过事实校验，只是比对范围从「模型自称用的那几条」变成「这条要点本来有的全部事实」。
- 不改接口、不新增错误码、不改数据库。
- 不动 `degraded` / 回退的对外说法（另一个 `fix-` 变更的事）。
- 不追「模型只改了 15 / 50 条」这件事——那是输出 token 预算的问题（推理内容占了 78% 的额度），属于另一轮。

## Decisions

### D1 · 提示词：把子句编号的归属说清楚

| | |
| --- | --- |
| **选** | 每条要点的子句行改成「**本要点的子句 N**：…」，系统提示第 6 条写明「clauses 填的是这条要点自己的子句编号，从 1 开始——要点 5 的子句 1 指要点 5 的第一个子句，不要把编号跨要点累加」。 |
| **为什么** | 这是根因的第一道修复：**让模型一开始就算对**，后面的兜底只是防它再犯。 |
| **备选** | ① 只改系统提示、不动每条要点的行 —— 模型仍然看到一排「子句 1、子句 2」，它要自己推断归属；实测它推断错了。② 每行加上要点号（`要点 5 的子句 1`）——跟现在的写法几乎一样，但行更长、提示词更啰嗦。 |
| **代价** | 提示词每个子句多四个字。一份 50 条要点的简历大约多几百 token，可以忽略。 |

### D2 · 校验：编号指到别处时，按这条要点的全部事实复核

| | |
| --- | --- |
| **选** | 模型的编号在**这条要点里查不到**时，分两种：<br>① 编号在**这次发出去的事实总数之内**——说明它指的是别处的事实（编号排错了），改用**这条要点自己的全部事实**复核，并记一条观察 `clause-index-missed`。<br>② 编号比事实总数还大——说明是编的，照旧判「模型没有指出它依据了哪些事实」丢掉。 |
| **为什么这样分** | 「模型引用了不存在的事实被换回」是既有行为（`llm-engine`：「SHALL NOT 采信指向不存在要点的引用」）。**编号指到别处**与**编号是编的**在结构上都是「查不到」，但只有前者值得救——前者模型的正文仍然是这条要点的内容，救回来之后照样要过事实校验；后者模型的正文多半是凭空来的，救回来就是放进一条没有依据的话。 |
| **底线没有放松** | 救回来的改写仍然要过完整的事实校验：数字、实体、评级、动词、实词，一样不过就换回规则产出。**只是比对的依据从「模型自称用的那几条」变成「这条要点本来有的全部事实」**——这正是规则路径一直在用的口径（`generateVersion.ts` 里规则的改写也是拿整条要点的事实去校验）。 |
| **备选** | ① 一律丢掉编号对不上的改写 —— 就是今天的行为：模型的产出被整批丢掉，用户看到的是「规则写的，跟原简历差不多」。② 一律救回来（不区分编号是排错还是编的）——「模型引用了不存在的事实被换回」这条既有行为就没了，规格上站不住。③ 让模型自己报全局编号 —— 事实账本是按要点组织的（`factId` 按 bullet 生成），改成全局编号要动账本的结构（F4），代价大得多。 |
| **代价** | 少数情况下会放行一条模型自己都没指对依据的改写。**它仍然必须完全落在这条要点的事实里**，所以「不编造」不受影响。 |

### D3 · 实词比对：两边用同一个口径

| | |
| --- | --- |
| **选** | `draftTermsOf` 取底稿实词时，也先去掉评级词与动词——和 `extractComponents` 对被改写正文做的处理是**同一个函数**。 |
| **为什么** | 比的是内容词。动词与评级各有自己的强度规则（「主导」改成「参与」是弱化，放过；「参与」改成「主导」是上调，拦住）。留着它们进实词比对，弱化会被当成新词拦掉，降级就永远走不到它自己的规则——这正是当初去掉动词的原因。**但只去一边就会误伤**：拿去掉动词的词去比没去掉的词，凡是动词开头的要点都对不上。 |
| **备选** | ① 不去动词（两边都不去）——那「主导」改成「参与」会被实词规则当成新词拦掉，降级永远走不到动词规则。与既有设计相反。② 比对时把两边都还原成「带动词」的形态——要还原就得记住每个词原来带的是哪个动词，比对逻辑更绕，且还原不出来（'负责' 和 '主导' 都可能是同一个词的来源）。 |
| **代价** | 实词表的粒度变粗了：「支持多部门联合演练」在表里成了「多部门联合演练」。这与被改写正文那侧的粒度一致，**两边对齐才是要的**。 |
| **F4 怎么算不撞** | 改的是**比对时用的词表怎么算**，不是校验规则：数字、实体、评级、动词的判定一字不改，「不通过就换回」的语义一字不改，`Fact` / `Claim` / `verifyClaim` 的结构一字不改。 |

### D4 · 模型正文的排版对齐规则路径

| | |
| --- | --- |
| **选** | 新增 `normalizeModelText(text)`：去项目符号、统一半角与技术词大小写、整理空格、去掉句末标点。**不动词、不动语序。** 模型写的正文先进这个函数，再进事实校验、也用归一后的文本入库。 |
| **为什么** | 规则路径的正文走 `applyTransforms`，去掉句末标点；模型写的正文不走，于是同一份版本里模型写的句子带句号、规则写的句子不带，导出的 PDF 一眼两套排版。 |
| **为什么不动词** | 动词前置、去掉领起副词是规则引擎的活（`allowVerbFronting` 开关管着它）。**模型改了动词是要被拦的**（强度上调），这里不能替它把动词改掉——否则模型写「负责」的句子被悄悄改成「主导」，反而绕过了强度规则。 |
| **备选** | ① 模型正文也走完整的 `applyTransforms` —— 里面含动词前置，等于替模型改了动词，绕开强度规则。② 不对齐 —— 两套排版混在一份 PDF 里。 |

### D5 · 服务端 `LLM_MAX_TOKENS` 的默认值

| | |
| --- | --- |
| **选** | `server/src/llm/config.ts` 的 `DEFAULT_MAX_TOKENS` 从 2000 提到 32000。 |
| **为什么** | 2000 是单次问答的量级。实测一整版简历的改写要 3 万 token 上下（推理内容占了 78% 的额度）——只配了供应商地址与密钥、忘了调这个值的人，第一次生成就撞上截断，界面提示「请调大 LLM_MAX_TOKENS」倒是说清了下一步，但**默认值本身就是个陷阱**。`server/.env.example` 里早就写着实测值是 32000。 |
| **备选** | ① 保持 2000，只在 `.env.example` 里强调 —— 已经强调了，踩坑的人还是踩。② 启动时打一条警告 —— 警告在启动日志里，用户看不到；界面那句「请调大 LLM_MAX_TOKENS」已经在了。 |
| **代价** | 默认的输出上限大了。真跑起来才会用到那么多 token，配置错了也只是一次调用的事。 |

### D6 · 让模型真的去「强调」，别只照抄现成的一句

| | |
| --- | --- |
| **选** | 改写提示词第 5 条从「尽量用原文的词。改写幅度越小越好。」改成「在保留全部事实的前提下，可以调整语序，把与这个岗位最相关的内容放在最前面。改写幅度要看得出来——不要只是照抄现成的一句」，并补一条「不要添加原文里没有的词」。 |
| **为什么** | 规格承诺的是「只**重组**、删减、**强调**底稿中已有的事实」（`jd-version-generation`）。原来的提示词写着「改写幅度越小越好」+ 给模型看了「现成的一句」，模型于是照抄——**改写路径交出去的东西跟规则产出几乎一样，用户看不出这一版优化了什么**。这是实现没兑现规格里的「强调」。 |
| **实测** | 用户那份 77 条要点的真实简历，同一个模型（MiniMax-M3.1-Flash）：<br><br>• **原提示词**：50 条改写全部被采用，但**去掉空格与逗号后文字几乎没变**——看不出优化。<br>• **只改第 5 条**：31 / 50 条文字实质变了，但 13 条因为模型加了原文没有的词被事实校验换回。<br>• **再补「不要添加原文里没有的词」**：**49 / 50 条被采用、校验异常 0 条、27 / 50 条文字实质变了**。<br><br>改写的效果正是「朝着这个岗位去」：那个 JD 要求「熟悉 Docker 与 CI/CD 流程」，模型就把 CI/CD 流水线那句提到了句首——原文是「带领 10 人全栈团队，推行 Scrum，搭建 Jenkins + GitLab CI/CD 流水线」，改成了「搭建 Jenkins + GitLab CI/CD 流水线，推行 Scrum 敏捷流程，带领 10 人全栈团队」。 |
| **底线没动** | 调语序、合并分句都在这条要点的事实里；事实校验照常逐项判定（数字、实体、评级、动词、实词），不过就换回规则产出。**「不编造」不受影响。** |
| **备选** | ① 保持原提示词 —— 用户的原话：「优化在哪里呢？」答不上来。② 只加「不要添加原文没有的词」不动第 5 条 —— 模型照样照抄，事实校验拦不住「照抄」这件事（照抄是合法的）。③ 把模型交给用户自己调 —— 这个产品面向的是求职者，不是调 prompt 的人。 |
| **代价** | **改写被换回的数量上升。** 模型改得越主动，越容易踩到事实校验。这不是坏事——被换回的要点在面板里写着「没通过校验」，用户看得见。但确实比「全部照抄」换回得多。 |

## Risks / Trade-offs

**[模型改得更主动，被换回的要点会变多]** → 补了「不要添加原文里没有的词」之后实测从 13 条降到 1 条；剩下的被换回要点在「这一版是怎么来的」面板里逐条写着原因，用户看得见。

**[救回来的改写可能不是模型真正想引用的那几条事实]** → 它仍然必须完全落在这条要点的事实里，「不编造」不受影响；模型自己指错依据这件事记成观察（`clause-index-missed`），在「这一版是怎么来的」面板里能看出来。

**[实词表变粗，可能放行不该放行的句子]** → 实词是中文层面的、放宽一点少误伤（这是既有设计）。数字、实体、评级、动词仍是严格的那一层。粗化后的词仍然必须是底稿里出现过的连续片段（两边都去掉动词之后）。

**[提示词变长]** → 每个子句多四个字，50 条要点大约多几百 token。

**[改了 F4 冻结的账本]** → 改的是比对时用的词表怎么算，不是校验规则。已在 proposal 里显式留痕，评审可以推翻；推翻的备选是把实词比对挪出账本（代价大得多）。

## Migration Plan

**没有数据迁移，没有部署顺序要求。** 行为变化在服务端生效，回滚就是回滚代码。已生成的版本不受影响——它们的正文与改动对照是快照。

## Open Questions

- **模型只改了 15 / 50 条**：输出 token 预算被推理内容吃掉（实测 29014 / 32000）。要么把改写这一步的要点收窄（只发与该 JD 相关的那些），要么换一个推理更省的模型。**本轮不做**，属于新一轮的范围。
- **改动对照里 39 条「改写」其实只改了空格**（`带领10人` → `带领 10 人`）。这是规则的排版规范化，界面上标成「改写」略有夸张（理由写的是「只调整了措辞与排版，事实没有变化」）。要不要把「只改排版」单列一类，是产品口味问题，**本轮不动**。
