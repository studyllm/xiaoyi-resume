# 生成 JD 定向版本：把黑盒拆开 · 变更设计

- 变更：openspec/changes/jd-generation-pipeline-clarity
- 澄清文档：docs/clarifications/jd-generation-pipeline-clarity.md
- 系统设计：docs/designs/jd-generation-pipeline-clarity.md（本文的每条决策都追溯到它的对应小节）

## Context

**现在是什么样。**

用户在「多 JD 版本」页粘一份 JD，服务端比对着简历算一遍要求与命中情况，用户确认后生成一版。整个过程对用户是三步黑箱：

1. `POST /api/v1/jd/analyze`（`server/src/routes/jd.ts`）——规则抽要求、算命中。模型路径下 `createLlmJdAnalyzer.analyze` 把**整份简历**摊平成 `PromptBullet`（`jdAnalysisPrompt.ts:56`）发给模型。
2. `POST /api/v1/versions`（`server/src/routes/resume.ts`）——`createLlmGenerator.generate` 拿规则产出的基线版，把**进了这一版**的全部要点连同**全部**要求发给模型改写（`generator.ts:159-165`）。
3. 打开版本详情——只有「简历预览 / 正文全文 / 要求覆盖 / 改动对照 / 未覆盖要求」五个页签，全是**结果**。这一版经过哪几步、模型看了简历的哪一部分、哪些句子是模型写的、哪几句被换回了，一个都看不到。

**已经在算但没露出来的东西**：`collectEvidence` 算出的相关度与命中关系（`coverage.ts:31`）、`generations` 表里记着的模型标识与 token 数（`routes/resume.ts:167`）、`trace.claims` 里哪些要点是模型写的（`generator.ts:276`）、`integrity.violations` 里哪几条没通过校验。这些算完就存起来，界面一个字都不显示。

**本变更要做的三件事**（澄清文档 §3）：

- **A** 两次调用的提示词裁剪（保持两次调用，不合并）。
- **B** 版本详情页的「这一版是怎么来的」说明面板。
- **C** 调用记录透出到面板。

**贯穿全程的不变式**（系统设计 §1.1）：

> 裁剪只影响模型能看到什么，不影响系统能判定什么。

**约束**（`AGENTS.md`）：

- 共享包 `packages/shared` 的源码被前后端引用**同一份**，不复制。改动那里两端同时生效。共享包里不能出现 Node 内置 API（前端会把它打进浏览器 bundle）。
- 服务端接口**字段只能加、枚举只能加**。`packages/shared/src/contracts/error-codes.ts` 与 `docs/api-contract.md` §5 是错误码表的唯一来源，**本变更不新增错误码**。
- 界面文案不得出现「底稿」，不得出现禁用词（`AGENTS.md` §7）。
- 样式里不得出现视觉字面量与 px 刻度（`AGENTS.md` §3.1、`flows.spec.ts` 会拦）。
- 引擎异步化语义（F1）、引擎模式开关口径（F2）、数据模型与 schema v1（F3）、事实账本与校验器（F4）、账号标识（F5）、指标口径（F6）、错误码表（F7）、隐私口径（F8）、共享包边界（F9）、存量规格退役清单（F10）——逐条核对见系统设计 §1.3。

## Goals / Non-Goals

**Goals**

- 比对那次只把与该岗位相关的要点发给模型，JD 全文照发。
- 候选要点**保留在整份简历中的原序号**，模型引用的号仍能对回原文。
- 模型判「未覆盖」的要求，在**全部**要点上用规则引擎复核一次，未覆盖清单不产生假阴性。
- 改写那次只发已覆盖的要求。
- 版本详情页多一个页签，把生成经过、模型调用、要点取舍、模型改写与换回四件事摊开给用户看。
- 比对的覆盖范围（简历共多少条要点、实际比对了多少条）对用户可见。
- 客户端等待模型有上限，上限值由服务端下发。

**Non-Goals**

- 不引入 SSE / 轮询（澄清文档 §3「明确不做」）。引擎接口形态不动，仍是 `Promise`。
- 不合并两次模型调用（澄清文档 §3）。
- 不引入新的相关性判定（澄清文档 §3）。候选筛选复用 `collectEvidence` 已经算出来的信号。
- 不改 `degraded` / 回退的对外说法（澄清文档 §3）。那是另一个 `fix-` 变更的事。
- 不做每日生成次数上限与每日成本上限（澄清文档未决 4）。
- 不加「取消本次生成」的入口——那要服务端的作业模型，改动量远超本轮（系统设计 §8.3 第 8 条）。
- 不做数据库迁移，不动 `server/src/db/schema.ts`。

## Decisions

### D1 · 候选要点怎么筛

**采纳系统设计 §1.2 D1，但把口径从 `relevance > 0` 改成 `jdRelated`。**

| | |
| --- | --- |
| **选** | 共享包新增 `packages/shared/src/engines/candidateSelection.ts`，纯函数 `selectCandidates(evidence, options)`。规则：① 候选集 = `evidence` 中 `jdRelated === true` 的要点；② 每个条目（item）至少留一条——该条目内 `jdRelated` 的要点里 `relevance` 最高的那条；条目内一条都没有 `jdRelated` 时，留该条目内 `relevance` 最高的那条；③ 按 `relevance` 降序截到 `maxCandidates`（默认 **40**，环境变量 `LLM_MAX_CANDIDATE_BULLETS` 覆盖）。 |
| **为什么不照系统设计的字面规则** | 系统设计 §1.2 D1 写的是「`relevance > 0` 的要点」。但 `coverage.ts:66-88` 的 `relevance` 里含 `otherCount`（命中任何目录词都算）与 `hasResultSignal` 的 +2 分——**几乎每条要点都会 > 0**，照字面实现等于不裁剪，本变更的成本与时延收益全部落空。代码里已经有正确的信号：`jdRelated`（`coverage.ts:88`）= 命中 JD 关键词 / 相关词 / 无关键词要求的核心短语，正是「与该岗位相关」。 |
| **为什么 `jdRelated` 才对** | 系统设计 D1 的「为什么」段说：复用这个打分是**为了**让「候选集与规则路径的排序、删减行为不会差太远」。规则路径判断「这条要点与 JD 无关」的信号正是 `jdRelated`——`ordering.ts:17` 的 `evidence.filter((entry) => entry.jdRelated)`。所以 `jdRelated` 才是 D1 想要的语义，字面的 `relevance > 0` 反而不是。 |
| **与规则路径的关系** | 规则路径（`rulesJdAnalyzer` / `rulesGenerator`）的产物**逐字不变**——候选筛选只发生在「模型要看什么」这一层，规则引擎自己始终看全部要点。 |
| **备选** | ① 按 `relevance > 0` 全取 —— 见上，裁剪不生效。② 只保留强相关 + 每条目一条 —— 太狠，会丢掉模型唯一能看出语义相关的那批。③ 引入向量检索 —— 引入新依赖与新失败模式，与「不引入新的相关性判定」冲突。 |
| **代价** | ① 简历里与该岗位语义相关但关键词不沾边的要点可能落在候选外——D3 的复核机制为这个兜底。② 模型看到的简历是「不连续」的（跳号），提示词里必须说清楚。③ 40 这个数没有实测来源，是配置项，改数不用改代码（产品已确认先按 40）。 |

**取舍记录要带出去**：候选函数除了返回候选要点，还要返回「每个条目至少留一条」这条规则的取舍记录（留了哪条、为什么留），面板的「要点取舍」区块要能说出「这条没参与比对是因为它与该岗位无关」。

### D2 · 序号怎么处理

**采纳系统设计 §1.2 D2（最承重的一条）。**

| | |
| --- | --- |
| **选** | **保留要点在整份简历里的原序号**（跳号）。`jdAnalysis.ts:365` 的 `bulletIdOf(draft, ordinal)` 按全量编号查表——**查表逻辑一字不改**，只是查表范围变成候选集：模型引用了一个不在候选集里的序号时，`bullets[ordinal - 1]` 取不到（候选数组按原序号取值，不是按 `ordinal - 1` 索引），落到现有的越界分支，`outOfRange += 1`，那条要求按「没有对应事实」处理。提示词里写明「序号是它在整份简历中的位置，中间被略过的是与该岗位无关的要点」。 |
| **实现要点** | 候选集必须保留**原序号**，不能重编。`jdAnalysisPrompt.ts` 的 `PromptBullet.ordinal` 语义从「连续编号」变成「全量编号，可以跳号」；取值时按 ordinal 查表，不是按数组下标。 |
| **备选** | ① 重编 1..N 连续号 —— **模型引的号对不回原文**。`jdAnalysis.ts:365` 的 `bulletIdOf` 按全量编号查表，重编后会把「要点 7」错查到另一条要点上，直接违反「查不出依据等于没引用」。② 重编 + 附序号映射表 —— 要让模型同时维护两套号，抄错的概率更高。③ 改用 bullet id —— 模型抄 16 位哈希错一位就查不出依据（`jdAnalysisPrompt.ts` 开头那段注释已经说过这个坑）。 |
| **代价** | 跳号会让模型困惑。缓解：提示词明确说明跳号含义；模型引用了候选集外的序号时，现有的越界逻辑直接丢掉那条要求，不会错挂到别的要点上。 |

**必须有一个专门的回归用例锁住它**，并且浏览器验收时要用一份真简历跑一遍，肉眼核对模型引用的序号对不对得上（系统设计 §8.1）。

### D3 · 模型判「未覆盖」的要求怎么办

**采纳系统设计 §1.2 D3（正确性的关键）。**

| | |
| --- | --- |
| **选** | 模型判 `none` 的要求，**用规则引擎在全部要点上再判一次**：规则也匹配不到 → 真的未覆盖；规则匹配到了 → 降为 `weak` + `approximate: true`。为此把 `coverage.ts:100` 的 `computeCoverage` 拆出一个单条要求的匹配函数 `matchRequirement(draft, requirement, evidence)`，`computeCoverage` 改为对每条要求调它。 |
| **实现要点** | `computeCoverage` 现在一次算完所有要求的 `exactHits` / `weakHits` / `metaHits`。拆的时候要把这三个集合的算法**原样**搬进 `matchRequirement`，`computeCoverage` 变成 `jd.requirements.map((r) => matchRequirement(draft, r, evidence))`——**规则路径的产物必须逐字不变**，这条由回归用例守住（系统设计 T10）。 |
| **备选** | ① 模型说不覆盖就不覆盖 —— **未覆盖清单会有假阴性**：用户在清单里看到「你的简历中没有对应事实」，而实际上简历里有、只是没给模型看。这是**对用户说谎**，「材料不足以支撑 JD 中的某项要求时……说明哪些要求没有对应事实」的前提被破坏。② 候选集扩到全部要点 —— 裁剪白做了。③ 对模型判 `none` 的要求再调一次模型 —— 多一次调用，与「保持两次」冲突，成本翻倍。 |
| **代价** | ① 覆盖清单里会出现「弱覆盖 + 按关键词近似匹配」这种看起来比现在弱的条目。② 多一次 CPU 计算（微秒级）。③ `computeCoverage` 要重构，规则路径的产物必须逐字不变。 |

### D4 · 改写那次发哪些要求

**采纳系统设计 §1.2 D4。**

| | |
| --- | --- |
| **选** | 只发**已覆盖**的要求：`tier` 为 `strong` 与 `weak` 的。`tier === 'none'` 的不发。`generator.ts:161` 现在是 `baseline.version.coverage.map((entry) => entry.text)`——**全量**，改成过滤。 |
| **备选** | ① 全发 —— 浪费 token；未覆盖的要求在正文里本来就不写内容，还会诱导模型去「照顾」它。② 只发 `strong` —— `weak` 的要求同样值得强调，丢掉就少了一档定向能力。 |
| **代价** | 模型看不到「这条要求你的简历里没有事实」这个信号，**对「要求很匹配但简历写得不明显」的要点可能改写得不够用力**。接受这个代价：事实校验兜底，且改写幅度本来就不是这个产品的主要卖点。 |

### D5 · 面板数据存在哪

**采纳系统设计 §1.2 D5。**

| | |
| --- | --- |
| **选** | 存在 `versions.payload` 里（jsonb），`ResumeVersion` 增加一个**可选**字段 `explain?: VersionExplain`（`domain/types.ts:317`）。`GET /api/v1/versions/:id` 原样返回；`GET /api/v1/versions`（列表）在服务端**剥离 `explain` 键**。 |
| **备选** | ① 新增一列 `versions.explain jsonb` —— 列表天然不受影响，但要写 SQL 迁移、动 `schema.ts`，**形式上撞 F3**（schema v1 已冻结）。② 详情页现算：运行时从 `jd_analyses` 查证据 —— `jd_analyses` 每账号只留 20 份（`routes/jd.ts:14`），老版本的面板会拿不到数据；从 `generations` 查同理，保留期比简历短。③ 不存，面板现算 —— 面板要显示的「模型改写与换回」在模型路径下**只有服务端算得出**（事实校验在服务端），现算等于把校验搬到浏览器，不成立。 |
| **为什么** | 放 payload 里，`explain` 与版本正文同生共死——版本是快照，面板描述的也必须是生成当刻的事实。 |
| **代价** | ① 列表要剥离一个键，契约里「列表项是完整版本」那句话要加一个例外。② `versions.payload` 变大。③ **形式上动了 F3 冻结的 `ResumeVersion` 字段**——论证见 §Risks。 |

### D6 · 面板放在哪

**采纳系统设计 §1.2 D6。**

版本详情页新增一个页签「这一版是怎么来的」，放在现有五个页签之后（`VersionDetailView.vue` 的 `el-tabs` 现在是 `preview / body / coverage / diff / uncovered`）。

**备选**：① 塞进「版本说明」卡片 —— 那张卡片已经有两段说明 + 四项 `el-descriptions` + 一个告警条，再塞就挤爆了。② 抽屉 / 弹窗 —— 打断阅读，窄屏更难读。③ 单独的路由页 —— 多一次跳转，用户会以为这里能编辑。

**代价**：页签从 5 个变 6 个。窄屏（375）下 `el-tabs` 横向滚动，可接受。

### D7 · 客户端超时

**采纳系统设计 §1.2 D7。**

| | |
| --- | --- |
| **选** | **加**。`GET /api/v1/engine` 的响应加一个 `timeoutMs` 字段（加字段，兼容），前端按 `timeoutMs + 60s` 设客户端超时；`available` 为假时用短默认值（规则路径是毫秒级的）。 |
| **现状** | `frontend/src/api/client.ts` 的 `api()` 已经透传 `options.signal`，但**没有任何调用方传 signal**；`server/src/llm/config.ts` 的 `timeoutMs` 默认 30 秒（`DEFAULT_TIMEOUT_MS = 30_000`），那是**服务端单次模型调用**的上限，与浏览器等多久是两件事。 |
| **备选** | ① 不加 —— **现状就是不加**：一次模型调用挂 10 分钟，HTTP 请求就一直挂着；用户关掉页面，服务端的调用还在跑，token 照烧。② 硬编码 15 分钟 —— 与服务端配置脱节。③ 用契约里写的 30 秒 —— **会把每一次真实的模型调用都掐掉**（实测一轮要 10 分钟）。 |
| **为什么** | `docs/api-contract.md` 已经承诺「客户端超时设 30 秒」，但实现里没有；这个数在模型调用要 10 分钟的前提下是错的。**把超时值从服务端下发**，两边不再各写一个数。 |
| **代价** | ① `timeoutMs` 是部署细节——但它不是模型 id 也不是供应商地址。② 客户端超时仍早于服务端时，用户会看到超时提示，而服务端可能已经把版本建好了——**`Idempotency-Key` 保证用户重试不会生成第二份**，刷新详情页能看到那一版。这一点要写进超时提示文案。 |

**超时落哪一层**：在 `frontend/src/api/client.ts` 的 `api()` 里加一个可选的 `timeoutMs`，用 `AbortSignal.timeout()` 合成 signal；`AbortError` 现在在 `client.ts:74` 被原样抛出（不转 `ApiError`）——**超时与用户主动取消要分开**：超时抛 `ApiError('UNKNOWN', FAILURE_STATES['llm-timeout'])`，用户主动取消仍然原样抛 `AbortError`。`llm-timeout` 这条状态**已存在**（`states.ts:194`），**不新增错误码**。

### D8 · 模型改写后的正文补禁用词检查

**采纳系统设计 §1.2 D8。**

在 `createLlmGenerator` 里，模型正文换回并重新 `assembleBody` 之后（`generator.ts:264`），再过一次 `assertCleanOutput(body, '版本正文')`；命中就整版回落规则产出并记原因。

**备选**：不补 —— 规格（`AGENTS.md` §7「引擎输出交付前都要过禁用词检查」+ `llm-engine`「模型输出的每一条要求 SHALL 不含界面禁用词」）已经要求了，现在只是没做到。

**代价**：命中时整版降级。触发概率低（模型主动写进禁用词不常见），但代价是用户白等。**接受**——「不编造」与用词底线比一次生成的成功率重要。

**注意**：这条是**整版回落**，不是单条换回——与「模型写的要点没通过事实校验 → 单条换回，整版仍算模型生成」是两种不同的降级粒度，在 `integrity.generator` 上表现也不同（前者是 `'rules'`，后者仍是 `'llm'`）。

### D9 · 面板不依赖 `degraded` 标志

**采纳系统设计 §1.2 D9。**

`degraded` 的语义矛盾本轮**不改**（澄清文档 §3 明确排除），但**面板必须不依赖那个有歧义的标志**。

面板的每条事实都从无歧义的来源推导：`diff[].change`（保留 / 改写 / 移除）、`diff[].placement`（是否移至末尾）、`trace.claims`（哪些要点是模型写的）、`integrity.violations`（哪几条没通过校验、什么原因）。

**具体做法**：给 `DiffEntry` 增加一个可选字段 `writtenBy?: 'model' | 'rules'`（`domain/types.ts:139`），在 `applyPatchedDiff`（`generator.ts:343`）里给模型改写过的要点打上 `'model'`。**加字段**，旧版本没有这个字段时按 `'rules'` 看（与 `integrity.generator` 的老版本兜底一致）。

**代价**：`DiffEntry` 是 F3 冻结的领域类型，同 D5 的论证（向后兼容的加可选字段，不需要迁移）。

### D10 · 共享包新增什么

**采纳系统设计 §3.3 的落点表。**

| 文件 | 性质 | 说明 |
| --- | --- | --- |
| `packages/shared/src/engines/candidateSelection.ts` | 新增 | `selectCandidates(evidence, options)` 纯函数 + 取舍记录。共享包里**只能用浏览器与 Node 都有的东西**（不能 import `node:*`）——它是纯数据处理，不碰 IO。 |
| `packages/shared/src/engines/explain.ts` | 新增 | `buildExplain(...)` / `mergeRewriteExplain(...)` 纯函数，从 coverage / evidence / diff / claims 组装面板数据。 |
| `packages/shared/src/domain/types.ts` | 改 | `ResumeVersion.explain?: VersionExplain`；新增 `VersionExplain` / `ExplainBullet` / `ExplainRewrite` / `ExplainModelCall` / `ExplainPipeline`；`DiffEntry.writtenBy?: 'model' \| 'rules'`。 |

**为什么放共享包而不是服务端**：`VersionExplain` 的类型前端也要读（面板组件渲染它），服务端也要写它（生成时组装）。放共享包，两端引同一份，形状不会漂。

## Risks / Trade-offs

### 序号一致性（最高风险）

**[序号不一致] → 模型引的序号对不回原文，「查不出依据等于没引用」失效，事实校验的担保随之失效。**
**缓解**：`T6` / `T7` 两个专门的回归用例锁住它；浏览器验收用一份真简历跑一遍，肉眼核对模型引用的序号。

### 裁剪把能命中的要点裁掉了

**[语义相关但关键词不沾边的要点落在候选外] → 覆盖结论比全量时保守。**
**缓解**：D3 的复核机制（模型判未覆盖 → 规则在全部要点上重判）+ 面板写明「比对了 N 条（共 M 条）」。裁剪本身**不产生假阴性**，只会产生「弱覆盖 + 按关键词近似匹配」这种更保守的分档。

### 面板与「改动对照」「要求覆盖」「未覆盖要求」三个页签打架

**[四个页签都在讲改动] → 用户分不清该看哪个。**
**缓解**：四个区块各有分工（系统设计 §2.1 的分工表）：「生成经过」讲过程、「模型调用」讲代价与时长、「要点取舍」讲**取舍的依据**、「模型改写与换回」讲**出处的出处**——都不与已有页签重复。浏览器验收要专门走一遍。

### `explain` 让 `versions.payload` 变大

**[每条要点一行依据摘要] → payload 变大。**
**缓解**：列表剥离 `explain`，详情才带。`explain` **不复制整份简历正文**——它引用要点 id 与文本片段，而 `diff[].fromText` 本来就是原文，没有新增一类敏感数据（系统设计 §5.4）。

### 缓存键不含裁剪参数

**[改了 `LLM_MAX_CANDIDATE_BULLETS` 之后，旧的缓存分析仍按旧口径返回] → 面板显示的 `comparedBullets` 与当前配置不符。**
**缓解**：面板显示的是**当时的真值**（`explain` 与分析结果在生成时一次性写进 payload）。要改配置后清缓存（`jd_analyses` 每账号只留 20 份，自然淘汰）。本轮按「运营上改配置后清缓存」处理（系统设计 §5.2）。

### 客户端超时早于服务端完成

**[用户以为失败了] → 可能白等一次，或重复生成。**
**缓解**：超时提示写明「刷新版本列表看看，这次可能已经生成好了」；`Idempotency-Key` 保证重试命中第一次的结果，不会生成第二份。

### F3：动了冻结的数据模型

**[`ResumeVersion` 加了字段、`DiffEntry` 加了字段] → 形式上撞 F3「数据模型与 schema v1 已冻结」。**
**论证为不撞**（系统设计 §1.3）：F3 冻结的是字段、序列化与迁移规则，危害写的是「P4 要改已落库结构 → 数据迁移 + 客户端兼容双改」。本设计的实际情况：

| F3 担心的 | 本设计的实际情况 |
| --- | --- |
| 数据迁移 | **不需要**。`versions.payload` 是 jsonb，`explain` 是**新增的可选键**，旧行没有这个键就是没有，不需要回填、不需要转换。 |
| 客户端兼容双改 | **不需要**。前端读 `version.explain`，取不到时按「这一版生成时没有记录生成过程」显示——老版本天然走这个分支。 |
| 改 schema | `versions` 表的**列**一个没动；`server/src/db/schema.ts` 不改；不加列、不加索引、不写迁移 SQL。 |

**这是向后兼容的扩展，不是存档结构变更。** 但它确实动了 F3 冻结的类型，所以**在 proposal 里显式留痕**，让评审能推翻这个判断；若评审认为仍算结构变更，备选方案是新增 jsonb 列 + 迁移（代价是多一个 SQL 迁移文件与 `schema.ts` 改动）。

### F8：隐私口径要改一句

**[`docs/privacy-conclusions.md` §7 现在写「两件事发的是同一批内容」] → 裁剪后两次调用发的不再相同。**
**缓解**：同意的范围**不变**（仍是简历正文 + 这份 JD），只是那句描述要改写成「比对时发的是与该岗位相关的要点子集，改写时发的是进了这一版的要点与其子句」。**发出去的内容变少了，没变多。** 姓名、抬头、联系方式**仍然不发**（`toPromptBullets` 只取分区、条目与要点正文）——这条不变。

### 禁用词复查让整版降级

**[模型正文含禁用词 → 整版回落] → 用户白等一次。**
**缓解**：概率低；接受——底线优先于一次生成的成功率。降级原因要写清是禁用词，不要说成「模型调用失败」。

## Migration Plan

**没有数据迁移，没有部署顺序要求。**

| 场景 | 处理 |
| --- | --- |
| 改动前生成的版本 | `version.explain` 为 `undefined` → 界面显示空态 `no-generation-trace`。**不回填**——回填要重跑模型，成本与隐私都不划算。 |
| 改动前缓存的比对分析 | `jd_analyses.payload` 里没有新的 `call` 字段 → 按缺省处理（模型标识与 token 数为空）。旧缓存会被 `pruneJdAnalyses`（每账号 20 份）自然淘汰。 |
| 数据库结构 | 不变，**不需要迁移 SQL**。 |
| 回滚 | 代码回滚即可。已写入的 `explain` 键会被旧代码忽略（JSONB 里的多余键不影响读取）。 |

**回滚的坑**：回滚后新生成的版本**没有** `explain`（旧代码不写这个键），但已写进去的旧版本仍然带着——旧代码不读它，无害。
