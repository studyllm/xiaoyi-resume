## Context

服务端启动需要一批环境变量：数据库连接串、SMTP、站点对外地址。部署时由进程管理器注入，本地开发时按 `server/.env.example` 的说法复制成 `.env` 再改——但没有任何代码读那个文件。

实测：`npm run dev:server` 一启动就退出，报「缺少环境变量 DATABASE_URL」；把 `.env.example` 复制成 `.env` 之后，报的还是同一个错。

后端起不来时，前端控制台看到的是 `GET /api/v1/me 500`。那个 500 是 Vite 开发代理在后端连不上时自己造的，不是服务端发的。

## Goals / Non-Goals

**Goals:**

- `npm run dev:server` 按 README 说的那样能起来。
- 部署时的行为一个字都不变。
- 缺东西时的报错说清下一步做什么。

**Non-Goals:**

- 不改 Vite 代理在后端连不上时的响应。那是开发环境的代理行为；生产环境前后端同源，后端挂掉时 `fetch` 直接失败，走的是「离线」那条状态，不是「出了点问题」。
- 不改接口、错误码与状态表。
- 不引入 dotenv 之类的依赖。

## Decisions

### D1. 用 Node 22 自带的 `process.loadEnvFile`，不装 dotenv

Node 22 自带 `process.loadEnvFile(path)`。实测它**不覆盖进程环境里已有的同名变量**——正好是部署要的语义：注入的值赢，本机文件只补空缺。

dotenv 是同一件事的第三方实现。为一件 Node 已经会的事多引一个依赖，就多一处版本与行为差异。

### D2. 读文件的动作只在启动脚本里，不进业务模块

只有 `server/src/index.ts` 需要它。放进路由或 store 会让每个请求都带着一份「配置文件从哪来」的隐含前提。

### D3. 文件不存在是正常情况，不报错

部署环境没有 `.env`。缺文件返回 false，进程继续走「只用进程环境」那条路。

### D4. 抽成独立的小函数，好测

`index.ts` 一 import 就启服务，没法在用例里加载。抽成 `loadLocalEnv(dir)` 之后三条都能测：临时目录里放一个 `.env` → 读得到；进程环境里已有同名变量 → 文件里的值不覆盖它；文件不存在 → 返回 false，不抛错。

### D5. 缺变量的报错带上补救步骤

现在缺变量时只说「缺少环境变量 DATABASE_URL」，不说人该怎么办——正是仓库里「每条失败都给出下一步」那条原则的漏网之鱼。改成同时给出本地怎么补：

```
缺少环境变量 DATABASE_URL
本地开发：cp server/.env.example server/.env 后按需修改
```

部署环境没有 `.env` 可复制，那条提示对部署者无用，但无害——部署时环境变量由进程管理器注入，缺了本来就是配置事故。

### D6. 仓库卫生守卫改判「会不会被提交」，不是「磁盘上有没有」

本地开发要在 `server/.env` 里放服务端的配置。守卫扫磁盘，看到这个文件就判失败——于是**照着 README 走的人，门禁是红的**。

规格写的是「环境变量文件 SHALL NOT **入库**」，场景写的是「出现在**待提交的内容**中」。守卫的实现比规格严：被 git 忽略的文件进不了仓库，不构成风险。

改法：判断一个文件会不会被提交，看 git 的忽略规则（`git check-ignore`），而不是看它在不在磁盘上。拿不到 git 的判断时按会被提交处理——保守。

守卫仍会拦住真正危险的情况：一个不在忽略规则里的 `.env`，`git add .` 就会把它收进去。

## 验证方式

- `server/src/config/env.spec.ts` 三个用例覆盖 D4 的三条。
- `frontend/src/repo-hygiene.spec.ts`：两个用例覆盖 D6——被忽略的 `.env` 放行，没被忽略的 `.env` 拦下。
- 手工：复制 `.env.example` 为 `.env` → `npm run dev:server` → 起得来（此前报「缺少环境变量 DATABASE_URL」）。
- 手工：`curl http://localhost:5173/api/v1/me` 经前端代理返回 401 与 `AUTH_REQUIRED`，不是 500。
