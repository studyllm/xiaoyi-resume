## Context

`docs/v0.1-产品需求文档.md` 定义了「小易」v0.1 的完整规则：一份结构化底稿 + 针对每份 JD 的不可变版本快照。但仓库中没有任何可运行产物，PRD 的规则从未被外化成可点击的交互契约。

本次变更交付一个**纯前端、无后端**的交互原型。它不是产品的最终实现，而是规则的第一次可执行验证：解析、诊断、生成三个环节的边界条件（尤其"不编造"）必须先在原型里跑通，实现阶段才不会反复推翻。

最关键的产品约束来自 PRD §7.3：生成版本只允许重组、删减、强调底稿中已存在的事实，可以调整措辞使结果更清楚，但**不得新增底稿中不存在的公司、项目、职责或数字**；材料不足以支撑 JD 要求时保持原样并显式说明缺什么。这条约束直接决定了原型的架构——所有"生成"行为必须可被机器校验，而不只是看起来合理。

约束环境：

- 技术栈由需求方指定：Vue 3 + TypeScript + Element Plus，独立置于 `frontend/`。
- 原型必须可离线运行、不发任何网络请求；数据存浏览器本地。
- PDF 上传在本原型中是**占位**：点击提示原型阶段不支持解析并引导改用粘贴文本。这是有意为之的偏差——它把"解析失败降级"这一最难的状态从原型范围中移除，代价是 PRD 验收标准中"PDF 能解析时得到可编辑底稿"一条不被原型覆盖。

## Goals / Non-Goals

**Goals:**

- 一条可点击走通的主流程：登录 → 放入底稿 → 结构化编辑 → 诊断（可跳过）→ 粘贴 JD 生成版本 → 版本列表 → 版本详情（改动对照 / 未覆盖要求 / 复制正文）。
- 底稿保存为可编辑的结构化内容（教育 / 经历 / 项目 / 技能），而非不可改的文本文件；每条要点有稳定 ID，供诊断意见与 diff 锚定。
- 诊断只评价底稿本身，每条意见落到具体句子并说明问题；不输出总分，不自动改写底稿。
- 版本生成遵守不编造约束，且该约束**可被机器校验**并在界面上自证。
- 版本是快照：底稿后续修改不回写旧版本；同一份 JD 可重复生成出两份快照。
- 引擎层是纯函数、确定性的，将来替换为真实后端时视图与 store 零改动。

**Non-Goals:**

- PDF 解析（占位）、Word / 图片 / 在线表格导入。
- 精美 PDF 导出、在线排版编辑器、模板市场。
- 多份底稿、简历库、协作、个人设置页。
- 任何题库、考点、刷题、模拟面试相关能力——PRD §8 规则 5 明确排除。
- 真实模型调用。原型中"解析 / 诊断 / 生成"均由本地规则引擎模拟。

## Decisions

### D1 原型形态：可走通的交互原型，而非静态页面

**选择**：本地 mock 引擎 + Pinia + localStorage 持久化，全流程可真实点击、数据可跨会话保留。

**替代方案**：① 写死数据的静态页面——开发快，但评审无法演示"改底稿 → 旧版本不变"这类快照语义，而快照语义正是 v0.1 最容易做错的地方；② 接入真实 LLM——需要 API key 与后端代理，且模型输出不确定，无法用于回归验证。

**代价**：需要认真设计 mock 引擎，初期投入高于静态页面。换来的是规则被验证过一次，且引擎可被断言覆盖。

### D2 引擎作为端口而非工具函数

视图层不 import 具体引擎实现，只通过 `useEngines()` 取实例：

```ts
export interface ResumeEngines {
  parseDraft(rawText: string, ctx: EngineContext, seed: IdSeed): ParseResult
  diagnose(draft: Draft, ctx: EngineContext): DiagnosisResult
  generateVersion(draft: Draft, jdText: string, ctx: EngineContext, options?: GenerateOptions): GenerateVersionResult
}
```

`mockEngines` 是当前唯一实现；未来 `httpEngines` 实现同一接口并把 `ctx.now` 换成服务端时间即可，视图与 store 零改动。

时间注入 `ctx.now`，引擎内部一律不调用 `Date.now()`，ID 用计数器而非随机数——同一份输入的输出完全可复现，这是快照测试与断言的基础。

### D3 领域模型：底稿结构化 + 稳定 bullet ID

```ts
interface Draft {
  id: string; userId: string; revision: number
  sections: DraftSection[]   // education | experience | project | skills
  updatedAt: string
}
interface DraftSection { id: string; kind: SectionKind; title: string; items: DraftItem[] }
interface DraftItem {
  id: string
  org?: string        // 公司 / 学校
  title?: string      // 职位 / 项目名
  start?: YearMonth | null
  end?: YearMonth | null
  present?: boolean   // 至今
  bullets: Bullet[]
}
interface Bullet { id: string; text: string }
```

bullet ID 在编辑文本、增删条目后保持稳定（新增用计数器生成，不复用），诊断意见与 diff 条目都靠它锚定。

**替代方案**：直接存一份纯文本并按行号锚定——但用户编辑后行号漂移，锚点全部失效。

### D4 解析引擎：表头切分 + 启发式兜底

`parseDraft(rawText)` 分三步：

1. **分区识别**：按中文简历惯例关键词切分（教育背景 / 工作经历 / 项目经历 / 专业技能 及变体），每个表头映射到一个分区 kind。
2. **条目抽取**：经历 / 项目 / 教育分区下，识别「公司/机构 + 职位/项目名 + 起止日期」的头行，其余行按 `· - •` 前缀或独立行归为 bullet。日期统一归一为 `YearMonth`（YYYY.MM），支持 `2021.03-2023.06`、`2021/03 - 至今`、`2021年3月` 等写法。
3. **兜底**：检测不到任何表头时，按启发式分组（首个日期行作为经历起点、连续的短行归入同一段、孤立长行归入经历），并**降低置信度**。

低置信度时，导入页展示解析结果预览 + `el-alert` 提示「结构识别不完整，请确认后再保存」，用户可直接在导入页修正后保存，而不是被强制进编辑页逐项修。

### D5 诊断引擎：规则表，每条锚定到具体句子

诊断**只读底稿，不接触 JD**。三类焦点区各由一组规则驱动：

| 区 | 规则示例 | 判定要点 |
|---|---|---|
| 只有职责没有结果 | 有职责动词（负责/参与/协助/跟进/完成/开发）但句中无结果信号 | 结果信号 = 数字 / 百分比 / 量级词（提升、降低、缩短、上线）/ 从…到… 对比 |
| 表述空泛 | 命中泛化词（团队协作、认真负责、日常维护、业务需求、积极向上） | 泛化词表 + 无技术名词 + 无指标 |
| 时间线或结构不顺 | 缺开始时间；结束早于开始；同分区区间重叠；未按时间倒序；分区为空 | 重叠只在 experience 分区判定（项目并行是常态，跨分区判重叠会大量误报） |

每条意见包含：类别、严重度、引用的原句（问题片段 `<mark>` 高亮）、"问题是什么"、"建议怎么改"、以及「定位到句子」按钮（跳到底稿编辑页并聚焦该 bullet）。

**不输出总分**——界面只显示条数，不计算任何"简历质量分"。

**建议文案的安全边界**：建议给句式模板，槽位用 `〈你的指标〉` 占位，**不出现任何具体数字示例**（否则用户会直接抄走编造的数字）。全文禁止出现面试/八股/考点/题库/刷题等词，引擎出口统一走 `assertCleanOutput()` 断言。

严重度三档（高/中/低），排序键为 `(严重度降序, 分区顺序, 条目内下标, bulletId)`——同严重度内保持文档顺序，符合"顺着读下去"的直觉。

### D6 生成引擎：证据分级 → 排序删减 → 受限改写

这是整个原型的核心，分四步。

**第一步：JD 解析。** 切句 → 过滤样板行（公司简介 / 福利待遇 / 薪资 / 工作地点等）→ 抽取岗位名与候选要求。

岗位名识别按优先级：`岗位：X` 类显式标注 > `招聘XX工程师` 类 > 首行"看起来像岗位名"（长度 ≤ 24 且命中角色词且不含"岗位职责/任职要求"等）> 前 3 行内的角色短语。**全部识别不到时用可编辑默认名 `版本 {n}`**（n = 已有版本数 + 1，确定性），PRD §7.3 要求版本名始终可改。

要求抽取依赖一个**需求目录**（catalog）：每个条目含 `aliases`（匹配用）、`related`（弱匹配词）、`category`。目录覆盖前端 / 后端 / 数据 / 基础设施 / 架构 / 工程实践 / 软技能 / 语言 / 业务域等类别，例如 React、Vue、TypeScript、高并发、分布式、微服务、Redis、MySQL、消息队列、Docker、K8s、监控告警、CI/CD、DDD、单元测试、带团队、英语等。

匹配规则：拉丁词走词边界（`Go` 不得命中 `Google`，`TS` 不得命中 `TSDB`），中文词走子串；**最长优先 + 掩码**（`Vue` 不抢占 `Vue3`，`Redis` 不抢占 `RedisCluster`）。命中目录词一个都没有的句子走"核心短语兜底匹配"，兜底命中的需求在界面上标注"弱相关（按关键词近似匹配）"，避免误判成强覆盖。

**第二步：证据匹配与覆盖分级。** 对每条 JD 要求，收集：精确命中（bullet 正文命中目录词）、弱命中（命中 related 词）、元信息命中（公司名/职位名命中）、规划性命中（句子处于"计划/后续/预计"语境）。

| tier | 条件 | 语义 |
|---|---|---|
| `strong` | 存在精确命中，且该 bullet 有可衡量结果 | 明确做过且有结果 |
| `weak` | 有精确命中但无结果；或仅弱命中；或仅元信息命中 | 做过但没写清程度 / 只沾边 |
| `none` | 无任何命中；或全部命中均为规划性表述 | 底稿里找不到对应事实 |

**第三步：版本内容构造。**

*保留策略*：教育 / 经历 / 技能分区全部保留（它们构成简历骨架，删掉即失真）；项目分区在"该条目全部 bullet 与 JD 无关"时整条略去——这正是 UI 上「已移除（与该 JD 无关）」的来源。

*排序*：条目内 `head`（与 JD 相关的 bullet）按相关度降序稳定排序在前，`tail`（无关 bullet）保持原相对顺序追加到末尾，标记为「移至末尾」。相关度 = `3×精确命中数 + 1×弱命中数 + 1×其它目录词数 + (有可衡量结果 ? 2 : 0)`。

三条护栏：① 某条目若无相关 bullet，则**不重排**（避免把"QPS 800→3000"这类强结果但未命中关键词的要点甩到末尾）；② 每个条目最多把 60% 的 bullet 移到末尾，至少保留前 2 条在原位；③ **条目顺序永不改变**——经历按时间倒序、项目按重要性，跨条目重排会破坏时间线叙事。

*删减*：条目内上限 6 条（超出按相关度升序移除）；归一化后重复的条目只留第一条；归一化后长度 < 4 的空条目移除。

**覆盖保护闸门**：删减后重算所有要求的覆盖级别，若某要求由 `strong/weak` 降级为 `none`，**回滚该次移除**（优先恢复相关度最高者）。宁可多留几条，也不丢失与 JD 相关的证据。

**第四步：受限措辞改写。** 只允许下表中的变换，任何超出表内的改写视为编造：

| # | 变换 | 为什么不算编造 |
|---|---|---|
| T1 | 删除行首 `· • - *` 与多余空白 | 纯排版 |
| T2 | 全角/半角与中英文间距规范化 | 纯排版 |
| T3 | 删除句首纯衔接状语（`在…期间，`、`同时，`、`此外，`） | 删的是连接词，不改变"谁做了什么" |
| T4 | `负责X的开发` → `开发X`（动词前置换序） | 动词 `开发` 本来就在原句里，只是重排，未提高动词强度 |
| T5 | 目录内技术词统一大小写（`vue`→`Vue`） | 拼写规范 |
| T6 | 去掉句末标点 | 纯排版 |

T4 有禁用守卫：句子含 `协助/共同/配合/支持/参与` 等协作标记时**不执行**——删掉"负责"会把协作事实升级为独立完成。

**明确禁止的变换**（写进代码断言清单）：动词强度上调（负责→主导、参与→负责）、动词强度下调、新增数字或指标、新增实体、新增职责、修改时间、因果缝合（"A，B"→"通过 A 实现 B"）、把 JD 关键词注入不相关 bullet、技能评级上调（熟悉→精通）、数字精度变化。

**不变量校验闸门 `assertNoFactsAdded(src, out)`**：对每条被改写的 bullet 机器校验——输出中的数字 token 必须逐字出现在原句；长度 ≥ 2 的拉丁词与目录词必须出现在原句或条目元信息中；输出的汉字必须出现在原句中；CJK 长度不得超过原句 + 4。违反则**回退为原文**（fail-safe），并记入 `integrity.violations`。

该校验结论显示在版本详情页：「本次生成未新增底稿之外的任何事实（N 条已校验，0 处异常）」——这是 PRD §7.3 的可视化自证。

### D7 diff 模型：内容维度与位置维度正交

每条底稿 bullet **恰好产出一条** `DiffEntry`，保证对照视图不重不漏：

```ts
interface DiffEntry {
  bulletId: string
  change: 'keep' | 'rewrite' | 'remove'      // 内容
  placement: 'same' | 'reorder' | 'to-end'     // 位置
  fromText: string | null
  toText: string | null
  toIndex: number | null
  reason: string
}
```

「移至末尾」不是删除：被移动的 bullet 在版本正文里仍然存在（`toText` 非空、`toIndex` 非空），只是位置变了；被移除的 bullet `toText === null`、`toIndex === null`，且不再出现在正文中。两者在数据层就是两个不同维度，不可能在 UI 上混淆。

UI 呈现为**分区条目卡片对照**：按经历 / 项目分区，每个条目一组卡片，左侧底稿原句、右侧版本文本，标签为 保留 / 改写 / 移至末尾 / 已移除（附原因），已移除项注明"底稿中仍保留"。

### D8 未覆盖要求的表达

对每条 `tier === 'none'` 的 JD 要求生成一条记录：JD 原句（逐字不改）+ 关键词 + 说明（`no-match` 或 `planned-only`，后者文案说明"只以规划性表述出现，没有已完成的事实"）。

版本顶部同时写明版本说明：本版本只对底稿中已有事实做重组、删减与措辞规范化，未新增任何公司、项目、职责或数字；共 N 项 JD 要求在底稿中没有对应事实，已在下方列出。

### D9 持久化：分 key + 版本号 + 迁移链

四个独立 key，各带版本号，便于局部迁移：

```
xiaoyi.meta.v1      { appSchemaVersion, savedAt }
xiaoyi.session.v1   { v, data: { user, session } }
xiaoyi.draft.v1     { v, data: Draft | null }
xiaoyi.versions.v1  { v, data: ResumeVersion[] }
```

读取时只认当前 key；缺失则按 `LEGACY_KEYS` 倒序回溯旧 key，命中后跑 `MIGRATIONS[key]` 迁移链，成功则写新 key 并删除旧 key；迁移抛错则丢弃该片数据并提示一次，**绝不白屏**。`localStorage` 不可用（隐私模式）时降级为内存态并在页头提示"本地存储不可用，刷新后数据丢失"。

### D10 演示模式可见性

全局常驻 `el-alert`：「原型演示模式 · 解析、诊断与版本生成均为本地规则模拟，未接入真实模型；数据仅保存在本机浏览器」；登录页注明「任意用户名 + 任意密码即可进入」；版本详情页注明「本版本由本地规则引擎生成，非真实模型输出」并展示完整性校验结论；提供「载入演示数据」按钮一键复现样例底稿 + 2 份 JD。

**理由**：评审时把 mock 输出误认为真实模型结果是这类原型最大的风险。显式标识的成本远低于误判的代价。

### D11 路由与守卫

| 路由 | 页面 |
|---|---|
| `/login` | 登录 |
| `/import` | 放入底稿 |
| `/draft` | 底稿编辑 |
| `/diagnosis` | 诊断 |
| `/jd` | 粘贴 JD 生成版本 |
| `/versions` | 版本列表 |
| `/versions/:id` | 版本详情 |

守卫规则：未登录 → `/login`；已登录访问 `/login` → 有底稿跳 `/draft`，否则跳 `/import`；**无底稿时 `/diagnosis` 与 `/jd` 不可达**（PRD §6），守卫重定向并 `el-message` 提示。

## Risks / Trade-offs

- **规则误报/漏报**：空泛词表是启发式的，必有误报。→ 每条意见只陈述"这句话缺少什么"，不判定好坏；低严重度默认折叠；提供"忽略此条"（前端本地记住 ruleId+bulletId 组合，不持久化）。同时版本详情页展示 `integrity`，让评审至少看到"没有编造"。
- **T4 动词前置改写的语义边界**：`负责X的开发`→`开发X` 由 PRD 明文许可，但严格看确实把职责表述转成了成果表述。→ 仅在句子不含协作类词时启用，改写后必须通过不变量校验（新增动词必须逐字来自原句），且该行为有独立开关可关。
- **「移至末尾」过多会让条目读起来断裂**。→ 每条目最多移走 60%，至少保留前 2 条留在原位；条目顺序永不改动。
- **整条项目被移出版本可能被评审认为"数据丢失"**。→ 默认只在项目分区且该分区有 ≥2 个条目时触发；每条被移除的 bullet 都在对照视图列出并注明"底稿中仍保留"；行为有开关。
- **覆盖保护闸门会让部分超长条目超过长度上限**。→ 闸门优先级高于上限（宁可多留几条也不丢 JD 证据），版本说明中注明。
- **JD 目录覆盖不到冷门技术栈**。→ 目录表可扩展且带弱匹配词；无关键词需求走核心短语兜底；仍未命中的需求会作为"未覆盖"列出，用户自行判断，不会因引擎不认识而悄悄丢掉。
- **JD 正文可能含笔试/算法题等内容**（真实 JD 常见）。→ 含禁止词的需求不进入覆盖与未覆盖清单；展示 JD 原文时对禁止词做掩码并注明"与本版本无关的题目类内容已隐去"。
- **localStorage 容量**：多版本各带一份快照会膨胀。→ 每版快照仅保留条目文本与元数据；超过 20 个版本时提示用户清理，但**不自动删除数据**。
- **纯前端无法真正验证"稿子跟着人走"**。→ 登录态存本地，页头显式标注演示模式与"数据仅存本机"，避免评审误判。
- **原型不覆盖 PDF 路径**（已知偏差）。→ 在提案与页面上均显式声明，评审时不会被当作漏做；实现阶段需补齐解析与降级编辑态。

## Migration Plan

本变更全部新增于 `frontend/`，不修改仓库中任何既有内容（`docs/`、`openspec/`），回滚即删除 `frontend/` 目录。

实施顺序遵循"先地基后视图"：

1. `domain/types.ts` + `domain/ids.ts`（无依赖，先稳定下来，后续模块都依赖它）
2. `engines/textUtils.ts`（词表与正则）+ `engines/catalog.ts`（目录表），配单测
3. `engines/parseDraft.ts` + 单测 → 接 `/import`
4. `engines/diagnose.ts` + 单测 → 接 `/diagnosis`
5. `engines/transforms.ts`（允许/禁止表 + 不变量闸门）→ `engines/generateVersion.ts` + 单测 → 接 `/jd`、`/versions`、`/versions/:id`
6. `stores/persistence.ts`（localStorage + 迁移链）→ 接入各 store
7. 布局、演示模式标识、演示数据
8. 回归：改底稿 → 旧版本不变；同 JD 生成两次 → 两份快照共存；退出登录再登录 → 数据还在

引擎层用 vitest 单测（不依赖 Vue）：`parseDraft` 覆盖标准中文简历 / 无分区头 / 乱序 / 仅项目 / 技能型文本 / 纯乱码六类输入；`diagnose` 每条规则至少一正例一反例；`generateVersion` 断言 `assertNoFactsAdded` 对全部输出通过、版本正文数字集合 ⊆ 底稿数字集合、同一输入两次生成结果完全一致（除时间戳与版本 ID）。

## Open Questions

1. `dropIrrelevantProjects`（整条略过与 JD 无关的项目）默认开还是关？建议先开，演示时可一键关。
2. 诊断的"忽略此条"是否持久化到 localStorage？原型阶段内存即可。
3. 严重度对用户展示三档标签（高/中/低）还是收敛为两档（需要改 / 建议改）？三档信息量大，两档更克制。
4. 技能分区是否要进一步拆成"技术名 + 熟练度"结构？v0.1 保持自由文本，熟练度由作者自己写。
5. 版本元数据是否附引擎版本号（`engineVersion`）？建议加，便于将来替换引擎后区分历史版本。
