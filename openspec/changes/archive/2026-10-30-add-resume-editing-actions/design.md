## Context

上一轮把编辑页从表单换成纸面时，只搬了"改"的部分：

```
编辑模式下的按钮： ['重新导入简历（覆盖）', '', '', '新增联系方式']
新增条目入口：0    新增要点入口：0    删除条目入口：0    删除要点入口：0
```

`draftStore` 里的 `addItem` / `addBullet` / `removeItem` / `removeBullet` 方法都还在，只是没有任何 UI 入口。

同时"即时保存"没有边界带来两个后果：

```
改字前：简历修订号 1
打了 7 个字后：简历修订号 8
```

修订号成了按键计数器；而内容一旦落库就无法撤回，改错一个字永久生效——简历没有草稿历史。

## Goals / Non-Goals

**Goals:**

- 编辑模式能新增要点、条目、技能行，能删除条目与要点
- 修订号按"一次保存"计，而不是按键计
- 纸上的新增入口说清楚新增的是哪一层
- 空对象不留壳；删除不可逆所以要二次确认
- 键盘流完整，能不碰鼠标改完

**Non-Goals:**

- 不做撤销栈（用户已定：暂不做）
- 不做拖拽排序（顺序仍由用户手工维护，诊断负责提醒）
- 不改诊断规则、批注内容、覆盖分级与版本能力
- 不改领域模型与存储键的结构，只改写入时机

## Decisions

### D1 内容即时更新，固化为显式保存

```
draft          当前内容（编辑即改，始终在内存里）
savedRevision  已保存的修订号 ← 只有点保存才 +1
savedSnapshot  上次保存的内容  ← 供「放弃修改」用
dirty          有未保存的修改
```

关键在于**内容不丢**：改动一直写在内存的 `draft` 里，用户切页面、切模式都不会丢字。变的只是"什么时候写进本地存储、什么时候算一次修订"。

如果改成"改动先落在草稿、保存才提交"，用户会面临"编辑了半天忘了保存"的经典焦虑；现在这个模型里，唯一的风险是刷新页面丢掉未保存的修改，而这一点有 `beforeunload` 提示兜着。

### D2 预览模式显示当前内容（含未保存）

如果预览显示"已保存的内容"，编辑到一半切预览，未保存的改动就看不见了，用户会以为丢了。

取"预览 = 当前内容的只读视图"。这样两个模式的差别仍然只有**能不能改 + 有没有批注**，正是最初拆模式的初衷，不再多一层"内容是不是最新的"。

### D3 生成版本与导出 PDF 前自动保存

版本记录"生成时的简历修订号"。带着未保存的修改去生成，内容是新的、修订号是旧的，对不上。

取自动保存 + 一句提示，不打断用户。导出 PDF 同理——导出的必须是当前看到的内容。

### D4 离开页面提示未保存

路由离开与刷新页面都要提示。这是显式保存有没有意义的前提。

两条路径能力不同，分开处理：

```
路由离开  自建弹窗，三个选择：保存并离开 / 放弃修改并离开 / 留在本页
页面刷新  浏览器原生 beforeunload 提示，只有"离开 / 留下"两种
```

刷新这条路给不了三个选择——浏览器只允许自定义一句提示文字，用户点"离开"就是丢。弹窗那三个选择是应用自己画的，所以能分清"保存""放弃""留下"。

### D5 纸上的新增入口用行内占位，且措辞区分层级

```
方案 A  行内占位，hover 出现「＋ 新增一条要点」/「＋ 新增一段工作经历」
方案 B  常驻 + 按钮
方案 C  命令面板
```

取 A。纸上放常驻按钮会破坏"这是一份简历"的感觉；命令面板可发现性太差。

**关键是两个层级都用文字而不是图标**，因为它们的粒度不同，光看一个"＋"分不出是加要点还是加经历。四个分区各说各的话：

```
教育背景  ＋ 新增一段教育经历
工作经历  ＋ 新增一段工作经历
项目经历  ＋ 新增一个项目
专业技能  ＋ 新增一条技能
```

专业技能区没有"条目"这一层（它是一条条技能行），所以那里的新增落在要点层。

### D6 新增后立即可输入，空对象自动清理

```
新增一条要点   → 空要点出现，占位「点此写一条要点」，焦点落在上面
新增一段经历   → 空条目头出现，焦点落在第一个字段
空对象失焦仍为空 → 自动移除，不在纸上留空壳
Esc            → 取消当前这条空的要点或空条目
```

自动清理很关键：一张有五个空壳要点的纸比一张少三个要点的纸更让人心烦。

### D7 删除用二次点击确认

不做撤销，所以删除不可逆。二次点击（点「删除」变成「确认删除？」）比弹窗更不打断，又比直接删安全。

### D8 键盘流是"更方便"的主体

```
Tab / Shift+Tab   条目头字段之间、要点之间移动
Enter（要点里）   下方新建一条要点并聚焦
Shift+Enter        要点内换行（一条要点通常是一行，所以 Enter 建新条）
Esc                取消空的要点或空条目
Cmd/Ctrl+Enter    保存并退出编辑模式
```

Enter 建新条而不是在要点里换行——简历的一条要点通常就是一行，这与 Word 列表的行为一致。

### D9 新增的条目插在末尾

简历按时间倒序排，新经历通常是最近的，插末尾会顺序不对。

但底稿的顺序本来就是用户手工维护的（诊断只提醒、不自动重排），所以这条闭环是现成的：新增插末尾，诊断的「未按时间倒序」会告诉用户顺序不对。这与"自动按时间插入"相比更符合"用户掌控顺序"的设计。

### D10 保存与放弃的位置

编辑模式的页头：

```
我的简历                [修订号 3] [预览|编辑]  [保存] [放弃修改]
```

- 「重新导入简历（覆盖）」只在**预览模式**出现——编辑时它会冲掉修改，没有意义
- 有未保存的修改时，修订号标签显示「修订号 3 · 未保存」
- 页头已被约束到纸的宽度（794px），编辑模式元素更多；若嫌挤，「放弃修改」可收进「更多」下拉

## Risks / Trade-offs

**[用户改了不保存就刷新，内容丢失]** → `beforeunload` 提示 + 页头的未保存标记常驻可见。风险可接受，因为不保存的窗口本来就很短

**[「保存」按钮被忘记]** → 未保存标记常驻 + 离开页面时提示 + 生成版本前自动保存，三重兜底

**[自动保存会打断"我要放弃这次修改"的意图]** → 只在生成版本与导出 PDF 这两个"必须固化"的时刻自动保存，编辑过程中的普通保存仍由用户显式点击

**[hover 才出现的入口在触屏上不可用]** → 原型以桌面为主；若要支持触屏，这三处入口改为常驻

**[空对象自动移除可能删掉用户正在填的内容]** → 只在"内容确实为空"时移除；填了一点的不会被动

**[纸面新增入口需要 ResumePreview 留插槽]** → 复用已有的插槽机制，不改动纸面的排版逻辑

## Migration Plan

1. `draftStore` 拆分"改动"与"保存"：引入 `savedRevision` / `savedSnapshot` / `dirty`，移除逐字输入时的修订号递增与写入
2. `ResumePreview` 增补两个插槽：分区末尾的新增入口、条目末尾的新增入口；条目与要点的删除入口
3. `DraftView` 接入：保存与放弃、未保存标记、空对象清理、键盘流、删除的二次确认
4. 路由离开与 `beforeunload` 的未保存提示
5. 生成版本与导出 PDF 前自动保存
6. 验证：新增三类对象、删除、空态清理、修订号按保存计、离开提示

**回滚**：改动集中在 store 的保存时机与编辑页的交互，无数据迁移。

## Open Questions

本设计无遗留开放问题。以下六项已定案：

| 问题 | 结论 | 落在 |
|---|---|---|
| 修订号怎么算一次修改 | 显式保存算一次 | D1 |
| 撤销做不做 | 暂不做 | Non-Goals |
| 新增的条目插在哪 | 插末尾，靠诊断提醒顺序 | D9 |
| 预览显示什么 | 当前内容（含未保存） | D2 |
| 生成版本前要不要先保存 | 自动保存 | D3 |
| 空要点的占位文案 | 「点此写一条要点」 | D6 |
