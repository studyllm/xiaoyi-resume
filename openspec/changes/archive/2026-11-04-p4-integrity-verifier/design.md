## Context

PRD 承诺的是「不得新增不存在的**公司、项目、职责或数字**」——四类。当前口径用的是「不许出现新汉字」这条更强的规则，它恰好覆盖四类，但代价是任何措辞改动都被拦。

要换的口径不是「放松」，而是**换判据**：从字符级换成成分级。

## Goals / Non-Goals

**Goals:**

- 判定只认「事实」，不认「措辞」。
- 抽取与判定都确定性，同一底稿两次结果全等。
- 误伤方向安全：宁可回退，不可放过。
- 形状定死，P3 能据此建 schema。

**Non-Goals:**

- 不做语义判定（「谁来判判判者」是另一个问题）。
- 不做数值单位换算。
- 不写可执行规范（那是 D4 的 `docs/fact-traceability.md`）。

## Decisions

### D1. 成分分五类，只硬判四类

度量、拉丁实体、技能评级、职责动词 → 硬判定。中文实词 → 只记录。

**理由**：确定性规则分不清「前端开发→前端工程」（合法改写）与「支付宝→微信支付」（语义编造）。前四类恰好对应 PRD 承诺的四类，且都能用确定性规则判。

**代价**：LLM 的换词能力被限制。这划定了 LLM 的职责边界——它做重组与取舍，换词交给规则引擎。

### D2. fact = 子句级，`factId` = 内容哈希

**理由**：整条要点做 fact 会让引用过宽（回到当前口径的毛病）；`factId` 取哈希让「同一底稿两次抽出的 fact 集合全等」自然成立，且跨版本可对照。

### D3. claim 的置信度不参与判定

**理由**：自评分数若参与判定，就是模型自己说自己可信。判定只看引用是否充分。

### D4. 回退目标是规则引擎的产出

**理由**：验收项 A4.2 要求「回退后输出与规则引擎逐字一致」；规则产出本身已被校验过，质量不低于源句。LLM 实现必须先跑一遍规则引擎作为回退备选。

### D5. `integrity.reason` 结构化

界面要按类型分组展示（「有 2 处新增了数字」「有 1 处职责被上调」），自由文本做不到。

### D6. 形状定死，P3 立即建表

F3 要求 schema 为 P4 预留扩展位。预留的具体形状现在是确定的，与其留一个含糊的 `extra JSONB`，不如把 `Fact` / `Claim` / `VersionTrace` 定死。

**理由**：含糊的预留位等于没有预留——到 P4 时还是要吵一遍形状，而那时 schema 已经落库了。

## Risks / Trade-offs

**[R5（中文实词）误伤率高]** → 误伤方向安全（回退后仍是一份能投的简历）。以 P4 的灰度对比数据衡量，必要时重开。

**[动词表/评级表要人工维护]** → 表要随引擎一起维护，超出表的词按强度 0 处理（不会造成上调误判）。

**[fact 粒度可能不合适]** → 以灰度对比里 claim 的数量分布与判定通过率为依据重开。

**[`trace` 放在版本内部会重复存 facts]** → 同一底稿修订号的多个版本各存一份。对 v1.0 的数据量可接受，换来的是版本自足——审计一份版本不需要 join 别的表。

## Migration Plan

无代码改动。P3 建表时按新形状建，P4 填内容。
