## Context

原型功能上已经跑通，但**界面没有自己的语言**：

```
硬编码颜色      66 处，散在 13 个文件
CSS 变量        4 个（--xiaoyi-bg / text / muted / border）
Element Plus    从未覆盖过主题 → 默认蓝 #409EFF
字体            继承组件库默认，未分层
圆角 / 阴影     各页各写一套
```

结果是界面看起来像任何一个用 Element Plus 做的后台面板。同时同一个产品里存在三种形态：编辑页是表单、诊断页是纸 + 批注、版本列表是表格。

而这个产品的本质是**在一份简历上批注**——诊断页那套气质是对的，只是没有推广。

这一轮的设计目标不是"变好看"，是**让界面在说同一件事**：你在纸上工作，纸就是你的简历。

## Goals / Non-Goals

**Goals:**

- 建立一套设计变量层，界面与纸面的视觉属性全部来自变量
- 主色与组件库一致，且**颜色只承担语义**
- 字体分层：界面无衬线、纸面衬线
- 编辑页与诊断页共用「纸 + 侧栏」布局，纸是内容承载形式
- 版本列表用卡片，落地页首屏用真实简历 + 批注
- 用测试把「不写死视觉字面量」这条锁住

**Non-Goals:**

- 不改任何业务逻辑：诊断规则、覆盖分级、排序护栏、删减闸门、措辞变换与不变量校验
- 不改数据模型、存储键与迁移链
- 不新增 npm 依赖
- 不做暗色模式（简历要打印和投出去，暗色无意义）

## Decisions

### D1 两层结构：变量层与语义层

```
tokens.css   ── 变量：颜色、字号、圆角、阴影、间距
   ↓
语义映射      ── 这个变量表示什么：--color-severity-high / --color-action / --color-surface-paper
   ↓
组件与页面     ── 只允许用语义变量或原始变量，不允许写死
```

原始变量（数值）与语义变量（含义）分开，是为了避免"这个蓝色到底是主色还是链接色"这类歧义在代码里蔓延。

### D2 主色松墨青，Element Plus 用 CSS 变量覆盖，不引 sass

实测确认 Element Plus 全程使用 `var(--el-color-primary)` 与其阶梯变量，所以覆盖变量即可换肤，**不需要 sass 编译主题**：

```
--el-color-primary:         #0F766E
--el-color-primary-rgb:     15, 118, 110
--el-color-primary-light-3: #579F99
--el-color-primary-light-5: #87B1AC
--el-color-primary-light-7: #B7D6D3
--el-color-primary-light-8: #CFE3E2
--el-color-primary-light-9: #E7F1F0
--el-color-primary-dark-2:  #0C5E58
```

**必须用 `html:root` 而不是 `:root`**：组件库的 base.css 里也是 `:root` 定义同一批变量，同特异性下由加载顺序决定谁赢。`html:root` 特异性更高，**覆盖结果与样式加载顺序无关**——这点在按需引入组件库时尤其重要，因为组件的样式是按 chunk 注入的，顺序不可控。

### D3 颜色只承担语义

```
角色              颜色            用在哪
────────────────────────────────────────────────
主色              松墨青 #0F766E   可操作的元素：主按钮、链接、焦点环、活动态
高严重度          #DC2626          批注、问题高亮
中严重度          #D97706          批注、问题高亮
低严重度          #64748B          批注、问题高亮
成功              #16A34A          已处理、校验通过
纸面              #FFFFFF          内容承载
桌面              #F2F3F5          画布背景
墨色梯度          #16181D → #E6E8EC 文字与分隔线
```

**主色不能用红、橙、靛蓝**——这三个色相已经被批注严重度占用了，界面上一旦出现同色系，用户分不清「这是重要」还是「这里有问题」。所以主色落在青绿区间。

低严重度用板岩灰而不是靛蓝：靛蓝与青绿同属冷色，邻近时区分度不够；板岩灰还顺带表达了"轻微"的分量。

### D4 字体分层：界面无衬线，纸面衬线

```
界面  -apple-system, BlinkMacSystemFont, 'Segoe UI', 'PingFang SC',
      'Hiragino Sans GB', 'Microsoft YaHei', sans-serif
纸面  'Songti SC', 'SimSun', 'Source Han Serif SC', 'Noto Serif CJK SC', serif
```

**为什么纸面可以用衬线而不破坏"所见即所得"**：阶段三之后，编辑页上呈现的就是那张纸本身，导出用的是同一份 DOM 与同一套 CSS。纸面用什么字体，屏幕上的纸和导出的 PDF 就是同一个字体——一致性没有被破坏。被区隔的是"界面 chrome"，那本来就该用屏幕友好的无衬线。

字号也分层：界面用 px（14/13/12），纸面用 pt（正文 10.5pt、标题 12pt、姓名 18pt），因为纸面要对应真实打印尺寸。

### D5 纸是内容的承载形式：编辑页与诊断页同一套布局

```
┌──────────┬──────────────────────────┬──────────────┐
│ 产品导航  │        纸（可编辑）        │  批注         │
│ ────────  │                          │  ▓ 缺可衡量结果 │
│ 分区目录  │   张三                    │    建议：…     │
│  教育  1  │   前端工程师 · 6 年经验     │  ▓ 表述空泛    │
│  工作  2  │   138-… · zhangsan@…      │              │
│  项目  2  │   ──────────             │              │
│  技能  1  │   工作经历                │              │
│          │   美团  前端工程师  …      │              │
└──────────┴──────────────────────────┴──────────────┘
   200px           794px 纸                320px
```

编辑页与诊断页的**结构完全相同**，唯一的差别是纸能不能编辑。这本身就是产品的故事：看批注 → 改 → 再看。

**左侧只有两栏，不设第三栏**：产品导航（我的简历 / 简历诊断 / 按 JD 生成 / 定向版本）与当前简历的分区目录合并在同一侧栏——上导航、下目录。分区目录取代了原来的分区页签：纸没有页签，页签是后台思维。

分区目录项显示分区名与条目数，点击滚动到纸上对应位置。

### D6 阶段三的三页改造

**编辑页**：分区页签 → 长纸。抬头、条目、要点就地编辑：抬头是纸顶部的两个行内输入，条目是纸上的标题行（公司/职位/日期），要点是纸上的正文段。日期仍用月份选择器，但触发后是纸上的行内弹出层。

**诊断页**：已是「纸 + 批注栏」，本轮做视觉统一，并明确纸为只读（去掉所有输入态）。

**版本列表**：表格 → 卡片。每张卡片是一份简历的缩影：岗位名为主标题、JD 摘要为副标题、生成时间与底稿修订号为元信息、右侧是打开与导出操作。

**落地页**：首屏左侧是一份真实的简历（样例底稿的纸面渲染），右侧挂三四条批注，下面才是产品说明。第一屏直接演示产品在做什么，而不是讲产品是什么。

### D7 交互规范

**破坏性操作默认不出现。** 现在每个条目常驻一个红色「删除条目」文字按钮、每条要点一个红色垃圾桶图标——整页都是删除入口，视觉噪音大且容易误触。改为：悬停该行时，删除操作从右侧滑入。

**三档操作**：

```
主操作    实心主色按钮      每页至多一个：保存、生成、重新诊断
次操作    文字按钮          复制、导出、查看
危险操作  文字 + 危险色      删除、忽略，hover 才现
```

**演示模式提示降噪**：现在是全宽黄色 `el-alert`，每个页面都有一条，占据视觉焦点。改为顶栏下方一条 1px 的低饱和色带 + 侧栏底部一行小字。

**菜单分组**：

```
工作                    交付
  我的简历                按 JD 生成
  简历诊断                定向版本
```

### D8 护栏：视觉字面量扫描测试

改完不锁住，下次加功能又是一堆硬编码。与已有的「界面不得出现『底稿』」那条扫描测试同构：

```
扫描 src/ 下所有 .vue 与 .css 的颜色字面量
tokens.css 自身除外
→ 出现即失败
```

圆角、阴影同理。打印样式也走变量——CSS 变量在打印时同样生效，所以纸面的颜色不需要写死。

## 实现中的发现

**`el-date-picker` 的根是 Fragment，Vue 不会给它加 scope 属性。** scoped 样式里的 `.paper-date :deep(.el-input__wrapper)` 因此完全打不进去（实测：wrapper 的 `box-shadow` 仍是组件库默认的 inset 边框）。解法是用一层**带 scope 的普通元素**包住它，样式改为 `.paper-date-field :deep(...)`。凡是根节点是 Fragment 的组件（`el-date-picker` 是典型）都不能靠根上的 class 做 scoped 选择。

**菜单分组默认展开。** 分组本身是对的（工作 / 交付），但 Element Plus 的 `el-sub-menu` 默认收起，会让「我的简历」这个第一入口变成两次点击。改用 `:default-openeds="['work', 'deliver']"`：保留视觉分组，不增加点击成本。

**行内编辑控件要显式去掉组件库的边框。** Element Plus 的输入框边框是 `box-shadow: 0 0 0 1px inset`，不是 `border`，所以 `border: none` 无效，必须同时写 `box-shadow: none` 与 `background: transparent`。

## Risks / Trade-offs

**[阶段三改动编辑页结构，风险最高]** → 分三阶段交付，阶段一与阶段二可独立发布；阶段三若发现问题可单独回滚，不影响前两阶段

**[三栏布局在笔记本上拥挤]** → 1440px 下：200 + 794 + 320 = 1314，留 126px 余量；窄于 1280px 时批注栏折叠为图标条（机制已存在），纸保持 A4 宽度并允许横向滚动

**[宋体在部分设备缺失]** → 字体栈逐级回退到 `serif`；衬线体在中文环境下几乎必然存在（宋体/宋体屏），不构成风险

**[纸面就地编辑的实现复杂度]** → 要点用 `contenteditable` 或"静态渲染 + 点选后行内输入"两种做法。后者更可控（不与 Vue 的响应式双向绑定打架），也更容易保证"改动只经由 store 落库"。选后者

**[表格改卡片后版本多时不好横向比较]** → 卡片按生成时间倒序，卡片上保留底稿修订号；版本超过 10 个时提供按岗位名过滤

**[Element Plus 组件的圆角与阴影与新 token 不一致]** → 阶段一同步覆盖 `--el-border-radius-base` 与 `--el-box-shadow-light` 等变量，让组件库与自绘界面一致

**[深色模式不做会不会被追问]** → PRD 场景是打印与投递，深色对简历无意义；不做是取舍而非遗漏

## Migration Plan

```
阶段 1（半天）建立 tokens.css
          覆盖 Element Plus 变量阶梯与圆角阴影
          把 66 处硬编码颜色收进变量
          纸面字体改衬线、字号改 pt
          加颜色扫描测试
          → 界面从"默认 Element Plus"变成"有主张"

阶段 2（1 天）破坏性操作改为 hover 才现
          主/次/危险三档用法固化
          演示模式提示降噪
          菜单按工作/交付分组
          → 信息层级清楚

阶段 3（2-3 天）编辑页：长纸 + 分区目录 + 批注栏
          纸上的抬头/条目/要点就地编辑
          诊断页视觉统一
          版本列表改卡片
          落地页首屏改真实简历 + 批注
          → 真正的辨识度
```

阶段一与阶段二是收敛，阶段三是表达。若要先发布一个明显不同的版本，阶段一与阶段二可以先行。

**回滚**：三个阶段各自独立，回滚即还原对应文件；无数据迁移。
