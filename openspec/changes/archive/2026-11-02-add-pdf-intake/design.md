## Context

PRD §7.1 要求上传 PDF 并「尽力解析成文本」，§9 验收第 2 条要求「不能解析时，用户仍能在文本上改完并保存」。当前 `ImportView.vue` 的上传页签是彻底占位——不读文件、不产生任何底稿内容。

**这一版的产物是纯前端原型**，没有后端，所以 PDF 的读取与文字提取全部发生在浏览器里。

实现前先读了 `parseDraft.ts` 与 `domain/time.ts`，摸清了「什么样的文本能被现有解析器吃下」。这个约束直接决定了提取算法，是本次实现里最容易做错的地方。

### 解析器对文本的三条硬性要求

| 要求 | 出处 | 违反后果 |
| --- | --- | --- |
| 条目头与它的起止日期必须在**同一行** | `findDateSpan(line)` 在单行内匹配；`parseStructured` 拿到日期后用同行剩余部分拆公司/职位 | 「美团 前端工程师 …… 2021-03」被拆成两行 → 前一行变成普通要点，后一行变成没有公司名的空条目 |
| 分区标题要在行首，且整行去标点后不超过 12 个字 | `headerKindOf`：先看冒号前的部分，再看 `normalized.startsWith(keyword)` 且 `normalized.length <= 12` | 「工作经历 负责公司营销活动页面的前端开发」整行 17 字 → 这个分区被漏掉，解析结果整体错位 |
| 段落之间靠换行区分 | `parseStructured` 逐行处理 | 全部挤成一行 → 只剩一个要点 |

**第一条是最要命的**：中文简历的条目头是「公司 职位 …… 起止日期」两端对齐的，字面上就有一个很大的左右间距。如果提取时按「间距大 = 分栏」去切，正好会把日期切走。

## Goals / Non-Goals

**Goals:**

- 上传 PDF 能得到可编辑的简历，路径与粘贴完全等价
- 提取不出或质量差时，把已经拿到的东西交给用户，不给死路
- 提取出的文本能被现有解析器正确识别——尤其是条目头与日期同行
- pdf.js 不进主包

**Non-Goals:**

- **不做 OCR**。扫描件交给用户判断并手动补全
- **不还原原 PDF 的视觉版式**——字号、颜色、缩进、图标一概不碰（PRD §7.5 明确不做）
- 不支持 Word、图片、在线表格
- 不改解析引擎 `parseDraft`、诊断引擎、版本生成链路
- 不动 `ResumeEngines` 接口

## Decisions

### 决策 1：PDF 提取放前端，用 pdf.js

`pdfjs-dist@^6`（当前 6.5.438，Node ≥ 22.13，本机 22.22 与 CI 的 Node 22 都满足）。

- **依据**：兜底路径天然属于前端。PRD 要求「不能解析时把已得到的文本交给用户修改」，而「在文本上改」是导入页纸面编辑的既有能力，已存在且已测试。前端解析可以直接复用；后端解析失败后必须把文本再传回前端走同一条路，多一次往返。
- **不破坏匿名可用**：`account-access` 规格明写导入页可匿名使用（粘贴、解析、纸上改都不问身份）。后端解析会强迫「先上传后解析」，与该规格冲突。
- **PII 最小暴露**：简历正文不出本机即可完成摄入，只有用户主动「保存」才出本机。
- **技术成本差异小**：`pdfjs-dist` 在 Node 端同样可用，所以真正的差别在上面三条，不在技术栈。

### 决策 2：`pdfText` 不进 `ResumeEngines` 接口

新增 `frontend/src/engines/pdfText.ts`，但**不**把它挂到 `ResumeEngines` 上。

- **依据**：`ResumeEngines` 是「解析 / 诊断 / 生成」这类**内容语义能力**的端口。PDF 文字层提取是文件 I/O 前置处理，不是内容语义。
- **更实际的原因**：接口里 5 个方法全是同步返回值。服务端引擎必然是异步的，接口异步化是冻结点 F1，明确留给 P3 服务端化。现在把 `pdfText` 塞进去就得提前把接口改成异步，视图与状态层的所有调用点都要二次返工——这正是 F1 要防的事。
- **下游完全复用**：提取出的文本照样走 `draftStore.ingest(rawText)`，与粘贴路径共用解析、置信度、结构问题清单、纸面编辑、保存的部逻辑。

### 决策 3：同一视觉行绝不拆开，空格由空白片段给出

这是从解析器反推出来的硬约束，优先于「还原版式」的考虑。

具体规则：

1. 按 y 坐标把文字片段聚成**视觉行**（容差取该片段高度的一半，最少 2pt）
2. 行内按 x 排序，逐段拼接：
   - 片段内容为空或全是空白 → 贡献一个空格（不贡献内容）
   - 片段有内容 → 直接接上
3. **整行输出为一行**，不管行内间距多大

**为什么用空白片段而不是几何间距判断空格**：实测 Chrome 导出的 PDF 里，真空格是一个独立的空白片段（宽度约 5pt），而两端对齐的间隔也是一个空白片段（宽度可达 340pt）。**片段本身就是「这里有空格」的明确信号**，比拿间距去猜可靠得多——用间距猜会在「一个词的间距」和「一个真空格的间距」之间踩线。

### 决策 4：不做分栏检测，承认这个边界

设计阶段原本打算检测左右分栏并按栏输出。**实施阶段用真实 PDF 探查后决定放弃**，理由如下。

**几何上无法区分两种情况**。实测双栏样本：

```
y=686  "⼯作经历"@x51   "专业技能"@x306     ← 真正的左右两栏
y=742  "经营数据可视化大屏"@x51  " "@x150  "2022-05 - 2022-11"@x442  ← 单栏的右对齐条目头
```

两行都有「左边一段、右边很远的另一段」。但前者是分栏，后者是**同一逻辑行两端对齐**——这正是中文简历条目头的标准形态，而且解析器要求条目头与日期同行（见 Context 的第一条硬约束）。

**误判的代价不对称**。把单栏简历误判成分栏，会把它的内容重排——**为了修少见情况而损坏常见情况**。而双栏 PDF 提取错乱的后果是：解析结果有偏差，用户在导入页的纸上看得见、改得动（这正是「把已得到的文本交给用户修改」这条兜底路径的用途）。

因此 v1.0 **不做分栏检测**，按视觉顺序输出。这条边界写进规格与已知限制，不假装能做到。

将来若要做，正确的信号不是 x 位置，而是**右侧内容是否形成自己的垂直流**（行距规律、条目数够多），而不是「右边远不远的距离」。

### 决策 5：文字统一做 NFKC 归一化

**这一条是实施阶段探查 PDF 才发现的，但它是最关键的一条。**

实测 Chrome 导出的 PDF：部分汉字被映射成了**康熙部首**——

| 原文 | PDF 里提取到的 | 码点 |
| --- | --- | --- |
| 工作经历 | ⼯作经历 | U+2F2F（⼯） |
| 清华大学 | 清华⼤学 | U+2F24（⼤） |
| 项目经历 | 项⽬经历 | U+2F6C（⽬） |
| 页面 | ⻚⾯ | U+2EDA / U+2F25 |

原因是字体里这些字形与部首共享同一个 glyph，PDF 写入时选了先出现的那个码位。

**不做归一化的后果**：每一个分区标题都认不出来（`headerKindOf` 拿「⼯作经历」去比对「工作经历」，`startsWith` 不成立），整份解析结果彻底错位。而这不是个别文件的怪癖——Chrome、以及相当一部分生成器都这样。

`String.prototype.normalize('NFKC')` 能全部还原（康熙部首有到对应汉字的兼容分解）✓。归一化在拼接完成后做一次即可，成本可忽略。

这条也顺带解决了全角/半角、兼容字形等一类的字符偏差。

### 决策 6：质量三档，阈值写死为具名常量

| 档 | 判据 | 出路 |
| --- | --- | --- |
| `none` | 全部页面提取到的文本去空白后为空 | 明确告知没有文字层，引导改用粘贴，焦点交给粘贴输入处 |
| `sparse` | 有文字，但**平均每页字符数 < 80** | **仍把已提取的文本交给用户**，同时明确提示「这份 PDF 能读到的文字很少，可能是扫描件或图片页」 |
| `text-layer` | 其余 | 正常解析 |

**80 这个数怎么来的**：一份正常简历每页约 500–2000 字符；80 远低于任何有文字层的简历的下限，意味这个 PDF 大概率是扫描件（能识别出的往往只有页眉、页脚、水印）。取值刻意压得低，是为了不把「简历本身很简短」误判成扫描件——宁可多提示一次，也不要把能用的文件说成不能用。

`sparse` 档仍然走完整解析，是这一档存在的全部意义：**给用户的是部分真实内容加一句警告，而不是一个空白页**。这正是 PRD 「把已得到的文本交给用户修改」那句话的字面落实。

### 决策 7：不做 OCR，但接口预留

不做 OCR 的理由：需要额外依赖（体积大）、中文识别质量不稳、服务端算力成本高。PRD 只要求「尽力解析」而非「识别一切」。

但接口预留：`extractPdfText` 返回 `{ text, pageCount, quality, warnings }`，`quality` 的取值域里留 `'ocr'`。将来真要加 OCR，只是多一条管线并把 `quality` 置为 `'ocr'`，调用方不用改。

### 决策 8：文件类型按字节判定，不信浏览器给的 MIME

先读文件头 5 字节，必须是 `%PDF-` 才当 PDF 处理。

浏览器给的 `file.type` 来自扩展名推断，可以被改名绕过；而文件头字节是内容自身说的。改名为 `.pdf` 的其它文件会被这一道挡住。

配套限制：大小上限 10MB、页数上限 50 页。一份文本型简历 PDF 通常不到 1MB、1–3 页；10MB 与 50 页都留了很大余量，同时挡住「上传一本扫描版教材」这类误用——那种文件必然落进 `sparse` 档并浪费大量提取时间。

### 决策 9：pdf.js 动态导入，不进主包

`import('pdfjs-dist')` 写在函数内部，只有用户真的选了文件才加载。主包体积不受影响。

worker 用 `import workerUrl from 'pdfjs-dist/build/pdf.worker.min.mjs?url'` 拿地址，再赋给 `GlobalWorkerOptions.workerSrc`。若打包后 worker 起不来（Vite 与 pdf.js 的集成偶有差异），退回 pdf.js 的主线程模式——代价是大文件时界面卡顿，功能不受影响。实现时先验证打包路径，再决定是否需要兜底。

### 决策 10：降级链路复用粘贴路径

提取成功后，**不新写一条解析路径**，而是把文本交给 `draftStore.ingest(rawText)`——与粘贴完全同一个入口。`sparse` 档也走这条路，只是在界面上多一条警告。

这样「两条摄入路径产出同一条底稿」是结构上保证的，不是靠两边代码写得一致。

## Risks / Trade-offs

- **分区标题与正文挤在同一行、且正文超过 8 个字时，这个分区会被漏掉** → 解析结果整体错位。已知边界，不在 v1.0 修：修它需要按字号做字体级切分，收益只覆盖少见版式。漏检会被现有的「置信度偏低」提示与结构问题清单暴露出来，用户在纸上改即可——这正是那条兜底路径的用途。
- **多栏 PDF 的内容顺序会交错** → 这是已知边界（决策 4）。错乱在导入页的纸上看得见、改得动，由低置信度提示与结构问题清单暴露。
- **`sparse` 档的用户拿到的文本可能很碎** → 这是事实，不是缺陷。文案必须说清「能读到的文字很少」，不能让人误以为解析成功。
- **pdf.js 体积不小**（主模块加 worker）→ 用动态导入隔离；只在用户选文件时才下载。
- **worker 打包可能出问题** → 决策 9 留了主线程兜底。
- **改 `ImportView.vue` 会牵动 `flows.spec.ts` 的守卫**（按钮尺寸、实心主色数量、动作区形态）→ 上传页签从占位改成真入口会新增按钮与提示，实施时必须跑守卫。

## Migration Plan

无数据迁移。改动只在新增模块与导入页，上传路径此前不存在，不存在行为回退。

回滚策略：还原 `ImportView.vue` 的上传页签与新增的 `pdfText.ts`，依赖移除即可。粘贴路径完全不受影响。

## Open Questions

- pdf.js 6 的 worker 在 Vite 6 下能否直接打包通过——实现时先验证，必要时用决策 9 的兜底。
- 中文简历 PDF 的真实分布（多少比例是扫描件、多少比例分栏）没有数据。`sparse` 的 80 字符阈值是按常理推的，实施后应拿几份真实简历 PDF 试一遍再定稿。
