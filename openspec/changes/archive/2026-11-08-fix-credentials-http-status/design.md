## Context

`401` 与 `403` 在这套 API 里被混用了：登录失败（凭据不对）回 `401`，而 `401` 本来是给「这个接口要登录态」的。

RFC 9110 §15.5.2 对 401 的定义是「请求缺少目标资源的有效认证凭据」，并且要求响应带 `WWW-Authenticate` 挑战头。§15.5.4 对 403 的定义是「服务器理解了这个请求，但拒绝授权它」。

登录接口不是受保护资源——它是认证入口本身。对它回 401 等于说「你得先认证」。

## Goals / Non-Goals

**Goals:**

- 每个状态码在接口里只表达一种意思。
- 契约文档、错误码表、实现三者一致。

**Non-Goals:**

- 不改任何接口的路径、方法、请求体与响应体结构。
- 不改错误码本身，也不改用户看到的文案。
- 不动 `AUTH_REQUIRED` 的 401。
- 不补 `WWW-Authenticate` 头（见 D4）。

## Decisions

### D1. `INVALID_CREDENTIALS` 改成 403

服务器完整收到了登录请求（请求体合法、字段齐），也明确知道凭据不匹配，于是拒绝授权——正是 403 的定义。

与 `EMAIL_NOT_VERIFIED`（邮箱没验证）同码也顺：两者都是「服务器认识这个账号，但你现在进不去」。而 `401` 从此只留给 `AUTH_REQUIRED`。

### D2. 不用 422

这套 API 里 422 专指「内容处理不了」——解析失败、生成失败、JD 为空。凭据不对也塞进 422 会稀释它已有的含义。

### D3. 改在 v1，不开 /api/v2

契约 §10 写着「不兼容的改动进 /api/v2」。这次确实是不兼容改动，但：

- v1 还没对外发布（README「现状：还在开发」）
- 前后端在同一个仓库里，一起发布
- 没有已发布的客户端会被这个改动打破

冻结契约的目的是保护已有客户端。现在没有。改在 v1，并在契约文档里记一笔，比为一个状态码值两个版本、并行一个发布周期划算。

### D4. 不补 `WWW-Authenticate` 头

RFC 说 401 应当带挑战头。这套 API 的认证方式是 cookie 会话——浏览器每个请求都带着 cookie，**没有可挑战的认证方案**。硬塞一个没注册的 scheme（`Session realm="xiaoyi"`）比不补更糟：严格的客户端会因此中止而不是继续。

这是已知偏差，记在这里而不是留给下一个人重新发现。

### D5. 前端不动

前端按错误码取文案（`stateForCode`），唯一读状态码的地方是「204 → 空体」。改状态码对它没有影响。

## 验证方式

- `server/src/auth/auth.spec.ts`：凭据不对的两个用例断言 `403`，并且邮箱不存在与密码不对的响应体仍然完全相同。
- `frontend/src/flows.spec.ts`：错误码表与状态表一一对应的守卫不受影响（它只对码与状态，不对状态码）。
- 手工：`curl -X POST http://localhost:5173/api/v1/auth/login -d '{"email":"nobody@example.com","password":"x"}'` → 403 + `INVALID_CREDENTIALS`；未带会话访问 `GET /api/v1/me` → 仍是 401 + `AUTH_REQUIRED`。
- 仓库根 `npm run verify` 全绿。
