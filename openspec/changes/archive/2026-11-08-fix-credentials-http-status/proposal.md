## Why

登录接口回 `401`，而这个 401 不该是 401。

`401 Unauthorized` 的 HTTP 语义是「请求缺少目标资源的有效认证凭据」——那是给**受保护资源**用的挑战（RFC 9110 §15.5.2 还要求响应带 `WWW-Authenticate` 头）。登录接口自己就是认证入口，对它回 401 等于说「你得先认证」，逻辑上死循环。

更实际的后果：这套 API 里 `401` 同时表达两件不同的事——「这个接口要登录态」（`AUTH_REQUIRED`，9 个受保护端点）与「你给的口令不对」（`INVALID_CREDENTIALS`，登录端点）。任何按状态码判断的客户端（网关、监控、前端拦截器）都会把「口令打错了」当成「会话过期了」，可能触发一轮无谓的重新登录。

`401` 应当只说一件事。

## What Changes

- `INVALID_CREDENTIALS` 的状态码从 `401` 改成 `403`。服务器理解这个请求（请求体合法），也明确知道凭据不匹配，拒绝授权——这正是 `403` 的定义；并且与 `EMAIL_NOT_VERIFIED` 同码，两者都是「服务器认识这个账号，但你现在进不去」。
- 改完之后 `401` 在这套 API 里只有一个含义：这个接口需要登录态，而请求没有。
- 契约文档同步改：§4.1 的正文与 §5 的错误码表。

**统一排查过其余端点，结论是其余状态码都没问题**，不动：

| 排查项 | 结论 |
| --- | --- |
| 错误码表 22 个码的状态码语义 | 只有 `INVALID_CREDENTIALS` 不对 |
| `401` 的其它 9 处用法 | 全是受保护端点上的 `AUTH_REQUIRED`，正确 |
| 成功状态码 | 注册 201、登录 200、验证/登出/登出全清/重置 204、生成版本 201、幂等重放 201、解析 422 —— 无问题 |
| 有没有硬编码状态码 | 没有，`sendError` 一律从错误码表取 |
| 前端依不依赖状态码 | 不依赖。文案按错误码取（唯一读状态码的是 204 空体），改状态码不影响前端 |

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `account-access`: 新增「状态码各自只说一件事」，并给「登录失败不暴露账号是否存在」补上状态码的约定

## Impact

**代码**

- `packages/shared/src/contracts/error-codes.ts`：`INVALID_CREDENTIALS` 的 http 改 403
- `server/src/auth/auth.spec.ts`：断言跟着改，测试名写清行为
- `docs/api-contract.md`：§4.1 正文与 §5 的表

**不受影响**

- 不改任何接口的路径、方法与请求体
- 不改错误码本身——`INVALID_CREDENTIALS` 这个码与它的用户文案一个字不变
- 不改前端——它按错误码取文案，不看状态码
- 不改 `AUTH_REQUIRED` 的 401：它是「需要登录态」的正确表达
