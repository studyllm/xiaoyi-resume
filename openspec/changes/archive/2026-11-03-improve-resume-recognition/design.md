## Context

用户实测简历导入，「核心技能」整段没进去。用真实语料量化诊断后，问题是一组识别规则的缺口，不是一条：

| 语料 | 诊断结果 |
| --- | --- |
| 分区标题 53 条 | 28 条没被识别（53%）——全部英文标题、8 种中文变体、4 种带序号/装饰的写法、2 种中英混排 |
| 要点 6 条 | 5 条被误当成表头吃掉（内容消失） |
| 日期格式 13 条 | 3 种没认出来 |

根因是 `parseDraft.ts` 的 `headerKindOf` 只有两条规则：

```ts
// 规则一：冒号前的部分必须完全等于某个关键词
// 规则二：去掉标点后，长度不超过 12 个字，且以某个关键词开头
```

规则二有两个问题：

1. **关键词表只有 18 个词**，且以「工作」「项目」「教育」「技能」这类裸词收尾——只要正文以它们开头就命中。
2. **只判「开头」，不判「后面是什么」**。所以「工作负责得很全面」命中「工作」，整行被当成分区表头，**这行内容从此消失**。

没被识别的表头会让整份简历从结构化路径掉进启发式路径，全部内容塞进默认的「工作经历」分区。而启发式只在「一个表头都没认出来」时才给提示——**部分漏认是完全静默的**，用户看到的就是「核心技能那段没了」。

## Goals / Non-Goals

**Goals:**

- 常见的中文、英文、带装饰、中英混排写法都能被识别成分区表头
- 要点不再被误判成表头，内容一条都不丢
- 常见日期写法都能读出起止时间
- 规则本身可预测——能说清一行为什么被认、为什么没被认

**Non-Goals:**

- 不新增第五个分区（自我评价、获奖经历、证书这类没有位置归属，是产品决策）
- 不识别「没有日期的条目头」
- 不改 PDF 提取层（多栏、文字转曲、表格排版三类失败出在提取层）
- 不改启发式路径的行为

## Decisions

### 决策 1：表头匹配从「以关键词开头」改成「关键词后面只能接连接词或非中文」

新规则：把整行归一化后，若它以某个关键词开头，**关键词之后的部分必须满足其一**：

| 剩余部分 | 判定 | 例子 |
| --- | --- | --- |
| 空 | 表头 | 「专业技能」 |
| 不含中文 | 表头 | 「工作经历 Experience」 |
| 以连接词开头 | 复合表头 | 「工作经历与项目经历」 |
| 含中文且不以连接词开头 | **不是表头** | 「工作负责得很全面」 |

这一条同时解决了两个问题：既救回被吃掉的要点，又认得出中英混排的写法。

连接词取「与和、及／/」这几个——复合表头里出现的就是它们。

### 决策 2：关键词表补齐中文变体与英文写法

中文补充（实测漏认的）：

| 分区 | 补充的写法 |
| --- | --- |
| 教育 | 教育与培训 |
| 工作 | 工作背景 |
| 项目 | 代表性项目 |
| 技能 | **核心技能**、IT技能、IT 技能、核心优势、个人能力、专业能力、擅长技能 |

英文（此前一条都不认）：

| 分区 | 写法 |
| --- | --- |
| 教育 | Education、Educational Background、Educational Experience、Academic Background |
| 工作 | Work Experience、Working Experience、Professional Experience、Experience、Career History、Work History、Employment History |
| 项目 | Projects、Project Experience、Selected Projects、Key Projects、Project |
| 技能 | Skills、Technical Skills、Core Skills、Core Competencies、Skill Highlights、Technical Stack、Qualifications |

**关键词表里长词必须排在短词前面**（「工作经历」在「工作」之前）。匹配是按顺序取第一个命中的，顺序错了短词会先命中。

英文关键词按空格归一化后比较（`Work Experience` → `WorkExperience`），两侧同样处理，不会有空格差异问题。

### 决策 3：先剥掉行首的序号与装饰符号

识别表头前先剥掉：

- 行首序号：`一、` `1.` `1、` `(1)` `1)`
- 成对括号与书名号：`【】` `[]` `（）` `《》`
- 装饰符号：`◆` `■` `●` `★` 等

序号里的数字**限制在 1–3 位**——否则「2021.03」这样的日期行会被当成序号剥掉前缀。纯数字 4 位不动。

### 决策 4：日期补三种写法

| 写法 | 处理 |
| --- | --- |
| `2019 - 2022`（只有年份） | 新增「年-年」模式，读出开始年 1 月与结束年 12 月 |
| `Mar 2021 - Jun 2022`（英文月份） | 月份名映射表 |
| `2021～2022`（全角波浪号） | 加进分隔符字符类 |

只有年份的区间取「起始年 1 月 → 结束年 12 月」：读成「2019-01 - 2022-12」，与「2019 年初到 2022 年底」的通常理解一致。

改动只落在 `findDateSpan`，它只被解析器使用，不影响版本生成与其它模块。

### 决策 5：不加第五个分区

「自我评价」「获奖经历」「证书」「语言能力」这类表头，产品里没有对应的分区归属。加一个分区要动领域模型、纸面版式、`sectionFields`、诊断规则与多条规格——那是产品决策，不该由一次识别率改进顺带做掉。

现状行为：这些表头不被识别，内容并入上一个分区，文字不丢。记为已知限制。

### 决策 6：不识别没有日期的条目头

「美团 前端工程师」这种没有时间的行，现在会降级成要点。判断「这行是条目头还是要点」缺少可靠信号——要点也可能很短、也可能没有标点符号。误判的代价是把要点变成空条目，比保持现状更糟。

现状行为：内容不丢，只是没被识别成条目。记为已知限制。

### 决策 7：提取层的失败模式单独记录

诊断中确认有三类失败出在 PDF 提取层而不是解析层，不在本次范围内，但要让用户知道：

| 失败模式 | 现象 | 现状 |
| --- | --- | --- |
| 多栏排版 | 内容顺序交错 | 已知边界，解析结果有偏差但可改 |
| 文字被转曲 | 提不出任何文字 | 落进 `none` 档，引导粘贴 |
| 表格型排版 | 单元格顺序乱 | 解析结果有偏差 |

## Risks / Trade-offs

- **收紧匹配可能漏掉某些真实表头** → 关键词表覆盖不到时，那一行会退回成要点。文字不丢，只是没被当成表头——这个方向的失败比「要点被吃掉」安全得多。
- **英文关键词可能误伤纯英文要点** → 匹配要求整行等于关键词或后面接非中文，「Vue, React, TypeScript」这类不命中。
- **「工作」这类裸词仍是关键词** → 「工作」单独成行时仍会被认成工作经历表头。这是有意的：确实存在只写「工作」两个字的简历。
- **年份区间的结束月取 12 月** → 用户的实际结束月份未知，取年末是最不容易误导的读法。

## Migration Plan

无数据迁移、无存储格式变化。改动只在两个引擎文件与规格。

回滚策略：还原 `parseDraft.ts` 与 `time.ts` 两个文件即可。

## Open Questions

- 「自我评价」「获奖经历」这类分区要不要给它们位置？需要产品决定——加第五个分区，还是明确它们并入某个既有分区。
- 无日期的条目头要不要识别？取决于能否找到可靠信号，以及误判代价能不能接受。
- `sparse` 档的 80 字符阈值仍是按常理推的，没有真实数据。
