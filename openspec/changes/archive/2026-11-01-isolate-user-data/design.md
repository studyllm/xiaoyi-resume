## Context

`account-access` 里写着「数据归属于登录用户」，代码也每次保存都往 `Draft.userId` / `ResumeVersion.userId` 里写用户标识——但存储和读取完全不看它。

```
stores/persistence.ts   draft: 'xiaoyi.draft.v2'       ← 固定 key
                        versions: 'xiaoyi.versions.v2'  ← 固定 key
stores/draft.ts:119     restore() 读完直接用，从不按 userId 过滤
```

一台设备上只有一份简历和一个版本数组。换个名字登录，登录态换人了，数据没换。

约束：

- 原型全在本机，localStorage 是唯一存储，没有服务端能帮忙分人。
- 存储结构变更要走迁移，迁移失败不白屏（`prototype-runtime` 的既有要求）。
- 身份只有名字、没有密码，所以「用户」本质上是「这台设备上的一个名字」。
- 落地页与导入页都已经改成「身份在保存时才问」，身份框是唯一的身份入口。

## Goals / Non-Goals

**Goals:**

- 换一个名字看到的是空白的一份简历，不残留上一个名字的内容。
- 换回原来的名字，那份简历与版本还在。
- 退出登录后落地页回到「导入我的简历」的样子——退出就是真的退出。
- 旧存档不丢：已有的简历与版本按记录的用户标识拆到各自位置。
- 常见的「还是我」不需要重新敲名字。

**Non-Goals:**

- 不做真正的账号体系：没有密码、没有注册、没有服务端校验，名字仍然是随便填的。
- 不清理某个名字下的数据（没有「删除我的数据」这个动作）。
- 不改引擎、纸面版式与界面结构。
- 不动登录态本身的存法（`xiaoyi.session.v1` 不变）。

## Decisions

### 决策一：按用户分槽存，key 带上用户标识

**选择**：简历与版本各自按用户分槽存放，key 形如 `xiaoyi.draft.v3:<userId>` / `xiaoyi.versions.v3:<userId>`。旧的全局 key 降级为只读的迁移源。

**为什么**：localStorage 是扁平的 key-value，没有服务端能替我们分人，唯一能分的方式就是 key 里带用户标识。key 带版本号（v2 → v3）是为了跟「存档结构变更」的既有约定对齐：结构变了就是变了，key 也该变。

**备选与取舍**：

- *一个 key 里存 `{ [userId]: Draft }` 的映射*：localStorage 里只有两个 key，更干净；但值的结构变了，迁移要从「一个 Draft」升级成「一个映射」，而且每次读写都要多一层拆包。分开存更符合 localStorage 的形状，迁移也更局部。
- *在内存里按 userId 过滤*：只解决「不显示」，不解决「不覆盖」——换个名字保存照样把上一个人的简历写掉。归属必须在存储层生效。

### 决策二：只有登录了才算「当前用户」

**选择**：当前用户 = 已登录时的登录用户。没登录时没有当前用户，内存里不载入任何人的简历与版本。上次用过的名字只用来给身份框预填，不参与决定读哪一份数据。

**为什么**：试过另一种做法——没登录时用「上次用过的名字」当当前用户，好处是退出登录后那份简历还在原地、落地页仍显示「打开我的简历」。但那等于「退出登录」只退了登录态、没退身份：用户明明点了退出，落地页还端着他那份简历，像是没退干净。退出就该是真的退出，界面回到「我还没简历」的样子，这是它该有的样子。

「上次用过的名字」保留下来只做一件事：给身份框预填。它让「我上次用过的名字是什么」这个念头不至于把用户挡在门外——数据按名字找回来始终是可能的，只是要他自己记得那个名字。

**备选与取舍**：

- *退出登录时连「上次用过的名字」一起清掉*：身份框变成全空，想找回自己那份就必须重新想起来。但退出登录往往意味着「我要换个人从头来」，预填上一个名字反而会诱导用户覆盖掉原来那份。保留预填、但让它在覆盖前明确问一次，是更稳的组合。
- *数据归属完全不看登录态*：就是最初那版（所有数据存在一处），换名字看到的还是上一个人那份。

### 决策三：身份一变就从对应槽位重新载入

**选择**：在 `main.ts` 里监听「当前用户」的变化，一旦变了就重新执行简历与版本两个 store 的 `restore()`。监听用 `flush: 'sync'`，让切换在登录那一刻就完成。

**为什么**：登录发生在身份框里，而身份框是在运行时才出现的——启动时那一次 `restore()` 覆盖不到它。监听放在 `main.ts` 而不是各个 store 里，是因为「谁负责换数据」是应用层的事：store 只管自己的槽位。

`flush: 'sync'` 是为了顺序：示例数据那条路径是「登录 → 解析 → 保存 → 跳转」一串同步动作，如果换数据是异步的，就会在保存之后才发生，把刚存进去的数据又读成旧的。同步换数据让顺序稳定。

### 决策四：全局槽位按用户标识拆开迁移

**选择**：启动时把旧的 `xiaoyi.draft.v2` 与 `xiaoyi.versions.v2` 里的数据按 `userId` 拆到各自分槽，然后删掉旧的全局 key。

**为什么**：旧存档里简历只有一份、版本可能混着多个人的（版本数组是累积的，每条都带自己的 `userId`）。简历只能归给一个人，版本可以按标识分组各归各家。数据里已经有标识，迁移不需要用户做任何事——他用回原来的名字就能打开自己那份。

**备选与取舍**：迁移只做一次（读到自己那份之后再拆）会让不同用户的数据挤在同一个全局 key 上互相覆盖；启动时统一拆更干净，代价是每个用户的槽位都会被建出来，即使他不再回来——那份数据还在，只是没人去看。

### 决策五：身份框预填上次用过的名字并选中

**选择**：`lastName` 单独存一个 key（`xiaoyi.lastName.v1`），退出登录也不清。身份框打开时把它填进输入框并选中，用户回车即可继续。

**为什么**：名字是随便填的，让人靠记忆找回自己的数据不现实。预填把「还是我」这个绝大多数场景变成一键，同时提示了「这台设备上有一份属于这个名字的简历」。选中是为了让想换名字的用户直接输入覆盖，而不用先删掉。

**备选与取舍**：不预填的话每次都要重新敲，敲错一个字母就进到空应用，而真简历还在 localStorage 里。

### 决策六：示例数据用演示身份，且不占「上次用过的名字」

**选择**：`loadDemoData` 始终以「演示用户」身份进入（示例简历落在演示用户的槽位），但这个身份不写进 `lastName`。

**为什么**：两件事。第一，示例数据不该覆盖用户自己的简历——现在只要点了「用示例简历试一遍」，用户自己那份就被静默替换掉了。第二，演示身份不是用户给自己起的名字，不该顶替它；否则用户试完示例，下次打开身份框看到的 prefilling 是「演示用户」，他自己的名字被挤掉了。

**备选与取舍**：示例数据不落盘、只留在内存里——那版本生成就存不下来（版本要跟着简历修订号对齐），演示就不完整。

## Risks / Trade-offs

- [退出登录后，用户想找回自己那份得再确认一次身份] → 身份框预填了上次用过的名字，回车即可；数据按名字找回来始终可能，只是要自己记得那个名字
- [localStorage 会为每个填过的名字留下一个槽位] → 名字是随手填的，理论上能攒出很多空槽位；每个槽位只是一份简历，量级可忽略，且真数据不会因为多槽位而丢
- [换了名字之后旧名字的简历还在，只是暂时看不见] → 这正是「换回原来的名字还能打开」的实现方式；界面上不去提醒，避免暴露「这台设备上还有别人的数据」这种信息
- [`lastName` 是一个新的存储 key，与 session 分开] → 退出登录时保留它，是为了让「还是我」这条路径成立；它只存一个名字，不含任何简历内容
- [身份切换时重新载入数据，如果用户在未保存状态下切换身份，改动会丢] → 身份框只在保存时出现，而保存前界面会先确认覆盖；顶栏的「退出登录」在有未保存修改时会被路由守卫拦住（既有行为）
- [分槽后 `hasDraft` 的含义变了] → 它现在表示「当前用户有简历」，落地页的「打开我的简历」与导入页的覆盖确认都跟着这个语义走

## Migration Plan

存档结构变更，按 `prototype-runtime` 的既有约定处理：

1. 启动时读旧的全局简历与版本，按 `userId` 拆到各自分槽，删掉旧的全局 key。
2. 旧的 `v1` / `v0` 存档仍走既有的版本链迁移，迁到全局 key 后再按上面的规则拆开。
3. 拆分失败不白屏：丢弃那一片数据并提示一次（既有机制）。

回滚方式：`git revert` 本变更涉及的提交。回滚后旧的分槽数据还在 localStorage 里（key 带 v3），而旧代码读的是 v2 全局 key——那份数据等于暂时看不见，但没有丢。

## Open Questions

- 要不要加一个「删除我这份简历」的动作？现在没有，用户填错名字留下的那份只能自己去清浏览器数据。这属于产品功能，不在本轮。
- 多名字之间的数据量会不会大到需要清理策略？原型阶段不会。
