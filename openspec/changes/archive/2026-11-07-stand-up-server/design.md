## Context

P3 的服务端从零开始。契约已冻结（21 个端点、19 个错误码），共享包已抽好，但服务端还不存在。

这一轮只做两件事：把架子立起来，并证明共享包的保证是真的。

## Goals / Non-Goals

**Goals:**

- `server/` 能跑起来，引用的是共享包里的同一份源码。
- 有一个可执行的断言证明「同一输入同一输出」。
- 端点实现与契约一致（路径、方法、请求体、响应体、状态码）。
- 两端都进 CI。

**Non-Goals:**

- 不做鉴权、存储、迁移（T3.2、T3.3）。
- 不实现契约的其余 19 个端点。
- 不落错误码表（T3.2）。

## Decisions

### D1. Fastify + `tsx`

Fastify 是计划里定下的框架。`tsx` 用来跑 TypeScript——Node 的类型剥离不认无扩展名的相对导入（`import './diagnose'`），而共享包内部正是这么写的。

**理由**：改所有相对导入加 `.ts` 后缀是几百处churn，而且 `allowImportingTsExtensions` 虽然允许、但读起来别扭。`tsx` 一个依赖解决。

### D2. `parse` 端点跑共享引擎，不重写

服务端调 `@xiaoyi/shared/engines/parseDraft`，**不复制逻辑**。

**理由**：这就是 F9 的内容。服务端自己实现一份解析，两端迟早漂移。

### D3. F9 的断言写成用例，不是注释

服务端用例断言「HTTP 端点的输出与直接调用共享引擎逐字一致」。

**理由**：注释会过期，断言不会。有人复制引擎、改引擎、换实现路径，这条都会红。

### D4. 时间由服务端注入

`EngineContext.now` 用服务端的 `new Date().toISOString()`，客户端不传时间戳（契约原则 5）。

**注意**：解析本身不用时间（`parseDraft` 的 ctx 参数是 `_ctx`），所以断言里直接调用与经 HTTP 调用拿到的时间不同——**输出仍然逐字相同**，因为时间不进解析结果。这正是断言能成立的原因。

### D5. 错误码先写字面量

路由里暂时写 `RESUME_EMPTY` / `PARSE_FAILED`。

**理由**：契约 §5 的错误码表要一次性给全（19 个码 + 每个码对应的前端状态），那是 T3.2 的活——那时状态表里的十条新状态也一起补上。现在写两个字面量，比造半张表干净。

### D6. `parse` 是公开端点

不需要登录。

**理由**：`account-access` 现有规格明写「导入页可以匿名使用」——未登录用户可以粘贴、解析、在纸上修改。契约照它定。

## Risks / Trade-offs

**[服务端 tsconfig 要 `skipLibCheck`]** → vitest 的类型声明引用了 `Worker` 等浏览器全局，服务端不需要它们。跳过 `.d.ts` 检查，别让第三方声明文件污染服务端类型。

**[契约实现了 2/21]** → 契约与实现的差距要看得见。契约文档里标出哪些端点已落地。

**[服务端没有存储与鉴权，端点只能公开]** → 本轮就是骨架。鉴权与存储落地后，`parse` 仍然保持公开（契约如此），但其它端点会要求会话。

## Migration Plan

无数据迁移。CI 第一次跑会重装依赖（lockfile 变了）。

## Open Questions

- `Idempotency-Key` 的存储：契约 §6 要求 24 小时的记忆，服务端落地时用 Postgres 一张表还是别的——契约 §12 第 2 条待定。
