## Context

真实规模的简历（77 条要点）上，模型调用要 5 分钟，输出还会被截断。日志里的失败原因不可行动。

## Goals / Non-Goals

**Goals:**

- 失败原因直接指向该调哪个配置、调到多少。

**Non-Goals:**

- 不改降级链。
- 不改重试判定。
- 不在这次里解决「模型改写整版简历要 5 分钟」本身——那是模型选型与分段生成的事。

## Decisions

### D1. 超时翻译成「调大 LLM_TIMEOUT_MS」

Node 给的「The operation was aborted due to timeout」没人知道该改什么 ✓ —— 实际上要改的是超时上限 ✓，而且当前上限是多少也要写出来 ✓（不然用户不知道该调到几 ✓）。

**保留原来的 name**：重试判定靠它（超时不重试 ✓）——翻译时把 name 与 cause 都带上 ✓。

### D2. 截断单独认出来

响应里的 `finish_reason === 'length'` 表示输出撞了上限 ✓ —— 这跟「模型压根没写」是两回事 ✓。前者重试没用 ✓，要调大的是输出上限 ✓。

推理模型尤其容易撞上：推理内容先吃额度 ✓，正文一个字没轮到 ✓。

### D3. 把实测写进 `.env.example`

「按一整版简历定」还不够 ✓ —— 要给出规模与时长的对应关系 ✓（77 条要点 → 5 分钟 ✓），用户才知道该给多少 ✓。

## 验证方式

- `server/src/llm/client.spec.ts`：超时的消息指向 `LLM_TIMEOUT_MS` ✓；截断的消息指向 `LLM_MAX_TOKENS` ✓
- 仓库根 `npm run verify` 全绿 ✓
