## Context

分区表头没被认出来时，那一段内容被并进上一个分区，界面上完全静默——用户只看到「少了一段」。识别率改进补齐了已知写法，但真实简历的写法没有穷举：「自我评价」「获奖经历」「证书」这类**产品里本来就没有位置归属**的分区，永远不会被识别成表头。

所以需要一条兜底提示。难点在于**判据的精度**：误报几次，用户就会开始忽略这条提示，它就废了。

## Goals / Non-Goals

**Goals:**

- 没被认出来的疑似表头行列出来，用户能一眼看到是哪几行
- 误报率压到零——宁可漏报
- 不影响既有的解析行为与界面

**Non-Goals:**

- 不把没认出来的内容自动归到某个分区（那是猜测）
- 不用英文规则扩大覆盖（实测误报太高）
- 不改识别规则本身

## Decisions

### 决策 1：检测放在解析器里，不放在界面层

只有解析器知道哪一行被认成了表头。放到界面层就要把「哪些行被认过」复制一份出去，两处判断迟早会不一致。

所以 `ParseResult` 增加 `suspectedHeaders: string[]`，由 `parseDraft` 算好返回。

### 决策 2：判据是「未被识别 + 不含日期 + 不以项目符号开头 + 短 + 后面还有内容」

逐条说为什么：

| 条件 | 排除什么 |
| --- | --- |
| 未被识别为表头 | 已认出来的表头不重复报 |
| 不含日期 | 含日期的行是条目头，不是表头 |
| 不以项目符号开头 | 带项目符号的行是要点 |
| 归一化后 ≤ 4 个字 | 排除普通要点（见决策 3） |
| 后面还有内容行 | 最后一行通常是落单的要点 |

### 决策 3：阈值定在 4，用量化定而不是凭感觉

用 16 条「应当被提示」的真实表头写法与 13 条「不该被提示」的普通要点做扫描：

| 阈值 | 命中 | 误报 |
| --- | --- | --- |
| **≤ 4** | 9/16 | **0/13** |
| ≤ 5 | 9/16 | 2/13（抗压能力强、学习能力强） |
| ≤ 6 | 10/16 | 4/13 |
| ≤ 8 | 11/16 | 7/13 |

≤ 4 是唯一误报为零的一档。中文分区表头几乎都是 4 个字（教育背景、工作经历、项目经历、专业技能、自我评价、获奖经历），2 个字的（证书）也在内，所以这个阈值覆盖了主要形态。

再放宽就会开始误报「抗压能力强」「有良好的沟通能力」这类普通要点。

### 决策 4：不采用英文规则

英文候选的判据是「全是英文单词、每词首字母大写、词数 ≤ 2、无中文」。实测命中 10/10，但误报 5/7——`Vue React`、`TypeScript`、`React`、`Figma`、`Sketch` 这类单行要点都会被误伤。

而且常见英文表头（Skills / Work Experience / Education / Projects / Core Skills）已经在识别率改进里被认成表头了，根本不会走到这条提示。收益小、代价大，不做。

### 决策 5：启发式路径下不报这份清单

一个表头都没认出来时，解析器已经给出「未识别到分区表头，已按启发式推断分区」的警告。那时整份简历都在猜测范围内，再列一份候选清单只会重复与噪音。

### 决策 6：提示要列出具体是哪几行

只给一个数字（「有 3 处没认出来」）用户没法处理——他不知道是哪三处。提示里带上原文行，用户能立刻在纸上找到并改掉。

## Risks / Trade-offs

- **漏报**（阈值 4 之外的表头不会被提示）→ 接受。这条提示是兜底，不是主要识别手段；主要识别手段是关键词表本身。
- **列出的行仍然在纸上**（它们被当成要点并入了上一个分区）→ 这是事实，用户看到提示就知道那几行「没归位」，可以在纸上删掉或改写。提示文案说的是「没认出来」，不是「丢了」。
- **英文表头基本不会触发** → 接受，常见英文表头已被识别。

## Migration Plan

无数据迁移。`ParseResult` 是新增字段，既有消费方不受影响。

回滚策略：还原 `types.ts`、`parseDraft.ts`、`ImportView.vue` 三个文件。
