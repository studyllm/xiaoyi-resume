## Context

v0.1 已把产品功能面全部铺开，但「改完就绿」这件事目前不成立。实测（2026-11-02，本机 8 核 / Node 22 / Vitest 2.1.9）：

| 跑法 | 结果 | 总时长 | transform | collect | tests |
| --- | --- | --- | --- | --- | --- |
| 默认（全并行） | 470/470 通过 | 30.46s | 15.09s | 121.49s | 46.01s |
| 随机顺序（shuffle seed=42） | 470/470 通过 | 76.49s | 38.29s | 266.29s | 88.48s |
| 限并发 `maxThreads=4` | **2 个用例失败** | 81.33s | 36.42s | 312.36s | 145.42s |
| 限并发 `maxThreads=4`（机器空闲时重跑） | 470/470 通过 | — | — | — | — |
| 限并发 + `testTimeout=30000` | 470/470 通过 | 85.52s | 46.43s | 335.33s | 130.45s |
| 全串行 `--no-file-parallelism` | 470/470 通过 | 128.83s | 12.41s | 48.07s | 38.00s |

三个事实：

1. **失败的用例本身不慢**。单用例最长 2.2s（`DraftView` 编辑模式），多数在 300–1200ms。默认超时 5s 在机器空闲时够用，在负载升高时不够。
2. **耗时主体是 collect 而非 test**。`collect`（含模块加载与 jsdom 环境创建）是 48–335s 的主要来源，`tests` 只占 38–145s。开销集中来自 `server.deps.inline: ['element-plus']`——每个 worker 都要把 Element Plus 的样式与组件重新 transform 一遍。
3. **降低并发反而更慢**。`maxThreads=4` 比默认并行更慢（81s vs 30s），且在有其它负载时出现失败。collect 成本随并发上升，说明瓶颈在 transform 与环境创建的共享资源争抢，而不是单纯的 CPU 数量。

**最关键的一条**：限并发的同一份配置在机器空闲时重跑即 470/470 全绿。这排除了「用例间存在真实顺序依赖」的可能——**失败是负载相关的超时误判，不是逻辑缺陷**。失败时的症状与初次勘察到的完全一致：`Test timed out in 5000ms`。

**因此问题的准确定性不是「测试写得慢」，而是「判定结论对机器负载敏感」**——同一份代码在不同负载下可能给出不同结论，于是「全绿」不构成证据，`flows.spec.ts` 里的 30 条产品不变量守卫随之失去约束力。

约束：

- 托管平台未定，仓库当前只有本地 `main` 分支、无远程。
- 不引入新的第三方依赖。
- 本变更不改变任何用户可见行为。
- `CLAUDE.md` §8 要求区分「静态扫得到」与「浏览器验」；本变更全部属前者。

## Goals / Non-Goals

**Goals:**

- 同一份代码在任何机器负载下重复执行，得到相同的通过/失败结论。
- 提供一个与托管平台无关的门禁入口，本地与 CI 调用同一入口。
- CI 按双跑法执行门禁：全量并行一次 + 随机顺序分片一次，两者都通过才算通过。
- 消除仓库里的误生成产物，环境变量与本机配置不入库。
- 生效规格写明各自解决什么问题，不再留占位符。
- 记录一份测试耗时基线，供后续阶段做性能对照。

**Non-Goals:**

- 不引入 Vitest workspace 多项目分池（实测降并发更慢，见决策 3）。
- 不优化测试本身的速度（缩短 collect 成本），只保证结论稳定。
- 不配置远程仓库、不推送代码——创建远程仓库属于影响外部状态的动作，需用户单独确认。
- 不改任何界面、文案或数据行为。
- 不为「让测试更快」而重构测试代码。

## Decisions

### 决策 1：提高超时阈值，而不是重写测试

把 `testTimeout` 与 `hookTimeout` 从默认 5000ms 提到 30000ms。

- **依据**：单用例最长 2.2s，30s 是 13 倍余量；即使机器负载把耗时放大 10 倍仍不误判。
- **替代方案**：拆分慢测试或 mock 掉 Element Plus 的样式加载——能真正压低 collect 成本，但改动面大、触及组件测试的渲染前提，属于优化而非本变更的目标。
- **代价**：真实卡死的用例会晚 25s 才被发现。这是可接受的：门禁里另有打乱顺序跑法作为二次探针。

### 决策 2：CI 双跑法用固定随机种子

门禁跑两次测试：全量并行一次；打乱顺序一次，**种子固定**（如 `--sequence.shuffle --sequence.seed=42`）。

- **依据**：固定种子让失败可复现——CI 报红后，用同一条命令在本地能重现同一批用例。随机种子做不到这点。
- **替代方案**：CI 用随机种子以覆盖更多顺序。放弃：无法复现，排查成本高。
- **本地探针**：本地想主动找顺序依赖时，用不带 `--sequence.seed` 的随机种子多跑几次。这是给人用的工具，与 CI 的固定种子并存。

### 决策 3：不限制并发，也不改用串行作为常规跑法

保持 Vitest 默认并发度。

- **依据**：实测 `maxThreads=4` 更慢且在有其它负载时出现失败；全串行虽然最稳（collect 48s）但总时长 128.83s，是默认跑法的 4 倍。CI runner 通常是 2 核，并行度天然低，collect 争抢比本地开发机轻。
- **保留**：全串行作为**诊断手段**写进文档——当怀疑存在用例间隐式依赖时，用它确认失败是否与并发有关。
- **已排除的隐患**：限并发下的失败经重跑证明是负载相关的超时误判，不存在真实的顺序依赖。因此不需要为「让 CI 跑法更贴近真实顺序」额外设计第三种跑法。

### 决策 4：门禁入口平台无关，CI 配置只是薄壳

`frontend/scripts/verify.mjs` 是「改动是否可交付」的唯一判定入口，按顺序执行：类型检查 → 全量并行测试 → 打乱顺序测试 → 构建。

`.github/workflows/ci.yml` 只负责「在什么时机、由什么事件、调起 verify」，不重复定义检查步骤。托管平台未定时这是默认实现；换平台时只需按 `docs/ci/README.md` 的说明改写「怎么调起 verify」这一层。

- **依据**：托管平台未定，但门禁的**内容**是确定的。把内容收敛到一处，换平台只改调用方式。
- **替代方案**：直接写死某个平台的 YAML——平台一变就要重写，且无法在没有远程时验证。

### 决策 5：仓库卫生守卫单独成文件，不并入 flows.spec.ts

新建 `frontend/src/repo-hygiene.spec.ts`，放三条检查：仓库内不得有嵌套的源码目录、环境变量文件不得入库、生效规格不得残留 Purpose 占位符。

`flows.spec.ts` 保持只测**产品不变量**（界面用词、禁用词、按钮语义、数字一致性等）。

- **依据**：两类断言的性质不同。flows.spec.ts 扫的是「产品不能变成什么样」，仓库卫生扫的是「工程不能变成什么样」。混在一起会让 flows.spec.ts 承担它不该承担的东西。
- **连带**：`CLAUDE.md` §8 的守卫清单要补一行，说明存在第二个守卫文件。

### 决策 6：Purpose 补写直接改生效规格，机制上另加规则防复发

OpenSpec 的归档只合并 Requirement，不搬运 `## Purpose`。因此 Purpose 补写**无法**通过 delta spec 走归档流程完成，只能直接编辑 `openspec/specs/*/spec.md`。

这不是绕过规范流程——`openspec/specs/` 是「当前生效的行为基准」，而 Purpose 描述的是既有能力域的定位，不是新增行为，不存在需要 delta 的需求变更。

为防止再产生占位符，在 `openspec/config.yaml` 加一条规则：归档变更时若产出新能力域，必须回填其 Purpose 段，不得保留占位符。

**本变更自身也受这条约束**：它会产出新能力域 `test-and-ci`，归档后 `openspec/specs/test-and-ci/spec.md` 的 Purpose 同样是占位符。实施步骤里必须包含「归档后回填 test-and-ci 的 Purpose」这一步。

### 决策 7：引擎模式开关本轮只定口径，不接线

新增 `frontend/.env.example`（只含键名与说明）与 `docs/adr/0001-engine-mode-switch.md`（写明取值域、未知取值回落本地规则引擎且不白屏、本地与远端的行为差异）。

`VITE_ENGINE_MODE` 的实际接线在服务端化阶段做。

- **依据**：`stores/engines.ts` 已有注入点，但 `ENGINES` 只有本地实现、`VITE_ENGINE_MODE` 没有 `.env` 落地，永远走本地分支。现在接线等于做一个没有第二个实现的开关。口径先定死，后续接远端实现时不再重新讨论。

## Risks / Trade-offs

- **提高超时可能掩盖真实卡死** → 用双跑法中的打乱顺序跑法作为二次探针；并在 ADR 里写明「单用例超过 20s 应视为待优化项」而非依赖超时兜底。
- **提高超时后仍可能漏掉极端负载下的误判** → 30s 是单用例实测最长耗时（2.2s）的 13 倍余量；门禁另设打乱顺序跑法，两次都超时的用例几乎必然是真实问题。
- **Purpose 直接改生效规格，可能与归档流程产生困惑** → 在 `openspec/config.yaml` 的规则里写清楚 Purpose 的归属，并在 `docs/decision-log.md` 留一条决策记录。
- **CI 配置针对 GitHub 写，托管平台尚未确定** → `verify.mjs` 是平台无关的真源，换平台只改调用层；`docs/ci/README.md` 给出等价做法。
- **CI 配置在无远程时不会真实运行** → 本地 `npm run verify` 提供等价验证；任务清单里把「推送触发 CI」标为需用户确认后执行。
- **测试耗时基线会随机器与依赖版本漂移** → 基线记录在文档里并标注测量条件，不作为硬门禁；后续阶段用它做对照时需重新测量。

## Migration Plan

无数据迁移、无接口变更。

回滚策略：本变更只增删工程文件与配置，不触碰 `src/` 下的业务逻辑（除新增守卫文件与 `vite.config.ts` 的超时配置）。回滚 = 还原提交。
