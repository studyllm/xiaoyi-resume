## Context

诊断页现在是意见清单。`DiagnosisIssue` 已经带着全部需要的信息：

```ts
interface DiagnosisIssue {
  id, ruleId, category, severity
  sectionId, sectionKind, sectionTitle
  itemId, itemLabel
  bulletId
  quote        // 整条要点
  highlight    // 问题出在哪几个词；时间线类问题为空
  problem, suggestion
}
```

但定位动作只带走了 `sectionKind + bulletId`：

```ts
uiStore.focus(issue.sectionKind, issue.bulletId || null)
```

于是 `quote` / `highlight` / `problem` / `suggestion` / `itemLabel` / `sectionTitle` 六条信息全部留在原地，编辑页只剩一条橙色高亮。

两处更细的断裂：

- **问题片段丢失**：诊断页高亮 `highlight`（问题出在哪几个词），编辑页高亮整条要点。到了编辑页不知道该盯哪几个字。
- **时间线类问题无处可挂**：缺开始时间、时间区间重叠这类问题针对的是**条目**而非某句话，它们的 `highlight` 是空的。過去只能整条要点一起高亮，无法表达"问题在日期上"。

## Goals / Non-Goals

**Goals:**

- 诊断页呈现为「简历 + 批注栏」，意见挂在它批评的位置旁边
- 定位不再是跨页跳转，改为同屏高亮，且能双向联动
- 编辑页在要点旁展示对应批注，改与建议同屏
- 每条意见有明确的三级锚点
- 批注可标记已处理；诊断过期时能看出哪几条已被改过

**Non-Goals:**

- 不做批注的回复与讨论（Word 的评论区）
- 不改任何诊断规则、严重度分级与排序键
- 不改建议文案与问题文案
- 诊断页的简历是只读的，修改仍在编辑页进行
- 不给批注加独立的持久化存储（沿用「忽略此条」的内存态做法）

## Decisions

### D1 诊断页改为「简历 + 批注栏」

```
┌──────────────────────────────────┬──────────────────────┐
│ 张三                             │ 批注 6   严重度▾ 类别▾  │
│ 前端工程师 · 6 年经验             │ ┌──────────────────┐ │
│ 138-… · zhangsan@…               │ │▸ 美团·前端工程师 │ │
│                                  │ │ 缺可衡量的结果    │ │
│ 工作经历 ──────────────── │ │ 建议：…           │ │
│ 美团  前端工程师   2021.03-至今   │ │ [去修改][已处理]  │ │
│ · 负责公司营销页面的前端开发 ▂▂▂   │ └──────────────────┘ │
│ · 主导活动平台前端架构升级…       │                      │
└──────────────────────────────────┴──────────────────────┘
```

关键在于**用户感知到的对象变了**：从"系统挑出了 6 个毛病"变成"我的简历上被标了 6 处"。后者才是简历诊断该有的形态。

「定位到句子」这个动作因此被**消解**了——批注本来就贴着那句话，不需要跳过去找。它退化成一个高亮联动。

左侧简历复用 `ResumePreview` 的 A4 排版（见 D2）。纸面本身就是「我的简历」，比紧凑列表更贴合这个隐喻，也让用户看清批注落在整份简历的哪个位置。

### D2 把 ResumePreview 泛化成吃「分区 + 抬头」的公共结构

`DraftSection`/`DraftItem` 与 `VersionSection`/`VersionItem` **结构同构**（分区有 kind/title/items，条目有 org/title/start/end/present/bullets，要点是 {id,text}）。所以同一个排版组件能同时渲染底稿与定向版本：

```
interface PreviewSection {
  kind: SectionKind
  title: string
  items: {
    id: string
    org?, title?, start?, end?, present?
    bullets: { id: string; text: string }[]
  }[]
}
```

`DraftSection` 多了个 `id` 字段，结构化类型允许多余属性，两个都能直接传进去。

组件同时接受一组高亮锚点，用于渲染批注锚定的文字：

```
highlight?: {
  bulletId?: string     // 高亮该要点中的片段
  fragment?: string     // 要点内被高亮的片段
  itemId?: string       // 高亮该条目的标题行
  sectionId?: string    // 高亮该分区的标题
}
```

要点内片段级高亮在模板里用文本切分实现（按 fragment 把 bullet.text 切成 before / mark / after），不需要 overlay 技巧。

### D3 锚点分三级，且可由现有字段推导

```
分区标题  ←  分区为空
条目标题  ←  缺开始时间 / 结束早于开始 / 时间区间重叠 / 顺序不对 / 缺公司名 / 缺职位 / 没有要点
要点正文  ←  只有职责没有结果 / 表述空泛
```

级别**不需要新字段**，从现有的 id 就能推出来：

```ts
function anchorLevel(issue: DiagnosisIssue): 'section' | 'item' | 'bullet' {
  if (issue.bulletId) return 'bullet'
  if (issue.itemId) return 'item'
  return 'section'
}
```

锚定的文字：

| 级别 | 锚定文字 | 来源 |
|---|---|---|
| bullet | `highlight` 或 `quote` | 已有 |
| item | `itemLabel`（公司 · 职位） | 已有 |
| section | `sectionTitle` | 已有 |

不新增数据通道，只新增一个推导函数。

### D4 双向联动

```
点批注    → 左侧锚定文字高亮 + 滚动到可见位置
点左侧文字 → 右侧对应批注高亮 + 滚动到可见位置
```

双向是必须的：单向的话，用户在批注栏点一条还得自己在左边找位置；反之在左边读到一句话想知道为什么被标，也得在右边找。

实现上，`uiStore` 持有 `activeCommentId`，两个视图都监听它。左侧"点文字"用 `@mouseup` 取当前选区文本，与各批注的锚定文字比对。

### D5 编辑页同屏展示批注

这是"割裂彻底消失"与"只是挪了个位置"的分界。用户从批注栏跳到编辑页时，屏幕上如果只有那句话和光标，建议等于又丢了——只是这次他刚看过所以记得住。**靠人脑记住就是割裂。**

编辑页的挂载位置按锚点级别决定：

```
要点下方      ← 要点级批注
条目标题旁   ← 条目级批注
分区标题旁   ← 分区级批注
```

成本可控：诊断结果本来就在 `draftStore.diagnosis` 里，编辑页按 `bulletId` / `itemId` / `sectionId` 匹配出该挂哪几条，不需要新通道。

### D6 已处理与已改是两个不同的状态

```
已处理   用户点了「已处理」        内存态，记 ruleId+bulletId
已改     底稿里的正文被改过        诊断后对比得出
```

「已改」的判定：诊断意见带 `quote`，拿它跟底稿当前正文比，不同就是被改过。

为什么两个状态都要：诊断是快照，底稿一改就过期，用户必须重新诊断。但重新诊断后，如果他的改法没解决问题，同一条意见会再次出现——如果界面毫无变化，用户会以为系统没生效。标出"你改过它"能解释这一点。

### D7 我替用户拍板的三个问题

以下三项在讨论中没有明确结论，我按如下判断推进，写在这里便于推翻：

| 问题 | 结论 | 理由 |
|---|---|---|
| 批注只挂诊断页，还是编辑页也挂 | **两边都挂** | 用户的原始诉求是"改的时候得看见建议"。只挂诊断页的话，割裂只是从"跳过去看不到"变成"跳过去要靠脑子记住" |
| 左侧简历用 A4 排版还是紧凑列表 | **A4 排版** | 复用已有的 `ResumePreview`，零新增排版代码；而且"这就是我的简历"才是对的隐喻，用户能看清批注落在整份简历的哪 |
| 改完之后批注怎么消失 | **已处理 + 已改并存**，诊断仍按快照失效 | 诊断过期是全局的，不能因为改了一条就假装其余意见还成立；「已处理」是用户的显式动作，「已改」是系统推导出来的，两者信息量不同 |

### D8 批注栏按简历位置排列，严重度用颜色区分

排序从「严重度优先」改成「顺着简历读下来」——这才是 Word 审阅的心智：批注挂在哪，就按那个顺序出现。严重度不再靠排序表达，而是靠**颜色**。

```
排序键    (分区序号, 条目序号, 要点序号)
颜色      高 → 红    中 → 橙    低 → 灰蓝
```

简历正文里锚定文字的高亮，与批注卡片用**同一种严重度颜色**，这样一眼能看出"这处标红 = 有个高严重度的问题"。

代价：打开批注栏时不再第一眼看到最严重的问题。补偿是批注栏顶部保留按严重度筛选，以及颜色本身的视觉权重。

排序需要「意见在简历中的位置」，而 `DiagnosisIssue` 只带 id。所以加一个纯函数 `orderByDocument(draft, issues)`：拿 id 去底稿里查分区序号、条目序号、要点序号，排序。引擎现有的严重度排序键**不动**（它仍用于「按严重度筛选」和编辑页的挂载顺序）。

### D9 批注栏可折叠

折叠后简历占据整屏，批注只留一个图标条与未处理数。批注为零时自动折叠。

折叠状态放在 `uiStore`（内存态），不持久化——与「忽略此条」「已处理」一致。

### D10 「去修改」跳过去后，批注展开成焦点

编辑页里每个有批注的要点下面挂一条**收起的**提示条：

```
● │ 负责公司营销页面的前端开发，配合设计团队完成活动上线
  │ ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓
  │ ⚠ 1 条批注 · 缺少可衡量的结果                        ▾   ← 收起时一行
  │   （展开后）问题是什么：…
  │            建议怎么改：…
```

收起时只有一行（严重度颜色 + 条数 + 摘要），避免满屏提示条。展开才看到完整建议。

「去修改」跳到编辑页时，**目标要点旁的批注自动展开并获得焦点**——这是「去修改」这个动作的完整含义：不只是把人送到那句话旁边，还要把对应的建议摆在他眼前。否则他到了编辑页看到的仍是一条橙条，割裂照旧。

## Risks / Trade-offs

**[左侧 A4 纸 + 右侧批注栏在笔记本上挤]** → A4 794px + 批注栏 320px + 侧栏 200px ≈ 1314px。窄于 1280px 时批注栏折叠为抽屉，或简历改为单栏堆叠。用 CSS 断点处理，不做缩放适配（与 A4 预览整页居中的既定决策一致）

**[批注栏与左侧简历的滚动不同步，读起来跳]** → 选中时两侧各自滚动到目标；不追求滚动位置联动（Word 也不追求），只保证"选中即可见"

**[要点内片段级高亮在文本被改过之后失效]** → 批注锚定的文字基于诊断时的原文。用户改过要点后，锚定文字可能已经不在正文里，此时高亮降级为整条要点高亮，并在批注上标「已改」

**[锚点级别靠 id 推导，遇到 id 缺失时判错]** → 三级都有明确的回退顺序（bullet → item → section），且 item 级批注的 `itemId` 一定存在；补一个引擎级单测覆盖三种级别

**[已处理状态是内存态，刷新就丢]** → 与「忽略此条」一致，是原型阶段的刻意取舍。刷新后批注全部回到未处理，用户重新诊断即可

**[诊断页从卡片列表变成简历视图，原有的「三个焦点区」分类浏览能力消失]** → 批注栏顶部提供按类别与严重度筛选，覆盖原来的浏览需求；分类标签仍显示在每条批注上

## Migration Plan

1. 先改规格（`resume-comment-anchoring` 新增、`draft-diagnosis` 两条需求改写），确立锚点与联动契约
2. 引擎侧：加锚点推导函数，输出级别与锚定文字（诊断规则本身不动）
3. 组件侧：`ResumePreview` 泛化 + 支持高亮；新增批注卡片与批注栏
4. 视图侧：诊断页改为左右布局；编辑页挂载批注
5. 状态侧：`uiStore` 承载高亮与已处理；`draftStore` 承载已改判定
6. 验证：单测（锚点三级、双向联动、已处理计数）+ 浏览器走查（三类意见分别挂在分区、条目、要点上）

**回滚**：改动集中在新增组件与两个视图的布局，规格与引擎的诊断规则未变，回滚即还原文件。

## Open Questions

本设计无遗留开放问题。批注栏排序、严重度配色、批注栏折叠与「去修改」后的焦点展开四项已定案，记录于此以免后续被重新提起：

| 问题 | 结论 | 落在 |
|---|---|---|
| 批注栏默认排序 | 按简历位置顺着读，严重度改用颜色区分 | D8 |
| 批注栏是否可折叠 | 可折叠，批注为零时自动折叠 | D9 |
| 「去修改」跳转后是否展开批注 | 展开并获得焦点 | D10 |
