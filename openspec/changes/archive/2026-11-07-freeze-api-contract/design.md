## Context

P3 要引入服务端。前端是 Vue SPA，服务端要新建。契约是这个接缝的定义。

之前 P0–P2 一直是纯前端，没有前后端接缝，所以「契约」这件事在 P3 才第一次出现。

## Goals / Non-Goals

**Goals:**

- 把接缝定死，让服务端与前端可以并行写。
- 把「谁说了算」的三件事定死：结构化数据谁产出、用户文案谁产出、文件要不要上传。
- 给出错误码与前端状态表的一一对应关系，让契约可被测试守住。

**Non-Goals:**

- 不写 TypeBox schema（随服务端落地）。
- 不实现任何端点。
- 不做接口 mock。

## Decisions

### D1. 错误码由服务端给，文案由前端映射

后端返回 `{ error: { code, message } }`，前端按 `code` 从 `states.ts` 取文案；前端没登记的 `code` 退回 `INTERNAL_ERROR` 的文案。

**理由**：文案只有一处来源（P2 建立的 `states.ts`）。后端也写文案的话，同一件事会有两套说法——那正是 P2 刚消灭掉的问题。

`message` 仍然返回，但只作为兜底与日志，**前端不直接展示它**。

### D2. 客户端提交原始文本，服务端产出结构化数据

`POST /api/v1/draft/parse` 收文本、返回结构化底稿、**不落库**；`PUT /api/v1/draft` 收结构化数据、**服务端重跑校验**后落库。

**理由**：ADR-0003 的「服务端是权威」。客户端提交的结构化数据不可信——它可能是在本地被改过的，也可能来自旧版本。

**parse 不落库**是为了不留「取消导入」的残留：服务端不存 pending 状态，客户端持有服务端刚产出的东西加上用户的编辑，保存时才提交并被校验。

### D3. 没有上传端点

PDF 在浏览器里解析，只发提取出的文本。

**理由**：P1 对用户的承诺（`pdf-intake` 规格：文件在浏览器里解析，不会上传到任何服务器）。也是 `privacy-conclusions.md` 的「副本」边界——PDF 不算副本。

服务端因此没有文件相关的错误码。

### D4. 页码分页，不用游标

一个账号的版本数不大，用户的心智是「第 2 页」。游标适合无限滚动的大数据量，这里用不上它的好处，却要付「不能跳页、拿不到总数」的代价。

### D5. 幂等键只给「不幂等且有副作用」的 POST

生成版本、注册、登录、存量迁移要 `Idempotency-Key`（24 小时）；发重置邮件**不要**——用户要能重发，只靠限流。

**理由**：幂等键解决「手快点两下」与「超时后重试」。重置邮件要能重发，限流解决它。

### D6. 错误码表是两侧的唯一来源，服务端由它生成

不是两处各写一份。契约测试断言「服务端生成的错误码集合」与「前端 `states.ts` 里带 `code` 的状态集合」一一对应。

**理由**：验收项 A3.1 要的是「契约文件与实现的字段/错误码一致性由测试断言」。两处各写就断言不了。

### D7. `useLlm` 是一次性开关，放在生成选项里

`options.useLlm: false` 时全程走规则引擎，简历正文不发给任何第三方。

**理由**：`privacy-conclusions.md` §5.1 的结论。生成选项卡已经有开关了，加第三个几乎零成本。

## Risks / Trade-offs

**[匿名可解析 = 服务端白干活]** → 限流。解析是纯计算，没有存储成本。

**[客户端提交的简历服务端要重验]** → 结构检查与不变量校验都在共享包里，同一份代码跑两遍。代价小，收益是服务端不信任客户端。

**[`message` 存在但前端不展示]** → 有被误用的风险。守卫可以扫「前端不直接展示 `error.message`」——但那是实现细节，交给契约测试与代码审查。

**[`Idempotency-Key` 要服务端存]** → Postgres 一张表，24 小时后清理。Redis 不在 v1.0 的技术栈里。
