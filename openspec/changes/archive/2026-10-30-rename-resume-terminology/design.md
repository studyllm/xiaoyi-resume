## Context

原型已完成并归档（`openspec/changes/archive/2026-10-29-add-resume-frontend-prototype/`），界面通篇用「底稿」与「版本」这两个词。

「底稿」来自出版与写作行业，在求职场景里不自然；更要命的是它暗示的权威方向与产品相反——用户读到「底稿」会以为那是一份还要再改的草稿，而它其实是唯一且永久的事实源，用户永远不需要再写一份「正式的」。「版本」则缺少方向性：用户分不清自己维护的那一份和投给每家公司的那一版。

改动横跨三层，且它们的用词必须一致，否则下一位实现者会把「底稿」重新写回界面上：

```
   产品需求文档      40 处「底稿」   ← 给人读的，术语需要精确
   openspec/specs/  108 处「底稿」  ← 给实现者读的，行为契约
   frontend/src/     76 处「底稿」   ← 给用户看的，必须白话
```

其中只有一小部分是**用户可见的界面文案**，其余是概念表述与解析关键词，这是本设计要区分的第一件事。

## Goals / Non-Goals

**Goals:**

- 界面上不再出现「底稿」二字，全部换成用户一眼就懂的词
- 「我的简历」与「定向版本」这对概念在导航、标题、正文里保持一致，不出现同物异名
- 产品需求文档与规格同步换词，文档读者能对照到界面
- 留一条可自动校验的约束，防止「底稿」以后再溜回界面

**Non-Goals:**

- 不改任何行为。诊断规则、覆盖分级、排序护栏、删减闸门、变换与不变量校验全部不动
- 不改数据模型、`xiaoyi.draft.v1` 存储键、`MIGRATIONS` 迁移链
- 不改代码标识符（`Draft` / `draftId` / `draftRevision`）与持久化字段名
- 不做界面结构调整（导入页并入编辑页等），见 Open Questions

## Decisions

### D1 三层用词各走各的，只在用户可见层换白话

先把「底稿 / 版本」的出现位置按**读者**分成三类：

| 层 | 读者 | 处理 | 理由 |
|---|---|---|---|
| 界面文案 | 求职者 | **换成白话** | 目标用户不会为「底稿」停下思考 |
| PRD / 规格 | 实现者、产品 | **保留原词 + 对照说明** | 这两个词精确表达了「唯一事实源」「快照」两个设计概念，评审时比白话更准 |
| 解析关键词 | 无 | **不动** | `教育背景`/`工作经历` 是中文简历的固定写法，是被解析的对象，不是界面用词 |

于是只有「用户可见的界面文案」这一类需要重写。这把改动从「全文替换」压缩到「约 50 处文案」。

**替代方案**：全局替换（PRD、规格、代码全换成「我的简历」）。好处是只有一套词；坏处是要改 30 条需求的主语，且 PRD 作为产品定义文档会失去「底稿」这个更精确的术语。同时把「概念表述」和「界面表述」混为一谈后，无法再用规格描述内部语义。

### D2 术语映射

```
内部概念（PRD / 规格）      界面用词
──────────────────────────────────────────
底稿                        我的简历
版本                        定向版本
```

选「我的简历」而不是「求职素材」：求职者脑子里本来就有一份「我的简历」，不需要先理解「素材」这个抽象层；而「素材」听起来像附件、证书那一堆，也暗示它不是一个文件。

选「定向版本」而不是「版本」：单说「版本」无法区分「我维护的那份」和「投出去的那一版」；「定向」明确指出它是为某份 JD 定向生成的。

**替代方案**：「简历」（不带「我的」）。但顶栏、面包屑等处脱离上下文时，「简历」会和「定向版本」里的简历混起来。「我的」提供了所有格归属，代价是三个字。

### D3 长短语境分工

「定向版本」四个字，塞进句子和按钮会明显变长。因此：

```
导航项 / 页面标题      → 定向版本   （用户在选页面，需要明确）
句子 / 提示语 / 按钮   → 版本       （上下文已经在了）
```

例：`这一版只对你简历中已有的事实做重组` 而不是 `本定向版本只对…`。

**替代方案**：全部用「定向版本」。一致性更好，但同一屏里出现三四个「定向版本」会很吵。

### D4 文档保留原词，但必须留对照

PRD 与规格继续用「底稿」「版本」，但 PRD 开头加一段对照说明：

> 文档中的「底稿」在界面上显示为「我的简历」；文档中的「版本」在界面上显示为「定向版本」。

对照放在 PRD 开头而不是散落各处，是因为读者可能只读其中一段。对照必须显眼，否则读 PRD 的人会把「底稿」直接写进界面。

规格里则不加对照段：规格本身就是给实现者读的，实现者同时会打开界面看到实际文案。

### D5 代码标识符与存储键一律不动

`Draft` / `draftId` / `draftRevision` / `xiaoyi.draft.v1` 全部保留原样。

- **不改存储键**：改键要同步改 `MIGRATIONS` 迁移链，而迁移链写错的后果是旧存档被静默丢弃（迁移失败会丢弃该片数据并提示一次）。这是纯文案变更，不该承担数据风险。
- **不改标识符**：`Draft` 在英文里与 `version` 并置时并不含糊（`draftStore.draft` vs `versionStore.versions`），改动会波及全部引擎、存储字段与持久化结构，收益只有「看着顺眼」。

领域类型上补一行注释指明 `Draft` 对应界面上的「我的简历」，让后来者不必自己桥接两套词。

### D6 用一条可执行测试守住这次改动

改名最怕回退。因此在 `flows.spec.ts` 里加一条断言：扫描 `frontend/src/views`、`components`、`layouts` 下的模板文本，断言其中不出现「底稿」。这条测试比任何评审意见都可靠。

引擎产出的用户可见文案（`versionAssembly.ts` 里的未覆盖说明、改动原因）同样纳入扫描范围。

## Risks / Trade-offs

**[文档与界面对不上，读者困惑]** → PRD 开头给出对照；规格里的用户可见文案已随增量同步（两处：未覆盖要求的说明、完整性校验结论）

**[只改了界面，漏掉某处文案]** → 用可执行测试扫描全部模板，而不是靠人工 grep；引擎文案纳入同一扫描

**[「我的简历」被理解为可以直接投递的成品]** → 落地页副标题明确说明它需要经过「粘贴 JD → 生成定向版本」才是投递件；编辑页副标题同样点明它是「唯一的事实来源」而非成稿

**[「定向版本」在短语境里被简写成「版本」造成歧义]** → 短语境里出现的位置必然已有上下文（同一屏内已有「定向版本」的标题或菜单），且规格里明确了两者的分工

**[改动只在文案，评审看不出价值]** → 改动量小是刻意的：这是术语问题，不是行为问题

## Migration Plan

1. 先补 `resume-terminology` 规格与两条增量规格，确立契约
2. 按 design 中的逐页对照表改界面文案，每改完一处即更新任务清单
3. 同步 PRD 的对照说明；PRD 正文保留原词不动
4. 补扫描测试，作为回归护栏
5. `npm run type-check` / `npm test` / `npm run build` 全绿，浏览器走查首屏与各页文案

**回滚**：全部改动都是文案与文档，无数据迁移，回滚即还原文件。

## Open Questions

1. **导入页是否并入编辑页**：导入只在「第一次」与「覆盖时」两个时刻有意义，日常用户几乎只在编辑页。若并入，侧栏可少一个概念，但这是结构调整而非改名，需单开变更。本次不做。
2. **侧栏「简历诊断」是否改回「诊断」**：四字比两字长，但能让用户知道诊断对象是简历而非 JD。
3. **产品名最终定稿**：「小奕·简历」——收敛为简短品牌名，①唯一事实源与②多版本的关系由落地页大标题「一份简历，按 JD 生成多个互不影响的定向版本」交代。
4. **代码标识符是否在后续变更中统一**：本次按 D5 不动；若产品决定长期对外使用「我的简历」，可在后续变更中一并处理，届时需同步迁移链。
