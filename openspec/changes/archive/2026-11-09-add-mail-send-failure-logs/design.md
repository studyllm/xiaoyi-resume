## Context

发信失败会经过两条路径，现在一条静默、一条失控：

| 端点 | 现状 | 问题 |
| --- | --- | --- |
| `POST /api/v1/auth/register` | `catch {}` 吞掉错误 → 502 `EMAIL_SEND_FAILED` | 日志里没有任何线索 |
| `POST /api/v1/auth/password-reset` | 没接住，冒泡到 Fastify 的兜底 → 500 `INTERNAL_ERROR` | 用户看到「出了点问题」；而且 500 只在「邮箱已注册」时出现 |

日志与隐私口径的边界：`docs/privacy-conclusions.md` §4.5 说「正文、邮箱、令牌一律替换」；`docs/ops/runbook.md` §3 说「日志里没有简历正文」。

## Goals / Non-Goals

**Goals:**

- 发信失败时，日志能回答「为什么失败」和「是哪一次请求」。
- 找回密码端点不因发信失败泄露账号是否存在。
- 本地环境照 README 走就能跑通注册。

**Non-Goals:**

- 不改发信的成败判定，也不换发信服务商。
- 不把邮件内容写进日志（正文、令牌、收件邮箱都不写）。
- 不给「发信失败」加新的用户可见状态——现有 `email-send-failed` 已经说了「验证邮件没发出去」。
- 不清理失败留下的令牌（见 D6）。

## Decisions

### D1. 只记白名单字段，不整包丢 `err`

nodemailer 的错误对象上可能带认证相关字段。记 `{ name, message, code }` 三个字段：`message` 里通常有 `connect ECONNREFUSED 127.0.0.1:1025` 这种能直接定位的信息，`code` 是机器可读的那一份（`ECONNREFUSED`、`ETIMEDOUT`、SMTP 的 `535`）。

`app.ts` 的兜底错误处理器里已经有一段一模一样的提取逻辑，挪到 `http/logger.ts` 共用，两处记出来的东西形状一致。

### D2. 找回密码发信失败仍返回 204

这个端点的契约是「无论邮箱存不存在都返回 204」——提示不同等于泄露账号注册过（ADR-0002 §3）。发信失败如果回 502，就只有「邮箱已注册」的那些请求会收到 502，**等于用状态码把账号存不存在说出来了**。

所以发信失败只进日志，响应照旧 204。用户等不到邮件，代价是排障靠日志而不是靠界面——这与登录失败「不区分邮箱是否存在」是同一个取舍。

### D3. 不记收件邮箱

项目的脱敏口径把邮箱列为要脱敏的项。定位一次失败靠 `requestId` 就够：用户在界面上报错时报出编号，运维按编号就能查到那一次请求。

（这条是**决定过的**，不是漏了。想看「哪个邮箱发不出去」时，先按 `requestId` 找到那一次请求。）

### D4. 注册失败仍然删账号

现在的行为不变：邮件没发出去就把账号删掉——留一个用户激活不了的账号，用户重试还会撞上「邮箱已注册」。只是删之前先把原因记下来。

### D5. README 补 Mailpit

`docker-compose.yml` 里 mailpit 在 `profiles: ['mail']` 里，默认不启动；README 的快速开始只写了 `npm run db:up`（只起 postgres）。照 README 走，注册链路必然 502。

快速开始改成把 mailpit 一起起来，并说明它默认不在 `db:up` 里。

### D6. 失败留下的令牌不清理

找回密码发信失败时，库里会留下一条没人知道的令牌（24 小时后过期、一次性、没人拿得到）。清理它要动存储接口的返回值，收益只是库里少一行垃圾。不做。

### D7. 失败要分类，并说清下一步

nodemailer 的错误对象里有三样决定性的东西：

| 字段 | 例子 | 说明什么 |
| --- | --- | --- |
| `command` | `AUTH PLAIN` | 失败在**哪一步**（认证 / MAIL FROM / RCPT TO / DATA） |
| `responseCode` | `526`、`535` | 服务端回��� SMTP 状态码 |
| `code` | `EAUTH`、`ECONNREFUSED` | 机器可读的分类 |

光看 message 只知道「认证失败」。有了这三样才能说「**认证这一步**被拒（526）」——那是授权码不对，跟网络没关系。

服务端据此把失败分成三类（认证被拒 / 连不上 / 其它），每类给一句中文的**原因**与一条**下一步**。分类逻辑放在 `smtp.ts` 的 `describeSmtpFailure`，注册与找回密码的日志都用它——一处分类，两处使用。

日志里同时记下 `command` 与 `responseCode`（白名单字段，都是 SMTP 协议字符串与数字，不含凭据）。

### D8. 启动时自检发信

`transport.verify()` 只登录不发信。启动时跑一次：

- 通过 → 打印「SMTP 自检通过」
- 认证被拒 → 打印原因与下一步，**但不让服务端退出**

为什么认证被拒不退出：邮件只影响注册与找回密码，导入、解析、编辑、导出都还能用。为了一个附属功能把整个服务挡住，代价比问题大。端口与加密方式自相矛盾（D9）那种静态可判的错仍然退出——那不是暂时的问题。

### D9. SMTP 端口与加密方式不匹配时，启动就退出

`465` 是隐式 TLS 端口（RFC 8314）。拿明文去连它，对面会直接掐断连接，nodemailer 报出来的是 `Connection closed unexpectedly`——**看不出是哪配错了**。

这不是「发信失败」，是「配置自相矛盾」。项目自己的原则是「带着半套配置跑起来的服务端比不启动更糟」（runbook §1.1），所以服务端启动时自检：端口是 465 而 `SMTP_SECURE` 不是 true，就退出并说清怎么改。

只查这一条：465 是标准端口，没有歧义。别的端口用哪种加密由服务商说了算，服务端不替它猜。

顺带把生效的发信目标（主机、端口、加密方式）打出来——配错时从这一行就能看出来，不用去猜。

### D10. 真实的邮件服务商怎么配，写在 `.env.example` 里

换成真实服务商时有两处容易错：`SMTP_SECURE` 要跟端口对上，`SMTP_PASS` 要的是**授权码**而不是登录密码。这两点写进 `.env.example` 的注释——那是开发者第一次看到这份配置的地方。

## 验证方式

- `server/src/auth/auth.spec.ts`：
  - 注册发信失败时，日志里有失败原因，且仍回 502、账号被删掉。
  - 找回密码发信失败时，仍回 204（不是 500），且日志里有失败原因。
- `server/src/auth/smtp.spec.ts`：
  - 465 配明文时报错；465 配隐式 TLS 与 1025 配明文都通过。
  - 认证被拒（`EAUTH` + `AUTH PLAIN` + 526）判成「认证」类，提示里出现「授权码」。
  - 连不上（`ECONNREFUSED`）判成「连不上」类。
  - `checkSmtp` 在 verify 成功时通过、失败时给出原因与下一步。
- 手工：把 Mailpit 停掉再注册 → 服务端日志出现「验证邮件发送失败」与底层原因（`ECONNREFUSED` 之类）；把 Mailpit 起起来再注册 → 201。
- 手工：启动服务端 → 打印生效的发信目标与自检结果；凭据被拒时打印中文原因与下一步，服务端照常起来。
- 仓库根 `npm run verify` 全绿。
