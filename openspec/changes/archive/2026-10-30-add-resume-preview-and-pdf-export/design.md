## Context

用户要把简历带走时，唯一动作是「复制正文」——得到一段纯文本，再自己贴进 WPS/Word 手工排版。系统已经把内容按 JD 组织好了，却没有交付一份能直接投出去的东西。这是投递链路上最实际的缺口。

PDF 导出在 PRD §4 的「不在本版」栏，本次要把范围挪回来，因此 §4 的措辞必须同步改写，不能当成一次纯前端优化。

同时探针确认了一个前置缺口：

```
原始文本前 4 行                    解析后
─────────────────────────────    ─────────────────────────────
张三                          →  已丢失
前端工程师 · 6 年经验            →  已丢失
手机：138-0000-0000              →  已丢失
邮箱：zhangsan@example.com      →  已丢失
```

`parseDraft` 只认分区表头，表头之前的行一律跳过。导出的 PDF 会是一份没有姓名和联系方式的简历，投不出去。

## Goals / Non-Goals

**Goals:**

- 定向版本能预览成一张 A4 简历，并能导出成带文字层的 PDF
- 预览与导出共用同一份 DOM 与 CSS，所见即所得成立
- 简历抬头进入底稿，导出物包含姓名与联系方式
- PRD 的范围边界同步改写，不再与实现矛盾
- 不新增运行时依赖

**Non-Goals:**

- 不做双栏、侧边色块、头像、图标、模板市场
- 不还原用户粘贴的原始 PDF 版式（原型从未持有原始版式，也拿不回来）
- 不为「我的简历」提供预览与导出（编辑态不是成品，且无 JD 定向）
- 不引入后端渲染（LaTeX / HTML→PDF 服务）
- 不改动诊断、覆盖分级、排序护栏、删减闸门与措辞变换

## Decisions

### D1 用浏览器打印导出，不用 html2canvas + jsPDF

决定性约束是**文字层**。简历投给 ATS（招聘管理系统），ATS 靠提取文字层来填姓名、公司、学历等字段。整页位图的 PDF，ATS 读出来是空白，简历等于不存在；候选人自己 Ctrl+F 也搜不到。

```
A. 浏览器打印（window.print + @media print）
   依赖 0 · 文字层 ✅（系统字体，无需嵌字体）· 排版 ✅（浏览器排版引擎）
   分页 ✅（CSS break-inside: avoid 现成）
   体验 ⚠️ 弹打印对话框，用户需自选「另存为 PDF」

B. html2canvas + jsPDF
   依赖 +2 · 文字层 ❌（整页位图 → ATS 拒）· 体积 ⚠️（一页 A4@2x ≈ 1-2MB PNG）
   → 否决

C. pdfmake
   依赖 +1 · 文字层 ✅ · 中文 ⚠️ 必须内嵌 CJK 字体（数 MB）
   走 CDN → 违反「不发任何网络请求」；打进 bundle → 体积膨胀
   → 成本比 A 高一个量级，收益相同
```

A 的唯一缺陷是「不像导出」，用文案化解即可：点击后调起打印，界面提示「在打印目标中选择『另存为 PDF』」。换来的是零依赖、完美文字层、最好排版与现成分页控制。

### D2 预览渲染结构化数据，不是渲染 body

版本正文是纯文本，形如 `美团 | 前端工程师 | 2021.03 - 至今`。那个竖线是**丢掉排版信息之后的补救**——纯文本无法做「公司名 …… 日期」两端对齐，而这正是简历最好认的形态。

`ResumeVersion.sections` 里 `VersionItem` 的 `org` / `title` / `start` / `end` / `present` 是分开的字段，因此预览直接吃 `sections`。

推论：**预览不是 body 的美化版，是结构化数据的第一次可视化**。这是新能力，不是旧功能的皮肤——排版规则要新写，body 保持原样继续服务「复制纯文本」。

### D3 排版层级限定为单栏经典版

```
级别 1  单栏纯文本排版          工作量小 · 观感接近"把文本印到纸上"
级别 2  单栏 + 经典层级  ← 选这个 工作量中 · 求职者认得 · 可直接投
级别 3  双栏 / 色块 / 图标       无底洞：字体、栏宽、A4/Letter、打印机差异、ATS 解析
```

级别 2 的具体规则：

```
分区标题    加粗 + 细下划线，字号比正文大一级
条目头      公司名(粗) 职位(常规) ········ 起止日期(右对齐，同一行)
要点        悬挂缩进，▪ 或 · 前缀
```

级别 3 正是当初被排除的「精美排版」。PRD 里要写死不做级别 3，避免下一轮又把它拉回来。

导出物**不加页码与页眉页脚**：多数公司模板与主流 ATS 都不带，加了还要额外处理「第 X 页 / 共 Y 页」的计算与多页对齐，是纯粹的负担。

预览**整页居中呈现**，不做缩略图模式：所见即所得优先于一屏看全。实现上是一张固定 210mm × 297mm 的纸，居中放在中性背景上，带纸张投影；纸比视口高时纵向滚动查看。代价是笔记本上第一屏看不到整页，换来的是预览与打印结果完全一致，不存在"预览缩着看、导出是另一回事"的落差。缩放适配（如「适应窗口」按钮）留作后续。

### D4 预览与导出同源

两者共用同一个 `ResumePreview` 组件与同一套 CSS。导出时用 `@media print` 隐藏界面 chrome（顶栏、侧栏、演示模式横幅、按钮），只留 A4 纸。

```
@media print {
  .layout-header, .layout-aside, .layout-banner, .page-actions { display: none }
  .resume-paper { box-shadow: none; margin: 0 }
}
```

风险：漏藏一个元素就会把「小奕·简历」印在简历上——比没有导出更糟。因此打印样式需要一条测试兜底（见 tasks 里的验证项）。

### D5 抬头进底稿，走存储键 v2 + 迁移链

抬头是事实，与其它内容同级，因此存进 `Draft.profile`（姓名 / 一句话定位 / 联系方式列表）。

**抬头只做这三项**，不加 GitHub、个人网站、社交账号等字段：这三项已经覆盖绝大多数中文技术简历的抬头需求，再加字段就要重新考虑提取规则（哪些域名算链接）与展示宽度，反而把一个简单能力做复杂。

```
interface DraftProfile {
  name: string
  headline: string
  contacts: { label: string; value: string }[]
}
```

解析时从**第一个分区表头之前**的行提取：短行且不含冒号 → 姓名候选；含 `：`/`:` 的行 → 拆成标签与值（手机 / 邮箱 / 微信…）。提取失败时 `profile` 为空，不影响解析成功判定。

存储影响：`Draft` 结构变了，`xiaoyi.draft.v1` 的格式不再兼容。

```
xiaoyi.draft.v1  →  xiaoyi.draft.v2      新键
LEGACY_KEYS 增加 xiaoyi.draft.v1
MIGRATIONS['xiaoyi.draft.v1'] = [{ version: 2, migrate: 补上空的 profile }]
```

**版本切片同样要迁移。** 这是实现阶段才暴露的：`ResumeVersion` 结构在这轮之前已经加过一次 `coverage`（要求覆盖分级），这轮又加了 `profile`，两次都没有配套迁移，于是老存档里的版本缺这两个字段，渲染预览时直接白屏。结构每变一次，切片就要跟着升一版：

```
xiaoyi.versions.v1  →  xiaoyi.versions.v2   新键
MIGRATIONS['xiaoyi.versions.v1'] = [{ version: 2, migrate: 补 profile 与 coverage }]
```

组件侧同时兜一层：预览组件对缺失的 `profile` 用空抬头兜底，不因为一个可选字段缺失就白屏。数据迁移负责补齐历史数据，组件兜底负责不让任何一条路径崩掉——两层都要有。

这是上次 `rename-resume-terminology` 的 D5 刻意推迟的那件事——当时判断「纯文案变更不该带数据风险」，现在真的要动结构了，迁移链正好是为这种情况准备的。旧存档迁移后 `profile` 为空，用户手动补一次即可，不阻塞。

### D6 版本携带生成时刻的抬头

快照语义要求版本独立。生成版本时把当时的 `profile` 拷进 `ResumeVersion`，之后改底稿抬头不回写旧版本。

因此导出 PDF 用的是 `version.profile`，不是当前底稿的抬头——否则旧版本导出会变，与「版本是快照」矛盾。

### D9 老键回溯按 key 家族隔离

老键回溯原先是一条扁平的 `LEGACY_KEYS` 列表，读哪个当前 key 就遍历整张列表。后果是：读 `xiaoyi.draft.v2` 时可能先命中 `xiaoyi.versions.v0`，把版本数组当成底稿写进底稿键。

改成按家族声明：

```
LEGACY_KEYS = {
  'xiaoyi.draft.v2':    ['xiaoyi.draft.v1', 'xiaoyi.draft.v0'],
  'xiaoyi.versions.v2': ['xiaoyi.versions.v1', 'xiaoyi.versions.v0'],
}
```

回溯只在本家族内进行，且没有对应迁移步骤的键直接跳过而不是把原值写进当前键。

### D7 三个带走出口并存，格式与用途各不相同

```
复制纯文本      →  version.body        ATS 解析、贴进自己的 Word 模板继续改
复制为 Markdown →  renderMarkdown()    投进接受 Markdown 的表单、贴进支持渲染的编辑器
导出 PDF        →  浏览器打印            直接投递
```

「复制正文」改名为「复制纯文本」以示区别。版本正文格式本身不变（仍可被 `parseDraft` 重新解析，这条已有规格）。界面上「复制」做成一个下拉，含「纯文本」与「Markdown」两项；「导出 PDF」独立成一个按钮——它是终态动作，不该藏在菜单里。

Markdown 从 `sections` 渲染而非从 `body` 改写，因此能表达纯文本表达不了的层级：

```markdown
## 工作经历

**美团** · 前端工程师 · 2021-03 - 至今

- 主导活动平台前端架构升级，引入 Vue 3 与 Vite，页面构建时间从 120s 降到 18s
```

分区用 `##`，条目用一行加粗的公司名开头而不是 `###`——简历是线性阅读的，每个条目都升一级标题会在目录里堆出大量噪声。Markdown 与 PDF 一样带抬头、一样只含该版本的内容。

`renderMarkdown` 放在引擎层（`src/engines/markdown.ts`），是纯函数、确定性、可单测，与 A4 预览共享同一份 `sections` 输入。

日期表示**统一沿用 `2021-03`**，Markdown、纯文本与 A4 预览三处一致，不在 Markdown 里单独换成 `2021.03`——三种带走方式应当给出同一份内容的事实，格式差异只体现在承载媒介上。

## Risks / Trade-offs

**[打印对话框挡住导出路径]** → 界面给出明确提示「在打印目标中选择『另存为 PDF』」；在 `window.print` 被拦截时给出降级提示，引导用户用「复制纯文本」

**[打印样式漏藏界面元素，把产品名印进简历]** → 打印样式集中在 `ResumePreview` 内；用测试断言打印样式规则存在且覆盖了顶栏、侧栏与横幅；浏览器走查时实际打印一次核对

**[A4 与 Letter 纸张不一致导致排版偏移]** → 预览固定用 A4 尺寸（210×297mm）并显式设定 `@page { size: A4 }`；用户打印机若不是 A4 由浏览器自行缩放，不追求像素级一致

**[不同浏览器的中文字体渲染差异]** → 字体栈使用系统默认（`PingFang SC` / `Microsoft YaHei` / `sans-serif`），不内嵌字体，因此不产生体积与网络开销；接受不同机器上字形略有差异

**[抬头提取误判，把正文首行当成姓名]** → 只在第一个分区表头之前提取，且姓名候选需满足短行、无冒号、无日期格式；提取结果在编辑页可见并可改，误判成本可控

**[预览与导出的分页表现不一致]** → 两者同源同 DOM，且都用 `break-inside: avoid`；浏览器走查时对比预览页数与打印页数

**[旧存档升级后抬头为空]** → 迁移链补空 `profile`，不阻塞；编辑页提示补全

## Migration Plan

1. 先更新 PRD（§4 范围表、§5 概念、§7 新增小节、§9 验收标准），把范围边界写死
2. 领域模型与存储：加 `Draft.profile`、`VersionItem` 抬头字段、`xiaoyi.draft.v2` 与迁移链
3. 解析器：提取抬头
4. 排版组件：`ResumePreview`（A4 纸张视图 + 打印样式）
5. 接入：版本详情新增预览页签与导出按钮，版本列表新增导出入口，编辑页新增抬头编辑区
6. 验证：单测 + 浏览器打印核对 + 全量回归

**回滚**：改动集中在新增字段与新增组件；回滚即还原文件，旧存档仍可被 v1 键读取（迁移链保留双向兼容）。

## Open Questions

本设计无遗留开放问题。以下四项在讨论中已定案，记录于此以免后续被重新提起：

| 问题 | 结论 | 落在 |
|---|---|---|
| 抬头是否支持 GitHub / 个人网站等字段 | 不做，只保留姓名 / 一句话定位 / 联系方式 | D5 |
| 导出物是否加页码与页眉页脚 | 不加 | D3 |
| Markdown 的日期是否换成 `2021.03` | 不换，统一沿用 `2021-03` | D7 |
| A4 预览是否需要缩放适配 | 不做，整页居中，留作后续 | D3 |
