## Context

`frontend/src/views/VerifyEmailView.vue` 与 `ResetPasswordView.vue` 写好了，从来没接在路由上。兜底路由 `/:pathMatch(.*)*` → `/draft` 把它们全都吃掉，于是邮件链接落到一个要求登录的页面，形成死循环。

链接路径本身也写了两份：服务端 `server/src/auth/mailer.ts` 里硬编码 `/verify-email`、`/reset-password`，前端路由各写一份。两边对不上没人拦。

## Goals / Non-Goals

**Goals:**

- 邮件链接落到能用的页面上。
- 链接路径只有一处定义。
- 「视图写了、路由忘了」这种半截实现不再溜过去。

**Non-Goals:**

- 不改这两个页面的界面与文案——它们本来就是对的，只是没被路由到。
- 不改接口、错误码与状态表。
- 不动登录、注册的其它流程。

## Decisions

### D1. 两条路由放在顶层，不进工作台布局

它们是从邮件点进来的**一次性页面**：验证完或改完密码就走。顶栏与侧栏是工作台的外壳，对一个刚点开邮件链接、还没登录的用户没有意义。

落地页已经是裸页了（`DefaultLayout` 里 `route.meta.public` 的那个插槽只渲染 `router-view`），所以裸页是既有形态，不是新样式。

放在顶层还有一个好处：路径是绝对的，可以直接引用共享包里的常量；挂在布局下就得写相对路径，同一个常量用不了两处。

### D2. 标 `public: true`

路由守卫第一道关就是「没登录态 → 送回落地页」。从邮件进来的人本来就没有登录态——验证邮箱这个动作**本身就是**建立登录态的地方（服务端在 `verify-email` 里直接建会话）。标成公开页，守卫才放行。

### D3. 链接路径进共享包

服务端建链接、前端接路由，引用同一份定义（`packages/shared/src/domain/links.ts`）。这是 `CLAUDE.md` §1 那条原则的应用：同一份事实不写两遍，靠结构保证，不靠约定。

放在 `domain/`：它是纯数据，没有依赖，两端都能引。

### D4. 两条守卫，一条查「链接指向的页面在不在」，一条查「有没有写了没接的页面」

- **链接路径都在路由里**：运行时检查（拿共享常量比对路由表）。这条直接覆盖这次的问题。
- **每个视图都接在路由上**：静态扫路由源码里有没有引用每个 `views/*.vue`。这条覆盖更一般的半截实现——视图写了、路由忘了。

第二条是文本扫描，但扫的是路由源码：**路由表本身就是字面量**，行为完全由它决定（与「CSS 的效果静态扫不到」不是一回事）。

## 验证方式

- `frontend/src/flows.spec.ts`：两条守卫。
- 手工：对着 Mailpit 注册 → 从 Mailpit 取出验证链接 → 无头浏览器打开 → 页面显示「邮箱已验证」，且登录态已建立。
- 手工：打开 `/reset-password?token=…` → 落到重置密码页。
- 仓库根 `npm run verify` 全绿。
