## Context

服务端已经实现 `POST /api/v1/draft/parse`（公开、匿名可用、纯计算不落库），前端却在浏览器里用同一份引擎源码解析。前端 API 层根本没有这个端点的调用方。

## Goals / Non-Goals

**Goals:**

- 导入页的解析走服务端，与冻结的契约一致。
- 服务端不可达时，界面说清现在的状态与下一步。
- 解析结果的形状不变——分区、要点、置信度、警告、其它分区表头都跟现在一样。

**Non-Goals:**

- 不动诊断与 JD 解析（服务端还没实现那两个端点）。
- 不改服务端那个 parse 端点的行为。
- 不改保存流程：保存时服务端重跑结构检查做权威校验，那条已经在了。
- 不引入「服务端失败就回落本地引擎」的第二条路径。

## Decisions

### D1. 前端解析改成调接口，不保留本地回落

导入页解析需要服务端可达。**不做本地回落**，理由：

- 两套路径意味着两套行为——服务端改了规则、浏览器里的那份没跟上，用户会拿到两份不一样的解析结果，而且没人知道拿到的是哪一份。
- 契约里只有一个解析端点。回落等于契约之外还有一个看不见的入口。

代价是断网时导入页不能解析。这是明说的取舍（导入页要联网），由 D3 的失败态兜住。

### D2. 失败态从错误码取，不自己编

服务端回 `422 RESUME_EMPTY` / `422 PARSE_FAILED`，前端按错误码从状态表取文案（`parse-empty` / `parse-empty`… 见 `states.ts`）。连不上时 `api()` 抛的是「离线」那条状态。

所以 store 的 `ingest` 不再返回引擎那份 `ParseResult`（它带 `reason: 'empty' | 'unrecognized'`，那是引擎内部的分类，网络失败没有对应值），改成返回自己的结果形状：

```ts
{ ok: true; draft; confidence; warnings; otherHeaders }
| { ok: false; failure: { state: StateCopy } }
```

`state` 里既有标题也有下一步，界面直接用。

### D3. 服务端不可达时，导入页说清下一步

状态表里「离线」那条：「现在连不上服务器 / 改动还在这个页面上，等连上再保存。」——但导入页没有「改动」可保存，用户需要的是「连上再解析」。所以导入页要用自己的说法：**说明连不上服务器，并给出「等服务端恢复后再解析」这个下一步**。

这是 `resume-draft` 规格里已有的一条（「界面说明连不上服务器」，§430）的具体化。

### D4. 解析结果里的 id 由服务端给，本机的种子要接着它续

本地解析时条目 id 来自浏览器里的 `IdSeed`；改走服务端后来自服务端的种子。

**本机新增的条目（加要点、加条目）用 store 里的种子生成 id。** 解析完必须把那个种子接到服务端给的 id 上——`resumeIdSeed(collectDraftIds(draft))`（`restore()` 读服务端草稿之后也是这么做的）。不接的话，本机种子从零开始，会生成服务端已经用过的 id（`sec-1`、`itm-1`……），撞号。

这条是被 store 的用例逮到的：「新要点拿到新标识」在改之前绿、改之后红——因为解析不再推进本机的种子了。

id 只需要在「解析 → 编辑 → 保存」这一段里保持稳定（服务端保存时校验的就是这批 id）✓。

### D5. 结构问题清单仍然在浏览器里算

导入页在保存之前就要把「缺公司名、缺时间」这类问题显示在纸面上方，而服务端的结构检查是**保存时**才跑的（那时才返回问题清单，契约 §4.2）。所以展示用的那一份仍在浏览器里算——它与服务端算的是同一份源码（`packages/shared` 的 `structure.ts`），保存时服务端那份才是权威。

不动它。

### D6. 5xx 配一段不是 JSON 的正文，算「连不上」

我们的服务端永远回 JSON（契约 §2.2）。所以浏览器收到一个**5xx 且正文不是 JSON**的响应时，可以断定请求没到我们的服务端——那是中间那层回的字（开发环境的 Vite 代理、网关）。

开发环境里后端一挂，Vite 代理就回这么一段 500（正文是 `text/plain` 的代理错误信息）。`fetch` 是**成功**的（拿到了响应），所以 `api()` 原来把它当成未知错误 → 界面显示「出了点问题，刷新一下再试」——用户不知道该等什么。

判成「连不上」之后，导入页才能说清下一步。4xx 不受影响：那是我们的服务端回的话。

### D7. 诊断与 JD 解析继续留在浏览器

服务端没实现 `POST /api/v1/diagnosis` 与 `POST /api/v1/jd/analyze`。动它们要先补端点（连带鉴权、幂等、错误码），不在本次范围。

代价是同一个应用里两种做法并存：**简历解析走服务端，诊断与 JD 解析在浏览器**。这是过渡期的状态，写进 README 与提案里，别让它变成「谁都没注意的既定事实」。

## 验证方式

- `frontend/src/stores/draft.spec.ts`：解析走接口（断言接口被调用）、服务端不可达时给出离线状态、空正文给出「没有可解析的内容」。
- `frontend/src/views/ImportView.spec.ts`：粘贴与上传两条路径都走接口；服务端不可达时界面说明连不上。
- 手工：起前端与服务端 → 导入页粘贴一份简历 → **Network 面板里出现 `POST /api/v1/draft/parse`** → 纸面上出现解析结果；停掉服务端再解析 → 界面说清连不上。
- 仓库根 `npm run verify` 全绿。
