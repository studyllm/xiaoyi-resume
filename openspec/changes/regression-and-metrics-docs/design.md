## Context

两份纯文档交付物。计划里的位置：

- T2.7 / D8 → `docs/regression-cases.md`：P2 出口门的一项（「回归库」），也是 P5 发布检查单（D10）的底稿。
- T2.8 / D3 / F6 → `docs/success-metrics.md`：**P3 开始前**就要产出，P5 补埋点与看板时按它实现。

现状：500 多个自动化用例覆盖不到 CSS 效果、版式、悬停反馈、PDF 文字层；产品则完全没有指标定义。

约束：

- 清单要能被人真的用下去——太长会被放弃，太短会漏。
- 指标口径要能被埋点事件算出来，否则定义了一个算不出数的东西。
- 原型是纯前端、零后端，埋点还没地方埋；本轮只定口径。

## Goals / Non-Goals

**Goals:**

- 人工验收有一份可逐条勾选、每条写清怎么看的清单。
- 成功指标有一个北极星、一条漏斗、一张事件表，三者互相算得出来。
- 两份文档都能被 P5 直接消费，不需要再翻译一遍。

**Non-Goals:**

- 不实现埋点、不做看板、不写代码。
- 不做数据分析、不做用户访谈、不给增长建议。
- 不重写已有的 500 多个自动化用例。

## Decisions

### D1. 回归清单按「要看出什么」组织，不按页面组织

按页面组织会写成「检查导入页」这种没法勾选的话。按**要观察的效果**组织，每一条写成「做什么 → 看到什么算通过」，验收人才不用自己想该看什么。

**理由**：清单的读者是验收人，他的任务是执行不是设计测试用例。

### D2. 清单只收自动化测不到的部分

结构、字段、状态流转、不变量这些已经有 500 多个自动化用例盯着。清单里重复它们只会让清单变长，且两处不同步时反而误导。

**理由**：清单的价值在于补上自动化盲区，不在于重复。

### D3. 北极星选「成功投递的版本数」

北极星要同时满足三点：代表产品真的帮上了忙、能由埋点算出来、不会被刷。

- 「简历份数」不行——放进来不代表用上了。
- 「诊断次数」不行——诊断是手段。
- 「页面访问」更不行。
- **「成功投递的版本数」**（用户导出一份版本并复制/导出投递）符合三点。

### D4. 漏斗按真实路径拆七步

落地 → 导入 → 保存 → 诊断 → 生成 → 导出 → 投递。

每一步的流失定义要能由事件算出来，所以定义成「到达这一步但没到下一步」，而不是「在这一步做了什么」。

### D5. 事件表不采集简历内容

简历正文、姓名、联系方式一律不进事件属性。这既是隐私底线，也让数据量可控。

**理由**：`docs/privacy-policy.md`（P5）还没写，但采集个人内容的风险不能等到写政策时再想。

### D6. 口径变更要留痕

指标定义改了要记原因与生效时间，历史数据分段标注。

**理由**：口径变更是看板数据不可比的头号原因，也是最容易被忘记的一步。

## Risks / Trade-offs

**[清单会过期]** → 每条写清它对应哪个能力域；能力域变了就要复核清单。清单里标上最后一次复核时间。

**[北极星选错]** → v1.0 只上线一个版本，先记着它；上线三个月后按真实数据复核。判断标准写进文档，不靠记性。

**[事件表设计得埋点实现不了]** → 每条事件标明「前端可记」还是「需要服务端」。纯前端阶段只记前者。

**[两份文档没人看]** → 清单进 P5 的发布检查单，事件表进 P5 的埋点任务。挂在流程上，不靠自觉。

## Migration Plan

无代码改动。文档合入即生效。

## Open Questions

- 演示模式下的行为要不要计入指标。目前倾向不计，演示用户不是真实用户。
