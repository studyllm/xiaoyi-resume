## Context

界面上的失败与空态文案目前逐处手写，分布在 6 个视图、1 个组件和路由守卫里：同一个「需要先导入简历」在 `router/index.ts` 与 `JdView.vue` 各写一遍且措辞不同；`ElMessage.error('解析失败')`、`ElMessage.error('生成失败')`、`ElMessage.error('JD 解析失败')` 只报告没成，不给出路；9 处 `el-empty` 里全部把状态句写在 `description` 上，标题与说明挤在一处，其中 2 处完全没有动作。

约束：

- 纯前端原型，全部失败都发生在本机，没有网络层；P3 服务端化之后才会出现「网络失败」「未登录」「存储不可用」这类新状态。本轮先把这三类登记进表里占位，触发条件留给 P3。
- 引擎产出的文案（`pdfText.ts` 的失败原因、`parseDraft.ts` 的警告）由引擎自己持有，界面只是把消息透出来。
- `CLAUDE.md` §7 已经规定界面文案不得出现「底稿」与禁用词，`flows.spec.ts` 有守卫在扫。这轮新增的状态表要一起进这道守卫。
- `docs/产品开发计划-v1.0.md` T2.3 / T2.4 要求「引擎失败必须给出下一步，不得只报失败」与「三类空态都有明确下一步」。

## Goals / Non-Goals

**Goals:**

- 失败态、空态、拦截态、信息态各有一张表，文案只有一处来源。
- 每条失败都能回答「现在能做什么」。
- 每处空状态都是标题、说明、主动作三层；没有主动作的必须讲清为什么没有。
- 把「还没开始 / 做完了但为空 / 有但被筛掉了」三类空状态分开。
- 守卫能挡住新写的失败与空态字面文案。

**Non-Goals:**

- 不改引擎的判定逻辑，不改数据模型，不改路由结构。
- 不引入网络失败、鉴权失败等服务端态的真实触发逻辑（P3 的事），本轮只登记占位文案。
- 不做错误码体系（错误码是 P3 服务端化的事，见计划 §11 F5）。
- 不重写成功提示（`ElMessage.success`）的文案，成功态没有「下一步」的问题。

## Decisions

### D1. 表放在 `domain/states.ts`，不放 `engines/`

**选择**：`frontend/src/domain/states.ts`。

**理由**：`domain/` 在 `CLAUDE.md` §1 里的定位是「纯数据类型与工具」，正好符合「一张文案表」。`engines/` 是规则引擎（解析、诊断、生成），把界面文案塞进去会让引擎目录承担它不该承担的职责，而且引擎之间并不共享界面文案。

**备选**：放 `engines/copy.ts`——`engines/forbidden.ts` 已经在做类似的事（一份词表 + 断言函数）。但 `forbidden.ts` 是**校验器**（给引擎用），状态表是**内容**（给界面用），两者性质不同，放一起会让引擎目录同时承担内容与校验两件事。

### D2. 每条状态三个字段：标题、说明、动作

```ts
interface StateCopy {
  title: string      // 短句，说明现在是什么状态
  hint: string       // 一句话，讲清为什么与接下来能做什么
  action?: string    // 主动作文案；没有可执行的下一步时不写
}
```

**理由**：三种呈现方式各取所需——消息提示用 `title + hint` 拼成一句话，页面内告警用 `title` 作标题、`hint` 作说明，空状态用 `title` 作标题、`hint` 作说明、`action` 作按钮。

**备选**：拆成 `message`（一整句）与 `title`（短标题）两个字段——`message` 会和 `title` 重复，且没法复用出页面内说明。拆成四个字段（标题/说明/按钮/消息）——`message` 必然是前两者的拼接，重复维护必然走偏。

### D3. 状态表放 `domain/`，但禁用词与内部术语在测试里校验，不在运行时自校验

`pdfText.ts` 现在的做法是调用 `assertCleanOutput(message, ...)` 在运行时抛错。这轮把 PDF 的失败文案搬到状态表之后，引擎就只剩一个 `reason` 了。

**选择**：状态表不自校验；改为在 `flows.spec.ts` 里断言表内每条文案都不含禁用词与「底稿」。

**理由**：`domain/` 依赖 `engines/forbidden.ts` 会让「纯数据类型与工具」这一层依赖引擎层，方向反了。把校验放在测试层，与现有的「界面文案不出现内部术语」守卫是同一道关，位置一致、读者找得到。

**备选**：运行时自校验——好处是漏写当场炸，但 `domain/` → `engines/` 的反向依赖换来的只是早几毫秒发现，不值。

### D4. 视图里的字面文案由守卫挡掉，而不是靠人记

守卫扫描 `views/`、`components/`、`layouts/` 的全部 `.vue` 文件（先剥掉 HTML 注释），要求它们不出现失败与空态的标志性说法：`失败`、`还没有`、`没有找到`、`请先`、`需要先`、`没能`、`读不出来`、`不可用`。命中即测试失败。

**理由**：这是项目里已有的守卫风格——禁用词、内部术语「底稿」、视觉字面量都是这么守的。新加一类状态文案，同一把尺子。

**备选**：只断言「表里的状态都被用到了」——那只能防漏，不能防有人又手写了第三套说法。防漏重要，但防重复更重要。

**代价**：正文里正常提到「失败」的合法场景（比如「减少失败风险」这种描述性文案）会被误伤。所以词表要挑得足够具体，宁可漏拦也不误伤；真被误伤时在守卫的例外清单里显式登记并写明原因（`CLAUDE.md` §8 的规矩）。

### D5. 批注栏的三态由组件自己判断

`CommentSidebar.vue` 现在已经有「尚未诊断」与「零意见」两态的分支。加第三态时，判断依据是「诊断有意见，但当前筛选后可见数为 0」——这是组件内部的派生状态，不需要父组件传参。

**理由**：筛选状态本来就住在组件里（`SidebarFilters.vue`），把它抬到页面层只会多一层无意义的传参。

### D6. 正向的空结果也走三层结构

「没有可对照的改动」「这份 JD 的要求在你的简历中都能找到对应事实」这类是好结果，但也用 `el-empty` 渲染。它们 SHALL 补上说明句，写清这是好结果；不补动作（没有要纠正的事）。

**理由**：这两处现在只有一个 `description`，用户会分不清「没差异」是好事还是页面坏了。一句说明就能消除这个歧义，代价极小。

## Risks / Trade-offs

**[守卫误伤合法文案]** → 词表只收「XX失败」「还没有…」「没有找到…」「请先…」「需要先…」这类完整说法，不收「失败」这种裸词；真被误伤时在例外清单里显式登记原因。

**[把 PDF 失败文案搬进状态表会牵动 `pdf-intake` 规格]** → `pdf-intake` 规格里「提取环节的用户可见文案合规」一条说的是「文案不含禁用词与内部术语」，不是「文案由谁持有」，所以只需回填 Purpose 时补一句来源，不算破坏性变更。

**[状态表变成一个大文件]** → 表是数据不是逻辑，一个文件放几十条状态没问题；如果条目超过约 60 条，按「失败 / 空 / 拦截 / 信息」拆成四个文件，用同一个索引导出。当前规模远没到。

**[P3 服务端化后表要扩]** → 本轮就把「网络失败」「未登录」「存储不可用」登记成占位条目（只有文案、没有触发条件），P3 填上触发逻辑时不用重新设计表结构。

**[守卫是静态扫描，看不出「下一步」是否真的有路]** → 「有路可走」靠 `docs/error-taxonomy.md` 的人工走查（B2.6）兜底，不指望测试能判断。

## Migration Plan

1. 建 `domain/states.ts` 与状态表，暂不改动任何视图——此时状态表是纯新增，测试全绿。
2. 逐个视图把字面文案换成表里的条目，一次换一个，每换完跑一次测试。
3. 补齐三处缺动作的空状态与批注栏第三态。
4. 最后把守卫加上——顺序不能反：先让存量全绿，再让守卫扫存量，否则守卫一上来就红一片。
5. 回滚：改动全在视图与一个新文件里，回滚提交即可，无需数据迁移。

## Open Questions

- 状态条目用中文 key 还是英文 key？倾向英文 key（`parse-failed`），文案另存——但表里若将来要做多语言，key 需要保持稳定。
- P3 的错误码体系（F5）与这张表的关系：表按「用户看到的状态」组织，错误码按「服务端原因」组织，两者不是一一对应，中间需要一层映射。这层映射留给 P3。
