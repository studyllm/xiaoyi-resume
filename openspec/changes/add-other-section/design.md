## Context

「自我评价」「获奖经历」「证书」「语言能力」这类分区不对应教育、经历、项目、技能任何一个。当前解析器认不出它们（没有对应的关键词），于是那一段被当成普通内容并进上一个分区。

要加一个「其它」分区，绕不开一个语义决策：**「其它」里的内容长什么样？**

勘察时确认了三处「把专业技能当特例」的实现，它们决定了改动面：

| 位置 | 特例的语义 |
| --- | --- |
| `ResumePreview.vue` 的 `showFields` | 专业技能不渲染条目头整行——没有机构名、职位、时间，只剩内容行 |
| `ResumeEditor.vue` 的 `addEntry` | 专业技能分区没有「条目」这一层，整个分区就是一个条目，新增落在内容行上 |
| `structure.ts` 的三处 `kind !== 'skills'` | 专业技能不查缺机构名、缺职位、缺时间，也不查时间线顺序 |

三处本质是**同一个事实的三次重复**：专业技能分区在结构上没有条目头。

## Goals / Non-Goals

**Goals:**

- 「其它」分区存在，且不对应主分区的内容进得去
- 空「其它」不产生任何噪音（不报分区为空、不产生解析警告、不拉低置信度）
- 旧存档读得出来，且读出来不变

**Non-Goals:**

- 不给「其它」分区加条目头
- 不做「其它」内容的自动归类
- 不改四个主分区的任何行为

## Decisions

### 决策 1：「其它」与专业技能同构——只有内容行，没有条目头

「自我评价」是一段话、「获奖经历」是「2021 年度技术突破奖」这样的一行、「证书」是「英语六级 CET-6」这样的一行、「语言能力」是「英语：流利」这样的一行——**它们本来就该是一行行标签**，没有「属于哪家公司、什么职位、起止年月」的概念。

同构带来三个好处：

- 语义准确：不需要为「其它」发明一套字段措辞
- 改动面小：技能的三处特例变成「没有条目头的分区」这一个概念，判定集中在一处
- 纸面一致：「其它」和专业技能长得一样，用户不需要理解两套版式

代价：「获奖经历」的年份只能写在文字里（`2021 年度技术突破奖`），不能结构化成起止年月。可接受——这些内容本来就不是时间线。

### 决策 2：给「无条目头」这个概念一个明确的名字

现状是 `kind !== 'skills'` 硬编码在四个文件里。加第五个分区后，如果继续堆 `kind !== 'other'`，很快会变成四个 `!==`。

改成领域层的一个判定：

```ts
/** 这些分区在结构上没有条目头——它们整个分区就是内容行。 */
export const SECTIONS_WITHOUT_ITEM_HEAD: SectionKind[] = ['skills', 'other']
```

界面与诊断都问它，不再各自判断。

### 决策 3：空「其它」不产生任何噪音

三处要改：

| 位置 | 现状 | 改法 |
| --- | --- | --- |
| `structure.ts` 空分区规则 | 分区一条内容都没有就报一条 | 「其它」为空时不报 |
| `parseDraft.ts` 分区没识别到内容的警告 | 每个空分区一条警告 | 「其它」为空时不警告 |
| `parseDraft.ts` 置信度 | 填满 `SECTION_ORDER` 的每个分区才算 1 | 置信度只看**必填**分区（四个主分区） |

第三条是关键：置信度公式用 `SECTION_ORDER.length` 判定「全部填满」，加了可选分区之后**永远到不了 1**。所以要把「必填分区」与「全部分区」分开。

### 决策 4：删掉基于长度的「疑似表头」启发式

`improve-resume-recognition` 里的提示用的是「归一化后不超过 4 个字」判据，当时测出零误报。**扩充语料后发现那是个假象**：12 条 4 字普通要点——沟通良好、文档能力、责任心强、抗压能力、团队合作、逻辑清晰、主动积极、认真细致、吃苦耐劳、性格开朗、学习能力、执行力强——**12/12 全部被误判**。

原来的「不应提示」语料里最短的是 5 字（「抗压能力强」），4 字那一类根本没进去，所以零误报是语料缺失造成的巧合。

这类误报的代价还不只是吵：长度启发式若用来**路由**（把短行当成表头），会把后面整段内容搬走——「沟通良好」被当成表头，后面的所有要点都跟着跑到「其它」分区去。

因此：
- **删掉长度启发式**
- 提示改成报告事实：「这份简历有 N 段我们不确定属于哪个分区，放在『其它』里了」，列出是哪几段。零误报，因为报的是确实进了「其它」的东西

### 决策 5：表头识别靠显式清单，不靠猜

「其它」分区的表头用一份显式清单：自我评价、获奖经历、荣誉奖项、证书、语言能力、社团经历、志愿服务、个人评价、实习项目、校园经历、专业认证、培训经历，以及英文的 Personal Summary、Self Evaluation、Awards、Certificates、Profile、Publications、Volunteer Experience、Interests、Activities。

不靠启发式去猜「这行看起来像表头」——猜测的代价是把后面的内容搬走。

清单外的写法（没被识别成表头）仍然会被当成内容并进上一个分区。这是**已知限制**：显式清单需要随真实样本持续补充，但补充的成本是加一个词，不会误伤既有内容。

### 决策 6：版本生成为只为底稿里存在的分区生成

`generateVersion` 现在遍历 `SECTION_ORDER` 无条件为每个分区生成一个版本分区。加了可选的「其它」之后，老用户生成的版本会多出一个空的「其它」分区（渲染时被跳过，但 `version.sections.length` 从 4 变 5）。

改成只为底稿里存在的分区生成。

### 决策 7：旧存档不受影响

存档里分区 kind 是字符串原样存进 JSON，读回来时**不校验 kind**。所以：

- 旧存档（只有四个分区）读回来还是四个分区，不会报错也不会丢数据
- 新存档里的 `"kind": "other"` 原样读回
- 更老的存档走 v0 迁移，未知 kind 一律降级成「工作经历」——这个行为不变

`persistence.ts` 的分区种类表加上 `'other'`，让 v0 迁移也能保留它。

## Risks / Trade-offs

- **显式清单不完整时，未知的其它类表头仍会被并进上一个分区** → 接受。清单可以持续补充，补充成本低且不会误伤。这比启发式猜表头安全得多。
- **「其它」里的内容没有结构化的起止年月** → 接受。获奖经历这类内容本来就以文字形式呈现更自然。
- **「其它」与专业技能长得一样，用户可能困惑** → 分区标题不同（「其它」vs「专业技能」），且纸面上分区名是可见的。可接受。
- **「其它」分区默认出现在每一份简历上** → 纸面只渲染有内容的分区（`ResumePreview` 遍历实际分区），编辑页的分区目录也只列有内容的分区。空分区不会出现在用户眼前。

## Migration Plan

无数据迁移。旧存档读出来不变——四个分区，没有「其它」。

回滚策略：还原领域模型、解析器、诊断、界面四个地方的改动即可。存档里已有的 `"kind": "other"` 在回滚后会被 `toSectionKind` 降级成「工作经历」——这是可接受的降级，不会崩。

## Open Questions

- 「其它」分区的标题是否要更具体（比如「其它信息」）？目前用「其它」。
- 显式清单要覆盖到什么程度才够？需要真实样本。
