# 系统设计

把一份**需求澄清文档**变成一份**能照着开发的设计**。

输入是 `docs/clarifications/<kebab-case>.md`（由 `requirement-clarification` skill 产出）。
输出是 `docs/designs/<kebab-case>.md`——七个设计维度 + 一份能直接开工的任务清单。

**不改代码。** 设计的产物是文档；落地走 `/opsx:propose` → `/opsx:apply`。

---

## 与其它流程的关系

```
需求（产品侧，中文）
  → requirement-clarification  → docs/clarifications/<name>.md   （要不要做、做到多大）
  → system-design（本 skill）  → docs/designs/<name>.md          （怎么做、拆成哪些任务）
  → /opsx:propose              → openspec/changes/<name>/        （proposal + design + tasks + delta specs）
  → /opsx:apply                → 代码
```

**本 skill 与 `/opsx:propose` 的分工**：

| | 本 skill | `/opsx:propose` |
| --- | --- | --- |
| 产出 | 详细设计（七个维度） | proposal / design / tasks / delta specs |
| 粒度 | 讲清楚**怎么做**：数据怎么存、界面长什么样、测试怎么写 | 变成可归档的**规格** |
| 关系 | 设计文档是 propose 的**输入** | 吸收本设计的决策，拆成归档级 tasks |

本设计的**任务拆分**要写成能被 propose 的 `tasks.md` 直接吸收的粒度：每条任务一个可验证的行为，说得清「怎么算做完了」。

## 流程

### 第 1 步 · 读输入与现状

```bash
ls docs/clarifications/          # 找澄清文档
```

读澄清文档，然后**对照现状核实**——澄清文档可能与代码脱节了：

- `openspec/specs/<能力域>/spec.md` —— 现有行为基准，改动前先读
- `docs/api-contract.md` —— 冻结的契约
- `reference/project-map.md`（本 skill 自带）—— 改动落点速查、硬约束、冻结点、守卫清单

**清单**：澄清文档里的「功能范围」每一条，都要能在现状里找到落点。找不到落点的，要么现状已经做了（澄清文档过时），要么落点判断错了（澄清文档要改）。**先解决这个再往下走。**

### 第 2 步 · 判断设计的重量与范围

**重量**：照 AGENTS.md §2.0 那张表判——「改错了会怎样」。

| 重（本次七维全写） | 轻（只写动到的那几维 + 说明其余为何不涉及） |
| --- | --- |
| `packages/shared` 的引擎与领域类型 | 样式、布局、颜色 |
| 服务端接口、错误码、状态表 | 单页内的交互与文案 |
| 数据库、存档结构与迁移 | 单个组件的局部逻辑 |
| 前后端契约 | |

**范围**：七个维度不是七篇小作文。**只写动到的**；每写一维，先问「这一维真的被动到了吗」。不涉及的那几维，在文档里写一行「不涉及 + 为什么」，不留空白让人以为漏了。

### 第 3 步 · 逐维设计

下面每一维都给出**这个项目该怎么写**的判据。

---

#### 架构设计

回答：这件事**放在哪一层**、**数据怎么流**、**边界在哪**。

必答：

- **落点**：前端 / 共享包 / 服务端 / 存储，分别承担什么。画一条数据流（谁调谁、经过哪几跳）。
- **端口与实现**：要新增引擎能力吗？新增的话走 `ResumeEngines` / `JdAnalyzer` 这样的**端口**，规则与模型是两个实现（ADR-0005 §2），视图与状态层不感知差异。**不新增端口而是在调用点写 if** 是错的。
- **密钥与第三方**：要调模型吗？密钥只在服务端；简历正文发给第三方前要用户明确同意（`docs/privacy-conclusions.md` §5.1、`model_consent_at`）。
- **时间与可复现**：引擎的时间由 `EngineContext.now` 注入；输出可复现；ID 由 `IdSeed` 决定。
- **不编造**：生成类改动要说明如何守住「不新增底稿之外的实体与数字」。模型给的结论要核对。
- **快照语义**：改动会不会影响「底稿后续修改不回写旧版本」这条。
- **冻结点**：逐条查 `project-map.md` §5 的 F1–F10。撞上了在这里写清楚。

产出：**决策表**——每个决策写「选了什么 / 备选是什么 / 为什么选它 / 代价是什么」。备选与代价不许省，那是后来人质疑你的依据。

---

#### UI 设计

回答：用户看到什么、怎么操作、**长什么样**。

必答：

- **页面与纸面**：这是「一张纸 + 一栏侧栏」还是只有纸？改动落在纸面还是侧栏？版式是单栏经典形态（**不做双栏、侧边色块、头像、图标**）。
- **信息层级**：这块内容在页面的什么位置，用什么容器（`.page` / `.card-block` / `.stack` / `.inline-row`）。
- **交互态**：可编辑块、悬停、聚焦的标记（**编辑标记不得改变版式**）。预览与打印稿不得出现任何底色、虚线、外圈。
- **按钮**：这一屏有哪几个动作？分别属于主操作 / 次要动作 / 破坏性操作哪一层？**一个界面至多一个实心主色**。尺寸跟动作区走（页面动作区 small、对话框 default、落地页 large）。卡片内行内动作**带图标**。
- **状态**：空态、失败态、加载态各是什么。失败与空态的**文案从 `states.ts` 取**，不在视图里另写。每条失败要给下一步。「还没开始」与「做了但为空」要分开说。
- **视觉落点**：颜色/字号/圆角/间距一律走 `tokens.css` 的变量，**不写视觉字面量**，也不写 px 尺寸（几何尺寸除外）。要新增变量就写清变量名与分组。
- **用词**：界面显示「我的简历」「多 JD 版本」，**不出现「底稿」**。不出现禁用词（面试、笔试、八股、考点、题库、题目、刷题、真题、面经）。
- **响应式与无障碍**：窄屏怎么变（`domain/breakpoints.ts` 的四档）。图标按钮有可访问名称。焦点始终可见。

产出：界面改动较多的，画 ASCII 线框图；小的用「元素 → 行为 → 状态」表。

---

#### 前端设计

回答：Vue 这一侧**具体怎么实现**。

必答：

- **落点**：`views/`（页面级）、`components/`（可复用）、`stores/`（状态）、`api/`（接口调用）、`router/`、`styles/`。
- **状态归属**：这件事的状态放哪个 store？新增 store 还是加到现有 store？判据：跨页共享 → store；页面局部 → 组件内 `ref`。
- **数据流**：组件 → store → api 的单向链路。**组件不直接 fetch**（经 `api/` 层）。
- **纯函数边界**：内容变更（编辑、加行、删行）用 `engines/editing.ts` 的 `applyOp` 那样的**纯函数**——给定简历与一项操作，给出变更后的简历，**不就地修改传入对象**（AGENTS.md §5.4）。组件只负责纸面与反馈，**不读写全局状态**；是否保存、是否标记未保存由调用方决定。
- **错误处理**：接口失败怎么变成用户看得懂的话——经 `ApiError.state` 取 `states.ts` 的文案，不要自己拼。
- **路由与守卫**：新页面/新路由，守卫条件（`requiresDraft` / `requiresLogin`）、页头动作、离开时未保存拦截。
- **命令式组件**：消息提示、确认框走 Element Plus 的**完整样式**（不能只引组件代码漏掉样式）。
- **Element Plus 按需导入**：**禁止** `import { X } from 'element-plus'`。

产出：文件级改动清单——`新增/改动 文件路径 → 改什么 → 为什么`。

---

#### 后端设计

回答：服务端**具体怎么实现**。

必答：

- **端点**：方法、路径、鉴权、幂等性、请求体、响应体。**必须与 `docs/api-contract.md` 的形状一致**——不一致就是契约变更，要写清楚是「加字段」（兼容）还是「改语义」（不兼容，要走 `/api/v2`）。
- **错误码**：新增的失败场景用什么 `code`。码加到 `packages/shared/src/contracts/error-codes.ts`、加到 `docs/api-contract.md` §5、加到 `states.ts` 的状态条目——**三处一一对应**，守卫会断言。服务端只给 `code`，文案由前端映射。
- **幂等**：这个 POST 要不要 `Idempotency-Key`？要的话键怎么生成、服务端怎么记（`server/src/db/idempotency.ts`）。`POST /api/v1/jd/analyze` 是「同输入天然幂等」——按（用户、修订号、JD 哈希、模式）缓存，命中直接返回。
- **鉴权与数据归属**：谁能访问这份数据？跨用户访问怎么挡？
- **服务端权威**：客户端提交的结构化数据，服务端要重跑校验（结构检查、不变量），不能信客户端。
- **时间**：所有时间服务端给，客户端不传时间戳。
- **可观测**：`X-Request-Id` 贯穿；失败日志带请求 id；**不记录简历正文**（`docs/privacy-conclusions.md`）。
- **降级**：模型不可用时怎么办？回落规则引擎并标 `degraded` + 原因，**降级不是错误**（返回 201 而不是 503）。哪些错误该回落、哪些该 5xx，逐条写。

产出：端点表（方法/路径/鉴权/幂等/请求/响应/失败码）+ 装配改动（`app.ts` 的 `AppDeps`、路由注册、`index.ts` 的依赖装配）。

#### 数据库设计

回答：**数据怎么存、怎么迁**。

必答：

- **表结构**：Drizzle 定义（`server/src/db/schema.ts`）。新表/新列/新索引逐条写清字段、类型、约束、注释。
- **形状**：树形/半结构化的简历与版本正文用 **jsonb 存整份 payload**（现有 `drafts`、`versions` 就是这样；`drafts` 是结构化简历，`versions` 是快照），不要拆成关系表——拆了更复杂。**关系型查询需要的字段才单列**（如 `revision`、`jd_hash`、`mode`）。
- **索引**：按查询模式定。已算过的比对结果用**唯一索引**保证「同一把键只算一次」。
- **迁移**：新增 `server/src/db/migrations/00NN_xxx.sql`，进版本库能手工审；同步 `_journal.json`。SQL 进版本库，**不要只靠代码建表**。旧数据怎么兼容——新字段可空、有默认值、还是需要回填。回填脚本要不要写。
- **保留期与删除**：这份数据留多久？谁来删？按 `docs/privacy-conclusions.md` 的口径写。账号注销时连带删什么。
- **隐私**：存不存简历正文？发给过模型吗？

产出：表结构变更表 + 迁移说明（新增/回填/兼容策略）。

#### 测试设计

回答：**怎么证明它对**。

必答：

- **分层**：共享包纯函数与引擎 → 单元测试（node 环境）。服务端端点 → 路由用例 + 存储用例。组件与视图行为 → `@vue/test-utils`（jsdom，文件首行 `// @vitest-environment jsdom`）。全流程与静态不变量 → `frontend/src/flows.spec.ts`。
- **测试落点**：测试文件与被测文件同目录同名前缀 `Xxx.spec.ts`。
- **断言什么**：每条用例写成「行为 + 预期」，中文命名。**先写会失败的用例再实现**（bug 流程）或与实现同批提交（新功能）。
- **怎么算自动化、怎么算浏览器**：能断言的写「自动化验收」，颜色、悬停、版式、分页、打印稿只能浏览器验收。**不要写断言 CSS 字符串的用例**——那是给未来的人制造「改了样式测试也不报」的假安全感。
- **守卫影响**：这次改动会触发 `flows.spec.ts` / `repo-hygiene.spec.ts` 的哪些检查？新增界面就对照 `project-map.md` §7 的清单自查。
- **回归**：这次改动可能破坏哪些已有行为？列出要回归的用例（`docs/regression-cases.md` 的黄金路径与边界情况）。
- **数据构造**：测试数据在文件内用工厂函数构造，不共用跨文件夹具。

产出：测试矩阵——用例名 → 断言点 → 验收方式（自动化 / 浏览器）。

---

#### 开发任务拆分

把设计切成**能顺序执行的、每条可验证的**任务。

规则：

- **每条任务一个可验证的行为**，说得清「怎么算做完了」。不是「实现 X 模块」。
- **顺序按依赖**：共享包 → 服务端 → 存储 → 前端 → 用例 → 文档。共享包的类型先定，否则两端同时改会打架。
- **标注验收方式**：每条任务后标 `[自动化]` 或 `[浏览器]`。
- **标注阻塞**：哪些任务必须串行，哪些能并行（目录完全隔离的可以）。
- **带上门禁与归档**：最后要有「类型检查 + 全量测试 + 打乱顺序测试 + 构建全过」（`npm run verify`）与「浏览器走一遍黄金路径」。

产出：分组任务清单，格式与 `/opsx:propose` 的 `tasks.md` 一致（编号 + 一句话任务 + 验收方式）。

### 第 4 步 · 写文档

写到 `docs/designs/<kebab-case>.md`（目录不存在就建）。文件名用**字母开头**的 kebab-case，与澄清文档同名。

结构：

```markdown
# <需求名> · 系统设计

- 日期：YYYY-MM-DD
- 输入澄清文档：docs/clarifications/<name>.md
- 重量：重 / 轻
- 涉及维度：架构 / UI / 前端 / 后端 / 数据库 / 测试（列出实际写的，不写的写「不涉及 + 原因」）

## 0. 需求回指
（澄清文档的范围逐条 → 本设计的哪一节落地。对不上的写「本设计不覆盖，原因」）

## 1. 架构设计
### 1.1 落点与数据流
### 1.2 决策表
### 1.3 冻结点检查

## 2. UI 设计
### 2.1 页面结构与线框
### 2.2 交互态
### 2.3 动作与按钮
### 2.4 状态与文案
### 2.5 视觉落点（变量）
### 2.6 用词与响应式

## 3. 前端设计
### 3.1 落点与状态归属
### 3.2 数据流
### 3.3 文件级改动清单

## 4. 后端设计
### 4.1 端点表
### 4.2 错误码与状态
### 4.3 幂等与降级
### 4.4 装配改动

## 5. 数据库设计
### 5.1 表结构变更
### 5.2 索引与约束
### 5.3 迁移与兼容
### 5.4 保留期与隐私

## 6. 测试设计
### 6.1 用例矩阵
### 6.2 守卫影响
### 6.3 回归范围

## 7. 开发任务拆分
（分组任务清单，每条带验收方式）

## 8. 风险与未决问题
```

文档内部可以用「底稿」「版本」等内部术语，但**必须给出与界面用词的对照说明**（AGENTS.md §7）。不写禁用词。

### 第 5 步 · 交棒

聊天里给摘要：

- **一句话**：这件事怎么做（落在哪几层、数据怎么流）
- **关键决策**：三到五条，每条为什么
- **任务数**：多少条、哪些是浏览器验收
- **风险**：最该盯的一条

然后：

- 设计与范围都对得上 → 提示 `/opsx:propose <kebab-case>`，并说明**设计文档的哪些节可以直接进 propose 的 proposal（Why/What Changes）、design（Decisions）、tasks（任务清单）**。
- 澄清文档的范围在设计过程中变了 → **先改澄清文档**，再进 propose。设计过程中冒出来的范围变化不能悄悄带进去。
- 用户明确要落地 → 才建 OpenSpec 变更。

**关卡提示**：进 `/opsx:propose` 时，proposal.md 的 `## Why` 段开头要有 AGENTS.md §2.0.2 的三行。
本 skill 的产物填其中的「系统设计」一行（路径就是这份设计文档）；「澄清文档」一行是输入的那份澄清文档；
「重量」一行取第 2 步的结论。

三行长这样（需求流程、重量为「重」时）：

```
- 重量：重
- 澄清文档：docs/clarifications/<name>.md
- 系统设计：docs/designs/<name>.md
```

**填的路径必须真实存在**——守卫会检查。

## 护栏

- **不改代码。** 唯一产物是文档。
- **设计要覆盖澄清文档的范围，不许超范围。** 范围变化先回澄清文档。
- **每条决策有理由，理由指向约束**（spec / ADR / 契约 / 冻结点），不是「这样更好」。
- **决策要写备选与代价。** 只写结论的决策后来会被质疑，也没法改。
- **不写视觉字面量、不写 px 尺寸**（几何尺寸除外），设计里举例也要用变量名。
- **界面文案示例不得出现「底稿」或禁用词。** 设计文档里的示例文案是会被照抄进代码的。
- **错误码三处对应**：错误码表、契约文档、状态表——设计里说了新增就要三处都写。
- **不编数字。** 工作量、覆盖率这类没有来源的不写死，写依据或写「待估」。
- **测试断言行为，不断言 CSS 字符串。**
- **不替产品拍板。** 设计给出做法与代价，取舍由用户定；发现澄清文档的判断有问题就说出来。
