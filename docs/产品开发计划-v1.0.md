## 0. 读法

每个阶段固定七段式：

| 段 | 内容 |
| --- | --- |
| 1 | 阶段代号与命名 |
| 2 | 核心问题（一句话） |
| 3 | 交付范围 |
| 4 | 关键任务清单（每条对应一个可验收行为） |
| 5 | **验收条件**（分「自动化」与「浏览器」两类，不混排） |
| 6 | 依赖关系 |
| 7 | 人日粗估与假设、风险与「不做会怎样」 |

**验收条件为什么分两类**：`CLAUDE.md` §8 明确「CSS 的实际效果静态扫描测不到，不要在测试里断言某段 CSS 字符串存在——那是给未来的人制造『改了样式测试也不报』的假安全感，靠浏览器验收」。所以凡是能靠测试断言的（结构、字段、状态流转、不变量）走自动化；凡是效果层面的（颜色、悬停、分页、版式、PDF 文字层）走浏览器人工验收，逐条勾选。

**阶段与 OpenSpec 的关系**：每个阶段内部拆成 1 个或多个 OpenSpec 变更，目录名 `YYYY-MM-DD-<kebab-case-短述>`，每个变更含 `proposal.md / design.md / tasks.md` 与 delta specs。**一轮变更全部实现完再统一归档**，不要边做边归档（`CLAUDE.md` §2）。阶段顺序 = 变更合并进主干的顺序，不是时间承诺。

**路径说明**：P3 之前，引擎代码位于 `frontend/src/engines/`；P3 完成共享包抽取后该目录迁入共享包，本文档 P4 及之后提到的 `engines/` 路径均指共享包。

## 1. 目标与非目标

### 1.1 v1.0 要达成的产品状态

一个真实可对外发布的简历产品：用户注册后放入一份简历，可以先看这份稿本身的问题，再粘贴 JD 得到一版定向简历，导出成能直接投递的 A4 PDF。数据存在服务端，跟着账号走。

### 1.2 v1.0 明确不做

- 长期「刷题」方向的任何交互、入口与文案（PRD §1 明确不为以后的题目预留交互或文案）
- 多份底稿 / 简历库 / 中英文分稿（PRD §3、§4）
- Word、图片、在线表格的简历摄入；**扫描件 OCR**（见 P1 说明，列为 v1.1 候选）
- JD 链接抓取（PRD §4）
- 模板市场、双栏版式、还原原 PDF 版式、头像/图标/侧边色块（PRD §7.5）
- 协作、分享链接、团队空间（PRD §4）
- 个人设置页、资料设置（PRD §4）
- 完整 WCAG 审计、移动端专属布局（见 P2 边界）
- 服务端多副本 / K8s / 微服务拆分

## 5. P1 · 摄入闭环

**核心问题**：PRD §7.1/§9 第 2 条要求「上传 PDF，尽力解析；解析失败时把已得到的文本交给用户修改」——这是当前唯一一处 spec 与实现的实质落差。

### 5.1 交付范围

- 新建能力域 `pdf-intake`；`resume-draft` 增补「上传路径」要求
- `frontend/src/views/ImportView.vue` 的「上传文件」页签从占位改为真实入口（拖拽 + 点选 + 校验 + 解析中态 + 结果区）
- 新增引擎模块 `frontend/src/engines/pdfText.ts`（**不放进 `ResumeEngines`**，理由见 §12.1）
- 新依赖 `pdfjs-dist`（前端），worker 走 Vite `?url` 打包
- 复用既有能力：`engines/parseDraft.ts`、导入页既有的纸面可编辑与低置信度提示

### 5.2 关键任务

| 编号 | 任务 | 产出的可验收行为 |
| --- | --- | --- |
| T1.1 | `extractPdfText(file)`：pdf.js 取每页 text items，按 y 聚合成行、按 x 间隙判列、跨 text item 合并断字 | 有文字层的 PDF 能抽出可读文本且行序正确 |
| T1.2 | 质量闸门三态：`text-layer` / `sparse`（每页字符密度过低，疑似扫描件或图片页）/ `none`（无文字层）。阈值写成常量并注明理由 | 三态可判定，阈值可调 |
| T1.3 | 三态对应文案与出路：`text-layer` 直接进解析；`sparse` **仍把已提取到的文本交给用户**并明确提示；`none` 明确告知无文字层并一键切到「粘贴文本」页签且聚焦输入框 | PRD §9 第 2 条的「不能解析时仍能改完并保存」落地 |
| T1.4 | 文件校验：仅 `application/pdf`、大小上限（10MB）、页数上限（50 页）；加密 PDF、损坏 PDF、非 PDF、超大文件各自一句可执行文案 | 四类异常各自有明确出路，不白屏 |
| T1.5 | 解析失败兜底链路：提取成功但结构解析失败时，与粘贴路径共用同一失败态与「在纸上改」路径 | 不要求用户重新整理版式（PRD 原文） |
| T1.6 | 解析期间禁止重复提交；大文件解析不卡 UI（worker 或分帧处理） | 解析中界面不冻结 |
| T1.7 | 补一份带文字层的可上传样例 PDF 进 `mock/`，供人工验收与回归 | 验收有固定样本 |
| T1.8 | `ImportView.spec.ts` 增补上传路径用例；守卫增补：`ImportView.vue` 不得再出现「原型阶段暂不支持 PDF 解析」类占位文案 | 占位实现不可复发 |

## 8. P4 · 可信生成

**核心问题**：把「不编造」从「逐字比对」升级为「每一条输出断言都能指回底稿里的某条事实」，然后才允许换掉规则引擎。

### 8.1 交付范围

- 能力域：`jd-version-generation`（重写「不编造」要求）、`resume-preview-and-export`（版本结构新增溯源字段）；新建 `fact-traceability`、`llm-engine`
- 引擎：新增共享包中的 `ledger.ts`（事实账本 / 声明账本）；重写 `transforms.ts` 的 `assertNoFactsAdded` → `verifyClaims`（**语义替换，不是叠加**）；新增 LLM 适配器实现同一 `ResumeEngines` 接口
- 版本结构：`ResumeVersion` 新增 `facts`/`claims` 段；`integrity` 字段语义从「逐字违规」改为「声明级判定 + 处置」

### 8.2 关键任务

| 编号 | 任务 | 产出的可验收行为 |
| --- | --- | --- |
| T4.1 | **事实账本**：把底稿拆成不可再分的 fact（动作 + 对象 + 度量 + 实体 + 时间），每个 fact 带 `factId` 与原文 span；抽取必须确定性（可复现要求） | 同一底稿两次解析出的 fact 集合全等 |
| T4.2 | **声明账本**：输出每条 bullet 拆成 claim，每个 claim 带 `sourceFactIds` + `operation`（保留/改写/合并/删除）+ 置信度。**先用现有规则引擎当第一个 claim 生产者** | 规则引擎产出的版本带 claim |
| T4.3 | 判定规则：claim 中每个数字/实体/度量必须能在其引用的 fact 中找到；无引用或引用不足 → 不可信 → 回退到源句（沿用现有 `integrity.violations` 的回退语义与呈现位置） | 编造内容一定被回退 |
| T4.4 | 合并/拆分类 claim：一条输出 claim 引用多条 fact 时逐 fact 校验，任一不可信则整条回退（**先严后松**） | 合并类输出同样受检 |
| T4.5 | LLM 适配器：实现同一 `ResumeEngines` 接口；密钥只在服务端；请求失败/超时/拒答 → **回落规则引擎产出**（降级而非报错），并在版本上标注「本次为降级生成」 | 模型不可用时功能不中断 |
| T4.6 | 引擎模式开关真正接线 `VITE_ENGINE_MODE`（兑现 P0 的 ADR）；`mock`/`remote` 双跑可比对 | 可一键切换引擎 |
| T4.7 | 回归基线：固定一组「底稿 + JD」样本，两个引擎各跑 N 次，产出差异报告（覆盖率分布、声明数、被回退条数、耗时、token） | 有量化对比依据 |
| T4.8 | 幂等与可复现：同输入同输出对 LLM 引擎**降级为「输出可审计」**——此项需显式修改 spec，不能默默破坏既有「可复现」要求 | spec 与实现不冲突 |

## 12. 关键判断

### 12.1 PDF 解析放前端，不等后端；扫描件做诚实降级，不做 OCR

**结论：前端做（pdf.js 提取文字层），长期形态就是前端。**

理由按权重排序：

1. **兜底路径天然属于前端**。PRD §9 第 2 条要求「不能解析时，用户仍能在文本上改完并保存」——「在文本上改」是导入页的纸面编辑能力，已存在且已测试。前端解析可直接复用；后端解析失败后必须把文本再传回前端，多一次往返。
2. **不破坏匿名可用**。`account-access` spec 明写导入页可匿名使用（粘贴、解析、纸上改都不问身份）。后端解析会强迫「先上传后解析」，与该 spec 冲突。
3. **PII 最小暴露**。简历正文不出本机即可完成摄入；只有用户主动「保存」才出本机。
4. **技术成本差异小**。`pdfjs-dist` 在 Node 端同样可用，真正的差别在上面三条。

**扫描件（无文字层）**：提取后按页统计字符密度分三态。

- `sparse`：**仍把已提取到的文本交给用户**（PRD 原文「把已得到的文本交给用户修改」），并明确提示「这份 PDF 能读到的文字很少，可能是扫描件或图片页」。用户看到的是部分真实文本 + 明确警告，比空白页有用。
- `none`：明确告知「没有可读取的文字层」，一键跳到粘贴文本并聚焦输入框。
- **不做 OCR 的理由**：需要额外依赖（体积大、中文识别质量不稳、服务端算力成本），而 PRD 只要求「尽力解析」而非「识别一切」。列为 v1.1 候选。
- **但接口要预留**：`extractPdfText` 返回 `{ text, pageCount, quality, warnings }`，将来加 OCR 只是新增 `quality: 'ocr'` 与一条管线，调用方不变。

### 12.2 「不编造」校验重设计是服务端化的**前置**，不是产物

现有校验（`transforms.ts` 的 `assertNoFactsAdded`）成立的前提是：规则引擎只做机械变换（去符号、规范化、动词前置），所以「输出字符串的数字/拉丁词/CJK 字必须逐字来自原句」可以当作等价的真实性检查。LLM 会重写整句、合并要点、换措辞 → 逐字比对会把「改写措辞」全部误判为编造。**旧校验不能直接用于 LLM，必须重设计。**

新模型：

- 底稿侧 **fact** = 不可再分的最小事实单元（动作 + 对象 + 度量 + 实体 + 时间），带 `factId` 与原文 span，抽取必须确定性。
- 输出侧 **claim** = 输出 bullet 拆成的断言，带 `sourceFactIds` + `operation` + 置信度。
- 判定：claim 中每个数字/实体/度量必须能在其引用的 fact 中找到；无引用或引用不足 → 不可信 → 回退到源句。合并类 claim 逐 fact 校验，任一不可信则整条回退（先严后松）。

**时序关键点**：P3 会把 `ResumeVersion` 的 schema 定死。若账本模型要往里加 `facts`/`claims` 段，**必须在 P3 定 schema 时预留扩展位**（F3）。所以校验器的**设计**必须早于 P3 收尾，**代码**在 P4。

落地顺序：先用**现有规则引擎**产出带 claim 的版本（规则引擎天然就是第一个 claim 生产者）→ 校验器上线并与旧校验做差异比对 → 不误伤率 100% → 再接 LLM。**先有校验器，后有 LLM。**

### 12.3 服务端化在先，引擎升级在后

- **为什么服务端化在先**：LLM 生成最终一定在服务端（密钥不能进浏览器）。若先升级引擎、后服务端化 → 生成逻辑要搬一次，且搬的过程中「引擎实现」与「存储/鉴权」同时在变，故障定位面翻倍。先服务端化（用规则引擎跑通全链路）→ 后引擎升级只是替换服务端的一个实现类，**前端零改动、API 零改动**。
- **为什么不并行合主干**：同一仓库、同一分支模型，历史节奏是 32 变更/4 天的高吞吐小步快跑；两个大分支并行会持续撞 `domain/types.ts`、`stores/`、`engines/types.ts` 三个共享文件，合并成本高于串行。
- **可并行的**：见 §3 的并行窗口表。

### 12.4 组件拆分不单独成阶段，并入 P2，且先于 P3/P4 的前端改动

- **不单独成阶段**：无用户可感知价值，单独一个「重构阶段」会让团队在无交付的日子里失去正反馈；纯机械工作，收益不依赖任何上下文，早做晚做结果一样，但晚做一定更贵。
- **必须先于 P3/P4**：P1 的兜底编辑、P3 的账号态、P4 的版本溯源展示都会改 `ResumeEditor`/`CommentSidebar`/`DraftView`。
- **拆分边界只抽两个，避免过度抽象**：`ProfileHeader.vue`（姓名/定位/联系方式/增删联系方式）、`ItemHeader.vue`（公司/职位/起止日期/至今/条目删除）。`ResumeEditor.vue` 保留纸面编排、事件编排、键盘流。
- **验收不绑行数**：行数是观测指标，写进任务描述作为目标值（ResumeEditor < 450、CommentSidebar < 350），**不作为通过门槛**。验收条件是「抬头区与条目头成为独立组件 + `ResumeEditor.spec.ts` 现有 43 个用例语义不变全部通过 + 键盘流 6 项行为不变」。

## 14. 全局估算与假设

**人日口径**：以「一名熟悉本仓库的高级前端工程师」为基准；不熟悉本仓库的开发者按 1.3–1.5 倍计。历史节奏为 32 次 OpenSpec 变更 / 4 天，但那些多为单点小改；本计划含服务端新建、契约设计与合规工作，**按历史速率的 40%–50% 折算**。估算包含实现、自测、代码审查与修一轮；**不包含**产品需求澄清轮次、法务正式意见、外部安全渗透测试、新视觉设计。

| 阶段 | P0 | P1 | P2 | P3 | P4 | P5 | P6 | 合计 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 人日 | 0.5（已投入 1.5） | 4 | 8 | 12 | 12 | 7 | 4 | **47.5**（已投入 48.5） |

- 单人：约 10 周；2 人（1 前端 + 1 全栈）：约 **6–7 周**（扣除并行窗口后约 5.5 周）。
- 不确定性最大的是 **P3 与 P4**（各 ±40%）：P3 波动来自账号形态与部署环境，P4 来自 LLM 输出质量与校验器不误伤率。

**其他假设**

- 部署环境：单容器 + 单实例数据库 + 对象存储；域名与证书现成。
- 模型供应商：有可用的服务端调用通道与预算上限；输出长度可控。
- 隐私合规：按通行模板起草 + 一次外部快速审阅；不假设有完整法务流程。
- 存量用户：原型阶段数据量小，迁移失败可接受「重录」。
- 无专职 QA / 设计 / PM：验收由开发自测 + 一轮交叉走查承担。
