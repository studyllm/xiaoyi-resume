# 运维手册（runbook）

服务端出问题时照着做。**每一条都写了「怎么确认」和「做完怎么验证」**——照着做不需要临场判断。

- **怎么部署**、**怎么回滚**、**数据坏了怎么办**、**简历内容泄露了怎么办**
- 备份与恢复的演练流程在最后一节。**没演练过的备份不算备份。**

相关文档：`docs/backend-stack.md`（技术栈与目录）、`docs/privacy-conclusions.md`（数据口径与保留期）。

---

## 1. 部署

### 1.1 环境变量

服务端缺哪个变量就直接退出（半套配置跑起来的服务端比不启动更糟）。清单在 `server/.env.example`：

| 变量 | 说明 |
| --- | --- |
| `DATABASE_URL` | Postgres 连接串 |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_SECURE` / `SMTP_USER` / `SMTP_PASS` | 邮件服务商的 SMTP |
| `MAIL_FROM` | 发信人地址 |
| `SITE_URL` | 站点对外地址。验证与重置链接指向它，**配错会让用户点不开邮件里的链接** |
| `HOST` / `PORT` | 监听地址与端口 |

### 1.2 顺序

```bash
npm ci                                     # 仓库根
npm run db:migrate                         # 迁移 SQL（先迁移再切流量）
npm --workspace server run build           # 有构建步骤时
# 重启服务
```

**迁移要先于新代码上线。** 新代码依赖新列时，旧代码还在跑，迁移加了列不影响它；反过来（旧代码 + 新表）会直接报错。

### 1.3 部署后确认

```bash
curl -s localhost:3000/api/v1/healthz    # {"ok":true}
```

然后人工过一遍：注册 → 验证邮件 → 登录 → 存草稿 → 生成版本 → 打开版本详情。**账号与版本是两条独立的链路，healthz 只证明进程活着。**

## 2. 回滚

### 2.1 回滚代码

```bash
git checkout <上一个 good commit>
npm ci && npm run build && 重启
```

**不要回滚迁移。** 数据库迁移只向前：多出来的列旧代码看不见（无害），删掉的列旧代码会报错（有害）。

### 2.2 回滚数据

只在数据被写坏时做（见第 4 节）。走恢复流程，**恢复前先给当前库拍一份快照**——恢复本身也会覆盖。

## 3. 监控

| 看什么 | 怎么看 | 异常时 |
| --- | --- | --- |
| 进程活着 | `GET /api/v1/healthz` | 看第 5 节 |
| 错误率 | 日志里 `msg: "请求出错"` 的条数 | 看错误里的 `requestId` |
| 请求 id | 每条日志都有 `requestId`，也在响应头 `x-request-id` 里 | 用户报错时让他们报这个编号 |
| 数据库 | 每日巡检脚本（见下） | 磁盘 < 20% 就清日志与旧备份 |
| 备份 | 巡检脚本会查「最近一次备份距今多久」 | 见第 6 节 |

### 3.1 巡检脚本

```bash
DATABASE_URL=... ALERT_EMAIL=... SMTP_*=... S3_BUCKET=... npm --workspace server run check
```

查四样：服务端活着吗、数据库连得上吗（连接数与体积）、磁盘还剩多少、**最近一次备份距今多久**（超过 26 小时就算没备份）。

**有问题就发邮件给 `ALERT_EMAIL`，没有就安静退出。** 邮件用服务端自己那套 SMTP 配置发——不另开通道，密钥只有一份。没配 `ALERT_EMAIL` 时告警只打在日志里。

建议挂到 cron，每天一次：

```
17 9 * * * cd /path/to/repo && /usr/bin/npm --workspace server run check >> /var/log/xiaoyi-check.log 2>&1
```

**收告警的邮箱要有人看。** 没人看的告警等于没有告警。

**日志里没有简历正文。** 需要定位某次请求时按 `requestId` 找，不要去数据库里翻正文。

## 4. 数据坏了怎么办

### 4.1 先分清是「数据坏了」还是「读不出来」

```sql
-- 用户说「我的简历没了」
select count(*) from users where email = 'someone@example.com';
select count(*) from drafts;
```

- 用户在、简历在 → 不是数据问题，是会话或前端的问题，看第 5 节
- 用户在、简历不在 → 可能被误删，走 4.2
- 用户不在 → 账号被删过，查审计日志

### 4.2 恢复单个用户的数据

整库恢复会把别的用户的数据一起盖回去——**除非确认库里只有这一个用户，否则不要整库恢复**。

```bash
# 1. 先给当前库拍一份快照
./scripts/backup.sh

# 2. 恢复到临时库，人工核对
TARGET_URL=postgres://.../xiaoyi_restore ./scripts/restore.sh <备份名>
psql postgres://.../xiaoyi_restore -c "select email, count(*) from users group by email;"

# 3. 核对无误后，把这一个用户的数据搬回去
psql postgres://.../xiaoyi -c "insert into users select * from xiaoyi_restore.users where email='...';"
```

**逐条搬，不要整库覆盖。** 恢复脚本里的 `pg_restore --clean` 会先删表——那是给演练用的，不是给线上抢数据用的。

## 5. 故障处置

### 5.1 登录不了

| 现象 | 大概率原因 | 怎么办 |
| --- | --- | --- |
| 提示「邮箱或密码不对」，但密码没错 | 邮箱大小写或前后空格 | 邮箱入库前已规范化（trim + 小写），让用户按小写输 |
| 提示「邮箱还没验证」 | 验证邮件没到 | 看 5.2 |
| 点了验证链接说「令牌无效」 | 令牌超过 24 小时，或已用过 | 重新发一封 |
| 服务端 500，日志里 `err.message` 是 `connect ECONNREFUSED` | 数据库连不上 | `docker compose ps` / 看数据库是不是挂了 |

### 5.2 验证邮件收不到

1. 看发信记录：日志里 `POST /api/v1/auth/register` 的 201 ✓ 说明信发出去了
2. 看邮件服务商的投递结果（拒信、延迟、退信）
3. **检查 `SITE_URL`**——链接指向它，配错的话用户点开是 404，而且链接里的令牌是好的，排查起来容易误判成「令牌失效」

### 5.3 保存简历失败

| 用户看到的 | 原因 | 怎么办 |
| --- | --- | --- |
| 「现在连不上服务器，改动还在这个页面上」 | 服务端不可达 | 恢复后重试。**改动没丢**——它在页面上 |
| 「简历在别处被改过」 | 修订号对不上（`DRAFT_REVISION_CONFLICT`） | 刷新看别人的改动，或用自己这份覆盖 |
| 「出了点问题」 | 服务端 500 | 按 `requestId` 查日志 |

### 5.4 生成版本失败

| 用户看到的 | 原因 |
| --- | --- |
| 「生成失败」 | 引擎抛错。按 `requestId` 查日志里的 `err` |
| 「JD 解析失败」 | 那段 JD 里认不出岗位要求，让用户检查是不是复制完整了 |
| 「模型服务暂时用不了」 | 模型不可用且回落也失败——回落路径是规则引擎，它失败说明引擎本身有问题 |

## 6. 备份与恢复

### 6.1 每晚的备份

```bash
DATABASE_URL=... S3_BUCKET=... AGE_RECIPIENT=... ./scripts/backup.sh
```

流程：`pg_dump` → **用 age 公钥加密** → 传对象存储 → 删本地副本。

**备份密钥与备份分开存放。** 备份拿到手也解不开，才叫加密——放在同一个桶里等于没加密。

### 6.2 每月演练一次

```bash
# 恢复到一个临时库
TARGET_URL=postgres://.../xiaoyi_restore ./scripts/restore.sh <最新的备份名>

# 核对：条数对得上吗？内容对得上吗？
psql postgres://.../xiaoyi_restore -c "select count(*) from users;"
psql postgres://.../xiaoyi_restore -c "select count(*) from versions;"

# 演练完把临时库删掉
```

**演练的产出记在下面那张表里。** 没演练过的备份不算备份。

| 月份 | 演练人 | 备份名 | 用户条数 | 版本条数 | 结论 |
| --- | --- | --- | --- | --- | --- |
| | | | | | |

### 6.3 恢复

见第 4.2 节。**恢复脚本里的 `--clean` 会先删表**，只用于演练与整库灾难恢复。

## 7. 简历内容泄露了

**这是最坏的一种事故**，照着走：

### 7.1 立刻（分钟级）

1. **切断入口**：把服务停掉，或在入口加一层只允许内网访问。泄露还在继续的话，先止住。
2. **换密钥**：数据库密码、`SMTP_PASS`、`AGE_RECIPIENT`（重新生成一对 age 密钥，**旧的作废**）。
3. **查范围**：审计日志里看这段时间有哪些账号被访问过、有哪些版本被下载过。

```sql
-- 谁在什么时候登录过
select user_id, created_at from sessions order by created_at desc limit 100;
-- 哪些版本被读过（如果服务端留了访问日志）
```

### 7.2 判定范围

| 泄露了什么 | 通知范围 |
| --- | --- |
| 只有邮箱 | 受影响账号的用户 |
| 邮箱 + 简历正文 | 受影响账号的用户 |
| 简历正文（不含账号） | 全体用户——因为不知道是谁的 |

### 7.3 通知

按合同与法律要求的时间线通知。通知里要有：泄露了什么、可能造成什么影响、用户该做什么（换密码、重新导��简历）、以及我们做了什么。

### 7.4 补救

1. 强制所有账号改密码（`users` 加一个 `must_change_password`）
2. 作废所有会话——**这一条能立刻止血**
3. 如果备份也泄露了（密钥同源），**所有数据都算泄露**，范围按全体用户算
4. 复盘：泄露面是怎么开的。写进 `docs/decision-log.md`

### 7.5 预防

这条剧本存在的理由，是下面几件必须一直成立：

- **日志里没有简历正文**——日志的可见范围远大于数据库
- **备份用 age 加密，密钥与备份分开存**
- **静态资源与接口同源**，别让第三方脚本读到会话 cookie
- **数据库只允许服务端访问**，不暴露在公网
