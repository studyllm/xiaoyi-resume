# 界面文案语气与用词

这份文档管的是**怎么说话**，不管说了什么。具体每一条状态说什么，见 `error-taxonomy.md`。

规范来源：`openspec/specs/resume-terminology/spec.md`（用词）、`openspec/specs/product-visual-language/spec.md`（视觉与语气）。本文件是对那些规格在文案层面的补充。

---

## 1. 三条基本要求

| 要求 | 含义 | 反例 |
| --- | --- | --- |
| **说清后果** | 告诉用户会发生什么、会失去什么 | 「确定吗？」 |
| **给得出路** | 失败了要说用户现在能做什么 | 「解析失败」 |
| **区分状态** | 「没开始」「做完了但为空」「有但被筛掉了」是三件事 | 「没有符合条件的批注」 |

---

## 2. 语气

### 2.1 用陈述句，不用反问

反问把判断的责任推回给用户，还占掉一次阅读。

- ✗ 「确定要删除这个版本吗？」
- ✓ 「删除这个版本？简历和其它版本不受影响。」

破坏性确认的正文直接说清后果，标题用问句（那是问句该待的地方），正文不用。

### 2.2 短

状态反馈一行读完。超过两行说明信息没想清楚——拆成标题与说明两栏，或者砍掉一半。

### 2.3 说「你」不说「您」

产品面向的是求职者，不是采购。全文统一用「你」。

### 2.4 不替用户下结论

诊断意见只说「这里缺什么」，不说「你应该」。「可以」「建议」这类词留给确实在给建议的地方（诊断意见本身就是建议，那里用「建议怎么改」）。

### 2.5 肯定句优先

能说「这份简历已经能被解析」，就别说「没能解析出这份简历」——除了失败本身必须用否定表述的地方。

## 3. 用词

### 3.1 界面不出现内部术语

| 内部说法 | 界面显示 |
| --- | --- |
| 底稿 | 我的简历 |
| 版本（导航与页面标题） | 多 JD 版本 |
| 版本（句子与按钮） | 版本 |

「底稿」两个字在界面模板与引擎产出的用户可见文案里都不允许出现，由 `flows.spec.ts` 扫描。

### 3.2 禁用词

面试、笔试、八股、考点、题库、题目、刷题、真题、面经——这些词不进界面，也不进引擎输出。词表在 `frontend/src/engines/forbidden.ts`。

### 3.3 说用户懂的话

| 别说 | 说 |
| --- | --- |
| 置信度不足 | 结构识别不完整，请确认后再保存 |
| 启发式推断出的分区 | 按推断认出来的分区 |
| 反序列化 | 读不出来 |
| 校验失败 | 没认出来 |

「置信度」这个词现在还留在导入页的标签上（`置信度 82%`）。那是给想看的人看的诊断信息，不是失败提示，暂时保留。

## 4. 空状态的三层

```
标题    现在是什么状态。短句。
说明    为什么是空的，以及接下来能做什么。
主动作  点了就能改变这件事的动作。
```

**标题与说明不能是同一句话。** 挤成一句的结果是用户分不清现在是缺东西还是没认出来。

**有主动作时，标题与说明要互补，不能各说各的。**

- ✗ 标题「还没有简历」/ 说明「还没有简历」/ 按钮「去导入简历」
- ✓ 标题「还没有简历」/ 说明「导入一份简历后，就能编辑、诊断，并按岗位生成版本。」/ 按钮「去导入简历」

**没有主动作时，说明里讲清为什么没有。** 不要放一个点了也没用的按钮。

### 4.1 正向的空结果照样分层

「没有可对照的改动」「要求都能找到对应事实」是好结果。它们照样有标题和说明，只是没有动作——没有要纠正的事，也就没有该点的按钮。

### 4.2 位置决定尺寸

按钮尺寸跟动作区走，不跟语义走（见 `AGENTS.md` §4.6）：

| 位置 | 尺寸 |
| --- | --- |
| 页面级空状态 | default |
| 侧栏空状态 | small |

## 5. 失败提示

失败提示 = **状态 + 下一步**。两样都要有。

- ✗ 「解析失败」
- ✗ 「解析失败，请检查简历内容后重试」——「请检查」没有告诉用户该检查什么
- ✓ 「解析失败：没能从这段文字里认出简历结构，换一种带「教育背景」「工作经历」这类分区标题的写法再试一次。」

消息提示（`ElMessage`）用一整句话；页面里的告警（`el-alert`）拆成标题与说明两栏，两边用同一份文案。

---

## 6. 状态文案放在哪

状态文案集中在 `frontend/src/domain/states.ts`。视图、组件、布局里不写失败与空态的字面文案——守卫会扫，命中就红。

| 要写的东西 | 放哪 |
| --- | --- |
| 失败、空态、警告 | `domain/states.ts` 的三张表 |
| 成功提示 | 就在视图里写，它没有「下一步」的问题 |
| 破坏性确认 | `ElMessageBox.confirm` 的正文，直接说后果 |
| 引擎产出的业务内容 | 引擎自己的文案，受禁用词与内部术语守卫约束 |

---

## 7. 自查

写完一句界面文案，问三个问题：

1. 用户看到这句，知道现在是什么状态吗？
2. 用户看到这句，知道接下来该做什么吗？
3. 同一个意思在别处是不是另一种说法？

第 3 条最容易漏——写的时候顺手在另一个视图里又敲了一遍同样意思的话，界面就出现了两套说法。守卫管得住失败与空态的说法，**业务文案的一致性只能靠人看**。
