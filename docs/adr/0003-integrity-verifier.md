# ADR-0003：事实账本与校验器

- **状态**：已接受
- **日期**：2026-11-04
- **相关变更**：P4 首个实现变更（待建）

## 背景

### 现在的校验是什么

生成路径上，规则引擎改写每条要点后调用 `assertNoFactsAdded(source, output, { metadata })`（`frontend/src/engines/transforms.ts`），返回一组字符串违规。它检查五件事：

| 检查 | 口径 |
| --- | --- |
| 数字 | 输出的每个数字必须在原句或条目元数据里出现过 |
| 拉丁名词 | 输出的每个拉丁词（长度 ≥ 2）必须在原句或元数据里出现过 |
| 中文字符 | 输出的每个汉字必须在原句里出现过 |
| 中文长度 | 输出比原句长不超过 4 个字 |
| 评级词 | `精通 / 专家 / 资深专家 / 大师` 不许凭空出现 |

判定失败就**整条回退**到原句，并记进 `IntegrityReport { checked, violations }`。

### 三个不足

**1. 粒度太粗。** `source` 是**整条要点**。一条要点里的所有成分被当成一个整体——引用了一条要点，就等于「这条要点里的任何成分都能被支撑」。输出里混进了别处的数字，只要这条要点里没有，就是违规；但如果这条要点里恰好有那个数字，来源对不对就分不出来了。**更严重的是反向**：一条要点里出现了某个数字，输出在**另一条**要点里用上它，当前口径认为合法（因为只要在「这条要点」里就行——不对，等等，当前口径的 source 就是那一条要点，所以跨要点挪用其实是被抓的）。真正的问题是合并：一条输出要点由两条源要点合成时，两条的内容被混在一个 source 里，来源分不清。

**2. 动词强度没有真正判定。** 诊断侧的规则目录里有 `verb-strength-up`（"把「参与」写成「负责」或「主导」"），但**生成侧没有强制**。现在靠中文字符检查兜底——「参与」与「负责」不共用汉字，所以会被拦，但理由是"出现了原句中没有的字"，不是"职责被上调"。而且只要要点别处出现过「负」或「责」字，这个拦截就失效了。

**3. 表达的是「逐字违规」，不是「声明级判定」。** PRD 承诺的是「不得新增不存在的**公司、项目、职责或数字**」——四类。当前口径用的是「不许出现新汉字」这条更强的规则，它恰好覆盖了这四类，但代价是：**任何措辞改动都会被拦**。规则引擎的改写因此被限制在「重排已有字符」（`负责X的开发` → `X`），这是有意为之，但也说明当前口径无法区分「合法改写」与「语义编造」。

### P4 要什么

P4 要把引擎换成 LLM。LLM 会做**语义改写**与**合并重组**——「负责支付宝对接」改成「负责微信支付对接」，当前口径抓得住（汉字不同）；「前端开发」改成「前端工程」，当前口径也拦得住，但那是**误伤**——合法改写被当成编造。

**结论：当前口径对 LLM 太严，对真正的语义编造又不够准。** 需要换一套判定口径：不再是「不许有新字」，而是「不许有新**事实**」。

## 决策

### 1. 五类成分：判定只认事实，不认措辞

一条文本里的成分分五类，**只有前四类参与硬判定**：

| kind | 是什么 | 例子 | 硬判定 |
| --- | --- | --- | --- |
| `measure` | 数字 + 单位/修饰 | `30%`、`120s`、`18s`、`3.7` | ✓ |
| `entity` | 拉丁词与专名 | `Vue 3`、`React`、`K8s`、`CI/CD` | ✓ |
| `rating` | 技能评级词 | `了解 / 熟悉 / 掌握 / 精通 / 专家` | ✓ |
| `verb` | 职责动词 | `参与 / 负责 / 主导` | ✓ |
| `term` | 中文实词 | `前端开发`、`容器编排` | ✗ 只记录 |

`term` 不硬判，理由是确定性的词级规则分不清「合法改写」与「语义编造」——「前端开发 → 前端工程」和「支付宝 → 微信支付」在字符层面长得一样。**这是本 ADR 承认的边界，见第 8 节。**

### 2. fact：底稿要点切出的子句

**fact = 一条底稿要点按句读切分后的一个子句**，加上从它确定性抽出的成分集合。

```ts
interface Fact {
  /** 内容的哈希。同一份底稿两次抽出的 fact 集合全等，且跨版本可对照 */
  factId: string
  /** 子句原文 */
  text: string
  /** 在底稿要点正文里的字符区间 */
  span: { start: number; end: number }
  components: FactComponent[]
}

interface FactComponent {
  kind: 'measure' | 'entity' | 'rating' | 'verb' | 'term'
  text: string
  /** 只对 kind === 'verb'：动词强度序上的位次 */
  strength?: number
}
```

**切分点**：句号、分号、逗号、顿号，以及连接词「并 / 、 / 同时 / 另外」。切得太粗则引用过宽（回到当前口径的毛病），切得太细则 claim 数量爆炸、生成器负担重。子句级是这两者的折中。

**抽取必须确定性**：纯规则，不含随机、不读系统时间、不依赖词频统计。`factId` 取子句内容的哈希，因此**同一底稿两次抽出的 fact 集合全等**（验收项 A4.1 由此自然成立），且不同版本引用同一条底稿要点时 `factId` 相同，可以跨版本对照。

**实体的来源有两处**：子句自身的拉丁词，以及**所属条目的元数据**（公司、职位）。元数据里的公司名是简历里的事实——「美团」写进条目头，它就是这份简历的事实。当前口径已经把元数据传进 `assertNoFactsAdded`，这里只是把它固化成 fact 成分的一部分。

### 3. claim：输出的一条断言及其引用

```ts
interface Claim {
  claimId: string
  /** 输出的哪一段（相对于该输出要点的正文） */
  span: { start: number; end: number }
  text: string
  /** 依据了哪些 fact */
  sourceFactIds: string[]
  operation: 'keep' | 'rewrite' | 'merge' | 'delete'
  /** 生成器的自评置信度（0–1） */
  confidence: number
}
```

四种 operation：`keep`（保留）、`rewrite`（改写）、`merge`（合并多条）、`delete`（删除）。

**`confidence` 是生成器的自评，不参与判定。** 判定只看引用是否充分。自评分数若参与判定，就变成「模型自己说自己可信」——那不叫校验。

**claim 的生产者**：

- **规则引擎**（第一个 claim 生产者）：每条输出要点产出一条 claim，`operation` 按实际变换取 `keep` / `rewrite` / `delete`，`sourceFactIds` 指向它覆盖的 fact。被丢弃的要点产出一条 `delete` claim，文本为空。
- **LLM**：每条输出要点产出一组 claim，引用它依据的 fact。

### 4. 判定规则

对每条 claim，令 `S` = 被引用 fact 的成分集合 ∪ 其所属条目的元数据成分：

| # | 规则 | 不通过时 |
| --- | --- | --- |
| R1 | `measure`：输出的每个度量必须与 `S` 中某个度量**同值**（数值相等，单位相等或省略） | 不可信 |
| R2 | `entity`：输出的每个拉丁词（长度 ≥ 2）必须出现在 `S` 的拉丁词集合里 | 不可信 |
| R3 | `rating`：输出的评级词强度**不得高于** `S` 中对应评级词的强度 | 不可信 |
| R4 | `verb`：输出的动词强度**不得高于** `S` 中对应动词的强度 | 不可信 |
| R5 | `term`：输出的中文实词必须**逐字出现在底稿的某个实词里** | **只记录，不拦截** |
| R6 | 无引用（`sourceFactIds` 为空）但有文本 | 不可信 |
| R7 | `operation: 'keep'`：claim 文本必须与被引用 fact 的文本实质相等（忽略空白与标点） | 不可信 |
| R8 | `operation: 'delete'`：claim 文本必须为空，且引用非空 | 不可信 |

**动词强度序**（位次越大越强）：

```
0 了解  1 熟悉  2 使用  3 参与/协助/配合/支持/协同/联合  4 负责/承担  5 主导/推动/牵头  6 创立/搭建
```

**评级强度序**：

```
了解 < 熟悉 < 掌握 < 精通 < 专家
```

**降级是允许的**：「主导」写成「参与」是弱化，不是编造，只记录不拦截。**上调一律拦截**——这是 PRD 承诺里「职责」那一类的落点。

**合并类 claim 逐 fact 校验**：一条 claim 引用多条 fact 时，对每条被引用的 fact 分别跑 R1–R4，任一不通过则整条 claim 不可信（**先严后松**）。

### 5. 回退语义

**粒度：一条输出要点**（不是一个 claim）。一条要点读起来是连贯的，挖掉半句会破碎；而合并类 claim 本来就跨越多条 fact，逐句回退没有意义。

**处置**：

| 情况 | 处置 |
| --- | --- |
| 该要点不可信，且规则引擎对同一组被引用 fact 有产出 | 替换为**规则引擎的产出** |
| 该要点不可信，且规则引擎对那组 fact 没有产出（LLM 新增的要点） | **删除该要点**，并记一条违规 |

回退目标是规则引擎的产出而不是源句原文，有两个理由：

1. 验收项 A4.2 要求「回退后输出与规则引擎逐字一致」——规则产出本来就是合法的，不该再被自己的校验器判一次。
2. 规则引擎的产出经过了它自己的字符级检查，质量不低于源句。

**所以 LLM 实现必须先跑一遍规则引擎**，把它的产出作为回退的备选。这与 ADR-0005 的「校验不过就回落到 `rules`」一致，只是粒度更细——按要点回退，而不是整份版本回退。

**降级标记**：发生过任何回退，版本标记为降级生成，界面可见（验收项 B4.3、A4.5）。

### 6. `integrity` 字段的新语义

从「逐字违规」改为「声明级判定 + 处置」：

```ts
interface IntegrityReport {
  /** 校验了多少条 claim */
  checked: number
  /** 不可信的 claim 与处置 */
  violations: IntegrityViolation[]
  /** 产出这份正文的引擎 */
  generator: 'rules' | 'llm'
  /** 有多少条输出要点回退到了规则产出 */
  reverted: number
  /** 只记录未拦截的观察项（如中文实词变更、动词降级） */
  observations: IntegrityObservation[]
}

interface IntegrityViolation {
  claimId: string
  bulletId: string
  kind: 'unsupported-measure' | 'unsupported-entity' | 'rating-up' | 'verb-strength-up' | 'unreferenced' | 'keep-mismatch'
  /** 哪个成分没被支撑 */
  component?: string
  /** 人话描述，给界面用 */
  reason: string
  originalText: string
  revertedText: string
}
```

`reason` 从自由文本改成**结构化的 kind + 人话描述**：界面要按类型分组展示（「有 2 处新增了数字」「有 1 处职责被上调」），自由文本做不到。`reason` 保留人话描述，供直接展示。

### 7. schema 预留位（F3）

F3 要求 P3 定 schema 时为 P4 的 `facts`/`claims` 段预留扩展位。预留形态：

```ts
interface ResumeVersion {
  // …现有字段…
  /** P4 填充；P3 恒为 null */
  trace?: VersionTrace | null
}

interface VersionTrace {
  facts: Fact[]
  claims: Claim[]
}
```

**放在版本内部而不是独立表**，理由是**自足**：一份版本要能被独立审计，不能要求再 join 别的表才能解释它。代价是同一底稿修订号生成的多个版本各存一份 facts——对 v1.0 的数据量可以接受。

`Fact` / `Claim` 两个类型本身放共享包（`domain/types.ts`），P3 就定义好，P4 只填内容。**P3 的 schema v1 冻结这两个类型的形状**，P4 不再改。

### 8. 已知限制（诚实写明）

**① 中文实词的语义编造抓不住。** 「前端开发 → 前端工程」与「支付宝 → 微信支付」在确定性规则下无法区分。前者被拦（回退，安全但误伤），后者因为「微信支付」在底稿里没出现过，也会被 R5 拦——**但 R5 本身被定义为「只记录不拦截」**。

**修正**：R5 对**新出现的实词**拦截，对**底稿里已有过的实词的改写**放行。判定依据是「这个词在底稿全量里出现过吗」：

- 「微信支付」在底稿别处没出现 → 拦截 ✓
- 「前端工程」在底稿别处没出现 → 也被拦截 ✗（误伤，但方向安全：回退到规则产出，仍是一份合格简历）

R5 因此**参与硬判定**，规则如下：

| R5 | 判定 |
| --- | --- |
| 输出的中文实词在**底稿全量**里出现过 | 放行 |
| 输出的中文实词在底稿全量里没出现过 | 不可信 |

代价是 LLM 的换词能力被大幅限制——**这划定了 LLM 的职责边界：它做重组与取舍，换词交给规则引擎**。这是有意的取舍，不是缺陷：回退的方向是安全的（回退后仍是一份能投的简历），而放开换词会让语义编造无处可拦。

**② `verb` 判定依赖一张人工维护的动词表。** 动词强度序里的词是人工枚举的，简历里出现的动词超出这张表时按「强度 0」处理（视为弱动词，不会造成上调误判）。表要随引擎一起维护。

**③ 数值等价不做四舍五入。** 「3.7」与「3.70」视为同值（解析成同一个浮点数）；「120s」与「2分钟」视为不同值（不做单位换算）——换算表要单独维护，收益不抵成本。

**④ `entity` 只覆盖拉丁词与元数据里的公司名。** 纯中文的公司名、产品名、项目名，若不在条目元数据里，靠 R5 兜住。

## 何时重开这个决策

- **接入 LLM 之后，R5 的误伤率过高**（灰度对比数据说话）：那时考虑引入「可审计的语义判定」——但必须先回答「谁来判判判者」，否则就是模型自证。
- **事实账本的粒度需要调整**（子句级太碎或太粗）：以灰度对比里 claim 的数量分布与判定通过率为依据。
- **动词表与评级表需要扩充**：以真实简历的动词分布为依据。
- **P4 的事实账本要支持跨版本对照**（同一底稿的不同版本之间比 fact 差异）：那时 `factId` 的稳定性要重新设计。

## 影响

- **共享包的 `domain/types.ts` 新增 `Fact` / `Claim` / `VersionTrace` / `IntegrityReport`（新形状）/ `IntegrityViolation`（新形状）**。P3 的 schema v1 冻结这些类型（冻结点 F3）。
- `transforms.ts` 的 `assertNoFactsAdded` 被 `verifyClaims` **语义替换，不是叠加**（计划 §8.1）。
- 新增共享包模块 `ledger.ts`：fact 抽取与 claim 生产。
- `ResumeVersion.integrity` 的形状变了——这是**落库结构的变更**，P3 必须按新形状建表，否则 P4 要做数据迁移。
- **P3 的 schema 冻结点提前**：F4 原定「P3 结束前冻结」，但本 ADR 已经把 `Fact` / `Claim` / `VersionTrace` 的形状定死了——**P3 开工时就要按这个形状建 schema**，不能等到 P3 结束。这是本 ADR 对 P3 工期的影响。
- 验收项对应：A4.1（fact 集合两次全等）由 `factId` 的哈希定义保证；A4.2 的四类注入样本分别对应 R1 / R2 / R3 / R4；A4.3（不误伤是硬指标）由 R5 的「底稿全量词表」口径保证；A4.5（降级测试）由第 5 节的回退语义保证。
- **与 ADR-0005 是两半**：0005 定「怎么调模型」，本 ADR 定「账本与校验器怎么判」。缺本 ADR，LLM 的输出没有可信的落地路径（R1 挡不住）。
