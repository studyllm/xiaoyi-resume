# 成功指标口径

这个产品做得怎么样，看哪几个数。本文件只定义**口径**——指标怎么算、事件怎么记、属性有哪些。埋点实现与看板属于 P5。

> **口径先冻结再实现**。口径一旦写进文档就不再随意改：改了口径，历史数据就不可比，看板要重做。确实要改的，按 §5 留痕。

---

## 1. 北极星指标

### 成功投递的版本数

**定义**：一个账号在一个统计周期内，导出的版本中被复制或导出 PDF 投递的次数（同一版本同一账号只算一次）。

**为什么是它**：这个产品的价值不是「让人改简历」，是「让人投出去一份针对某个岗位的简历」。三件事都得满足：

- 放进来一份简历不代表用上了——放进来不用，白搭。
- 诊断只是手段，用户可以跳过。
- 页面访问数会被演示与好奇流量灌水。

「成功投递的版本数」只统计用户真的把一份针对岗位的简历带走的那一刻。

**怎么算**：`export_copy` 与 `export_pdf` 两个事件去重后的计数。

**它不能单独看**：投递数涨了也可能是同一批人反复导出。所以下面配一条护栏指标。

### 护栏指标

| 指标 | 定义 | 看什么 |
| --- | --- | --- |
| 版本里的不实事实数 | 每个版本生成时通过校验的事实条数里，与底稿对不上的条数 | 北极星涨的同时这个数也涨，说明「不编造」这条底线松了 —— **这是发布否决项** |
| 解析一次成功率 | 导入的简历里，不需要用户改结构就能保存的比例 | 涨不上去说明摄入这条链路的识别率不行 |

## 2. 漏斗

从落地到投递，七步。**每一步的流失 = 到了这一步但没到下一步。**

| 步骤 | 进入条件 | 流失定义 | 相关事件 |
| --- | --- | --- | --- |
| 1 落地 | 打开落地页 | 落地后既没点「导入我的简历」也没点「用示例简历试一遍」 | `landing_view` → `import_start` / `demo_start` |
| 2 导入 | 进入导入页 | 进了导入页但没发起过一次解析 | `import_start` → `parse_attempt` |
| 3 解析 | 发起解析 | 解析没成功（解析失败或没有可解析的内容） | `parse_attempt` → `parse_success` / `parse_fail` |
| 4 保存 | 解析成功 | 解析成功但没有保存（关掉了页面，或卡在身份确认） | `parse_success` → `resume_saved` |
| 5 诊断 | 有已保存的简历 | —— **这一步可跳过，不算流失** | `diagnosis_run` |
| 6 生成 | 粘贴了 JD 并解析出要求 | 解析出要求但没生成版本 | `jd_parse` → `version_generated` |
| 7 导出 | 有版本 | 导出过但没复制/导出 PDF | `version_preview` → `export_copy` / `export_pdf` |

**为什么诊断不算流失**：诊断是可选的，用户可以跳过它直接生成版本。把它算进漏斗会让人误以为「没诊断就是没价值」。

**每一步都能由事件算出来**——这是本表与埋点事件表之间的硬约束：表里有的事件算不出这一步的流失，口径就是错的。

### 2.1 每步的流失率

```
步骤流失率 = 该步流失数 ÷ 该步进入数
```

看的时候**看相邻两步**，不要看绝对值。绝对值受流量总量影响，波动大没有信息量。

## 3. 埋点事件表

**通用属性**（每个事件都带）：

| 属性 | 类型 | 说明 |
| --- | --- | --- |
| `event_id` | string | 事件唯一 ID。**每次发生都不同**——用 `crypto.randomUUID()`，不要用引擎里的 `IdSeed`（那个是可复现输出用的，埋点要的恰恰是不可复现） |
| `occurred_at` | string | ISO 时间戳 |
| `session_id` | string | 一次会话。匿名用户也要有——**不采集任何个人信息** |
| `account_id` | string | 已登录时的账号 ID。匿名时为空 |
| `app_version` | string | 构建版本号 |
| `viewport_tier` | string | `wide` / `narrow` / `compact` / `too-small`，取自 `domain/breakpoints.ts` |

**事件**：

| 事件 | 触发时机 | 专有属性 | 前端可记 |
| --- | --- | --- | --- |
| `landing_view` | 落地页出现 | — | ✅ |
| `import_start` | 点「导入我的简历」或进入导入页 | `entry`: `cta` / `nav` | ✅ |
| `demo_start` | 点「用示例简历试一遍」 | — | ✅ |
| `parse_attempt` | 点「解析」 | `source`: `paste` / `pdf` | ✅ |
| `parse_success` | 解析成功 | `source`、`confidence_bucket`、`sections_found`、`pdf_quality` | ✅ |
| `parse_fail` | 解析失败 | `source`、`reason` | ✅ |
| `resume_saved` | 保存成功 | `is_overwrite` | ✅ |
| `diagnosis_run` | 发起诊断 | `issue_count` | ✅ |
| `jd_parse` | JD 解析成功 | `requirement_count` | ✅ |
| `version_generated` | 生成版本 | `jd_role`、`coverage_strong` / `coverage_weak` / `coverage_none`、`duration_ms` | ✅ |
| `version_preview` | 打开版本详情 | `tab` | ✅ |
| `export_copy` | 复制正文或 Markdown | `format` | ✅ |
| `export_pdf` | 导出 PDF | `format` | ✅ |
| `copy_fail` | 复制失败 | `format` | ✅ |
| `screen_too_small` | 命中降级提示 | — | ✅ |

`confidence_bucket` 分三档：`high`（≥0.8）/ `medium`（0.6–0.8）/ `low`（<0.6）。**不记具体数值**——具体数值会让人去调分数而不是改产品。

## 4. 不采集什么

| 不采集 | 为什么 |
| --- | --- |
| 简历正文、要点、条目内容 | 这是个人内容。指标不需要它，采集它只是风险 |
| 姓名、手机号、邮箱 | 同上。账号 ID 足够区分用户 |
| 粘贴的 JD 全文 | 同上。只记 `requirement_count` 与 `jd_role` |
| 诊断意见的正文 | 只记条数与严重度分布 |
| 任何能反推出个人身份的内容 | — |

**这是隐私底线，不是指标选择。** `docs/privacy-policy.md`（P5）还要再写一遍给用户看，但采集端先守住。

## 5. 口径变更的留痕

改口径时，在本文件末尾追加一行：

| 日期 | 改了哪个指标 | 改前 | 改后 | 为什么 | 生效时间 |
| --- | --- | --- | --- | --- | --- |
| — | — | — | — | — | — |

**变更前后的数据分别标注，不混在一起。** 看板上看板要能切换口径，并且知道哪段数据是旧口径。

哪些改动算「改口径」：北极星指标的定义、漏斗的步骤或流失定义、事件的名字或触发时机、属性的含义。哪些不算：事件属性的**新增**（只要不改已有属性的含义）、看板的展示方式。

## 6. 还没定的事

| 问题 | 现在的倾向 | 定下来之前怎么办 |
| --- | --- | --- |
| 「复制正文」算不算投递 | 算——用户复制就是为了拿去投 | 先两个都记，看板里分开列 |
| 演示模式的行为要不要计入 | 不计——演示用户不是真实用户 | 事件里带 `is_demo`，看板里过滤掉 |
| 多久算一个「统计周期」 | 自然周 | P5 上看板时定 |
| 多账号的版本怎么归属 | 归属到生成它的账号 | 不变 |

这些问题**在 P5 埋点实现前定下来**。定了之后再改，历史数据就不可比了。
