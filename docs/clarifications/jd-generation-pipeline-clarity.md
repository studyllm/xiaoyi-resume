# 生成 JD 定向版本：把黑盒拆开 · 需求澄清

- 日期：2026-11-13
- 状态：待决策

> **术语对照**：本文用「底稿」指代用户持续维护的唯一事实源（界面上显示为「**我的简历**」），
> 用「版本」指代按某份 JD 生成的快照（界面导航显示为「**多 JD 版本**」，句子里简称「版本」）。

---

## 1. 作用

让用户在版本详情页看得懂「这一版是怎么来的」，同时让生成这一步**等得更短、花得更少**。

用户能做什么（一句话）：

> 打开版本详情页的一个说明面板，逐条读懂这份 JD 的要求各自命中了简历里的哪几点、简历里的哪些内容进了这一版、哪些被删了及为什么、哪些句子是模型改写的、哪几句没通过校验被换回、哪几项要求在简历里没有对应事实；并且生成时模型只看到与该岗位相关的内容，等的时间比现在短。

---

## 2. 解决什么问题

### 2.1 界面上只有三步，中间是黑的

`frontend/src/views/JdView.vue:302` 的 `el-steps` 只有「粘贴 JD / 确认要求命中情况 / 生成版本」。
用户在「确认要求命中情况」看到的是一张表（JD 原句 / 关键词 / 命中依据 / 覆盖），在版本详情页看到的是
正文、改动对照、覆盖清单与未覆盖清单——**从 JD 到正文之间发生了什么，一次都没显示**。

### 2.2 判定依据算出来了，但被丢掉

`packages/shared/src/engines/coverage.ts:16` 的 `collectEvidence` 为**每一条**要点算出：
`relevance`（相关度打分）、`exactTerms`（精确命中的关键词）、`relatedByEntry`（弱关联的词）、
`approxRequirements`（近似命中的要求）、`jdRelated`（是否与该 JD 相关）。

`packages/shared/src/engines/ordering.ts:13` 的 `orderBullets` 与 `:38` 的 `trimBullets` 正是靠这些
字段决定「哪条要点排前面、哪条要点被删、删的理由是什么」。

**这些依据一个都没到界面上**：`server/src/routes/jd.ts:122` 的 `toResponse` 只返回
`roleName`、`requirements`、`coverage`、`warnings`、`engine`、`degraded`、`degradeReason`；
`evidence` 留在 `jd_analyses` 表里，接口不吐。

### 2.3 两次模型调用的提示词没有裁剪

| 调用 | 在哪 | 现在发过去的内容 |
| --- | --- | --- |
| 比对 JD | `packages/shared/src/engines/jdAnalysisPrompt.ts:80` | JD 全文 + **全部**要点（`toPromptBullets` 把每个分区每个条目的每条要点摊平编号） |
| 改写正文 | `packages/shared/src/engines/llmPrompt.ts:39` | 岗位名 + **全部**要求（`generator.ts:161` 把 coverage 全量映射，**含 `tier=none` 的未覆盖要求**）+ 全部保留要点的**全部子句** + 每条的规则产出 |

两处浪费：

- **未覆盖的要求对改写没有指导意义**——它们在正文里本来就不写内容，却占着提示词体积，
  还可能引导模型去"补写"（虽然有事实校验兜底）。
- **比对那次把所有要点都发过去**——包括与该 JD 明确无关的项目要点。

### 2.4 等待时间的真实量级比想象大一个数量级

`server/.env.example` 的实测记录（原话）：

> 实测（MiniMax-M3.1-Flash，简历 77 条要点）：
> - **超时**：要 10 分钟上下（每条约 7.6 秒）。120 秒不够，撞上了就整版回落规则引擎——等了两分钟拿到的还是规则写的。要点越多越慢，给 900 秒。
> - **输出上限**：16000 不够（推理内容占了 78% 的额度，正文没轮到就被截断，finish_reason=length）。给 32000。

而 `server/src/llm/config.ts:18` 的配置默认值是 `LLM_TIMEOUT_MS = 30_000`（30 秒）。
**默认配置下改写必然超时**，整版回落规则引擎（`packages/shared/src/engines/generator.ts:184`）。

「每条约 7.6 秒」意味着：**等待时间与发给模型的要点数成正比**。裁剪要点是缩短等待的直接杠杆，
不需要动调用次数。

另外：链路上**没有任何请求级超时**——Fastify 没设 `requestTimeout`，前端 `fetch` 没传 `signal`
（`frontend/src/api/client.ts:69`）。一次 10 分钟的模型调用会让 HTTP 请求挂 10 分钟；
用户中途关掉页面，服务端的调用还在跑，token 照烧。

### 2.5 超时的后果是「白等」

模型超时 → `generator.ts:184` → `rulesOutcome` → **整版**用规则引擎产出。
用户在生成页看到的是「模型这次没有用上」，版本详情页显示「这一版由规则引擎生成」。
**用户等 10 分钟，拿到的是规则写的。**

现有的错误码表里其实有 `LLM_TIMEOUT`（504）与 `LLM_UNAVAILABLE`（503）
（`packages/shared/src/contracts/error-codes.ts:33`），但模型路径**从不抛这两个码**——
失败原因只是一个自由文本 `degradeReason` 字符串，界面原样显示。

### 2.6 对应漏斗的哪一步

`docs/success-metrics.md` §2 的第 6 步「生成」：`jd_parse` → `version_generated`。
等待过长与"看不懂结果"都压在这一步，而它是投递前最后一道。

## 3. 功能范围

### 在范围内

#### A. 两次调用的提示词裁剪（**保持两次调用，不合并**）

**A1 · 比对那次：要点从「全部」改成「规则粗筛出的候选」**

- JD 全文**照发**——要求必须逐字摘自 JD 原文（`llm-engine` 规格「要求不在 JD 原文中 → 不采用」），
  裁 JD 会直接丢要求。
- 粗筛复用**已有的 relevance 打分**（`coverage.ts:77`），**不引入新的相关性模型或向量检索**。
- ⚠️ **序号必须保持可核对**：现在 `toPromptBullets` 编 1..N，`jdAnalysis.ts:291` 的 `bulletIdOf`
  按 1..N 全量编号回查要点。裁剪后若重新编号，模型回引的序号就对不回原文——
  **查不出依据等于没引用**，这条底线不能破。裁剪后要保留要点在整份简历里的**原序号**，
  并在提示词里说明序号是它在整份简历中的位置。

**A2 · 改写那次：要求列表从「全部」改成「已覆盖的」**

- 只发强覆盖与弱覆盖的要求；`tier=none` 的未覆盖要求不发。
- 要点已经是删减后的（`generator.ts:148` 展平的是 baseline 版本），保持不变。
- 子句全发——`verifyClaim` 的校验依赖完整 facts，裁子句会让校验对不上。

**A3 · 不引入新的相关性判定**

粗筛只用现有的规则目录与 relevance 打分，行为与规则路径一致。

#### B. 版本详情页的「这一版是怎么来的」说明面板（**生成后**可见）

面板要能回答四个问题，每个答案都要能点回原文核对：

1. **要求命中**：JD 里的 N 条要求，每条命中了简历里的哪几条要点，覆盖分档的依据是什么。
2. **要点取舍**：简历里的 M 条要点，哪几条进了这一版、哪几条被删了、删的理由是什么。
3. **模型改写**：哪些句子是模型改写的、哪些没通过事实校验被换回规则产出、换回的原因是什么。
4. **未覆盖**：哪几条 JD 要求在简历里没有对应事实、为什么（现有 `uncovered` 已有一半）。

**数据来源与缺口**：

| 面板要什么 | 现在在哪 | 缺什么 |
| --- | --- | --- |
| 要求的覆盖与命中要点 | `version.coverage` | — |
| 未覆盖要求与原因 | `version.uncovered` | — |
| 要点删改与理由 | `version.diff`（`reason` 已是人话） | — |
| 校验没过的要点与原因 | `version.integrity.violations` | — |
| 要点的相关度与命中了哪些要求 | `jd_analyses` 表的 `evidence` | **接口不返回**（`routes/jd.ts:122`） |
| 哪条是模型改写、哪条是规则引擎改写 | `version.trace.claims` 的 `llm-` 前缀能分辨 | **没有直接字段**——`diff.change` 两者都是 `'rewrite'` |
| 这次用了哪个模型、哪版提示词、发过去多少内容 | `generations` 表（`routes/resume.ts:167`） | **版本 payload 里没有** |

#### C. 调用记录透出到面板

模型标识、提示词版本、这次发过去的要点条数与 token 数、耗时。

### 明确不做

- **不引入 SSE / 轮询**。生成期间的界面不变，仍是「正在等模型改写，已等 N 秒」。
- **不合并两次调用**。
- **不做分批调用**。分批会重发系统提示与要求列表，总 token 可能不降反升；且与「保持两次」冲突。
- **不改「降级 / 回退」的对外说法与 `integrity.degraded` 语义**。⚠️ 但澄清中发现现有语义有一处互相矛盾，
  见「未决问题」第 1 条。
- **不换模型供应商、不改密钥配置方式**。
- **不引入新的相关性模型或向量检索**。
- **不改模型路径的调用形态**（同步请求、密钥在服务端、模型只改写不增删要点、每条断言过事实账本——
  `llm-engine` 的四条底线一条都不碰）。

### 与相邻能力的边界

| 能力域 | 关系 | 说明 |
| --- | --- | --- |
| `jd-version-generation` | **MODIFIED** | 覆盖判定、改动对照、未覆盖清单的口径**不变**，只加「看得见」；新增一条「版本说明这一版是怎么来的」 |
| `llm-engine` | **MODIFIED** | 「比对 JD 时只发必要的内容」现在只规定「不发姓名抬头联系方式、不发整份简历」，裁剪后要规定**发哪些要点、序号怎么保持可核对** |
| `version-management` | **MODIFIED 或新增** | 版本详情要承载说明面板（视该域现有覆盖范围定） |
| `draft-diagnosis` / `resume-comment-anchoring` | **不动** | — |
| `docs/privacy-conclusions.md` §7 | **要改一句** | 现在写「两件事发的是**同一批内容**……所以一处同意即可」。裁剪后两次调用发的**不再相同**（比对发候选要点，改写发全部保留要点与已覆盖要求）。**同意的范围不变**（仍是简历正文 + 这份 JD），但这句话要跟着改 |

## 4. 影响

### 4.1 规格影响

| 规格 | 改什么 |
| --- | --- |
| `openspec/specs/jd-version-generation/spec.md` | 新增「版本说明这一版是怎么来的」一条要求（面板内容 + 可核对性）；「说明 JD 中没有对应事实的要求」补一条：面板要能看出未覆盖的原因 |
| `openspec/specs/llm-engine/spec.md` | 「比对 JD 时只发必要的内容」按裁剪后的口径重写：要发哪些要点、序号保持原样可回查、未覆盖要求不发 |

| `docs/api-contract.md` | `POST /api/v1/versions` 的响应加字段，或新增 `GET /api/v1/versions/:id/explain` |

### 4.2 工程影响

| 层 | 改什么 | 轻重 |
| --- | --- | --- |
| `packages/shared/src/engines/jdAnalysisPrompt.ts` | 候选要点筛选 + 原序号保持 + 提示词说明 | **重** |
| `packages/shared/src/engines/llmPrompt.ts` | 要求列表裁剪（只发已覆盖） | **重** |
| `packages/shared/src/engines/generator.ts` | 把「这条是模型改写的」与调用记录写进版本 | **重** |
| `packages/shared/src/domain/types.ts` | 版本结构加字段 | **重** |
| `server/src/routes/jd.ts` | `toResponse` 能返回要点证据摘要 | **重** |
| `server/src/routes/resume.ts` | 生成记录写进版本 payload | **重** |
| `frontend/src/views/VersionDetailView.vue` | 说明面板（页签或抽屉） | 轻 |
| `frontend/src/views/JdView.vue` | 生成等待文案可能要跟着实际等待时间调 | 轻 |
| 提示词版本号 | `llm-jd-analysis-v1` → v2、`llm-rewrite-v1` → v2。不升号，审计记录分不清两批输出 | 轻 |
| 数据库 | `jd_analyses` 已存 `evidence`，**无需迁移**。若把证据摘要复制进 `versions.payload`（jsonb），加键不破坏旧数据，但要确认是否算改 schema | 见 5.3 |

**顺带要补的一个缺口**（属规格已有要求，算修复不算新范围）：
`packages/shared/src/engines/generator.ts:264` 在模型改写后重新 `assembleBody` 出正文，
**没有再过一次 `assertCleanOutput`**——只有规则产出的正文在 `generateVersion.ts:351` 查过禁用词。
也就是说模型写的正文里出现禁用词不会被拦。`AGENTS.md` §7 要求「引擎输出交付前都要过禁用词检查」，
`llm-engine` 规格也要求「模型输出的每一条要求 SHALL 不含界面禁用词」。本轮要补。

### 4.3 产品与文案影响

- 界面用词：「我的简历」「多 JD 版本」「版本」。**不出现「底稿」**（`AGENTS.md` §7）。
- 禁用词：面板会展示 JD 原句与模型改写后的正文——两处都要过禁用词检查（`frontend/src/engines/forbidden.ts`）。
- 新文案：面板标题与各段落说明；「这次只比对了 N 条要点」这类交代成本的话。
- 状态：面板不是新状态，是版本详情的一个区块（`version-management` 域内）。

### 4.4 用户影响

**好处**

1. 版本详情页多一个入口，打开就能逐条读懂这一版的来路。
2. 依据都能点回简历原文核对，不必猜「为什么这条不见了」「为什么这条是强覆盖」。
3. 生成等待时间随要点数量下降（同样的模型、同样的简历，模型看到的要点更少）。
4. 同样等待时间下更容易在超时前拿到结果——`.env.example` 实测：超时撞上就整版回落规则引擎。

**风险**

1. **裁剪可能连能命中的要点一起裁掉**。粗筛用规则相关性，对「用词不同但语义相关」的情况会漏。
   缓解：未覆盖的要求如实列出（现有规格已有）；面板写清「这次只比对了 N 条要点」——
   **覆盖结论会比全量时保守，这是实话，要说**。
2. **面板会暴露「这一版删了你哪些要点」**。用户可能觉得被删了不该删的，需要让删减依据可核对。
3. **等待时间仍可能很长**。裁剪按比例缩短，改不掉「每条约 7.6 秒」这个底（深度推理模型本身就慢）。
   这条要如实说，不能承诺「等一会儿就好了」。
4. 快照语义不变：版本生成后独立保存，底稿后续修改不回写。

## 5. 实现难度

### 5.1 轻重判据（`AGENTS.md` §2.0）

| 触及项 | 判据 |
| --- | --- |
| `packages/shared` 的引擎与领域类型 | **重** |
| 服务端接口与响应契约 | **重** |
| 前后端契约 | **重** |
| 数据库存档结构（若动 `versions.payload`） | **重** |
| 单页内的交互与文案 | 轻 |

→ 落在**重**范围。

### 5.2 工作量档位

| 项 | 档位 |
| --- | --- |
| 提示词裁剪（共享包引擎 + 单元测试） | 中（1–3 人日） |
| 证据摘要透出 + 契约扩展 + 服务端 | 中（1–3 人日） |
| 说明面板（前端视图 + 空状态 + 守卫通过） | 中（1–3 人日） |
| 补 `assertCleanOutput` 缺口 + 文档同步 | 轻（≤0.5 人日） |

合计档位：**中到重，3–6 人日**。⚠️ 没有实测来源，不写死精确数字。

### 5.3 风险点

1. **序号一致性（最要命）**。裁剪要点后，模型回引的序号必须还能对回原文。
   这是「可核对」底线的承重墙，也是最容易出错的一处。
2. **裁剪连能命中的要点一起裁掉**。缓解口径见 4.4；粗筛沿用规则路径同一套打分，
   排序与删减行为不会差太远，但覆盖结论会偏保守。
3. **撞冻结点 F3**（数据模型与 schema v1，P3 开始前冻结）。往 `versions.payload` 加字段
   是否算「改 schema」要先确认——payload 是 jsonb，加键不破坏旧数据，但 F3 的纪律是
   「存档结构变更后按迁移规则转换旧存档」。
4. **不撞 F1**（引擎异步化）——本轮不引入 SSE，引擎接口形态不动。
5. **不撞 F6**（指标口径）——`version_generated` 的 `duration_ms` 口径不变，只看分布变化，不用留痕。
6. **每日成本与次数上限仍然缺位**。`docs/adr/0005-llm-access-shape.md` §3 要求定的三个数
   （单次输出上限、每日生成次数上限、每日成本上限），现在只落地了第一个
   （`LLM_MAX_TOKENS`）。裁剪降低了单次成本，但没有上限仍可能失控。见「未决问题」第 4 条。

## 6. 是否有必要实现

**结论：做。**

**理由**

1. **直接服务北极星指标的前置**。北极星是「成功投递的版本数」（`docs/success-metrics.md` §1），
   漏斗第 6 步「生成」是投递前最后一道。「看得懂」是投递的前提——**用户不敢投一版自己看不懂的简历**。
2. **现有能力拼不出来**。现有 spec 只规定了「版本说明这一版是谁写的」（降级原因、回退条数），
   **没有规定「这一版是怎么来的」**：改动对照有、未覆盖清单有，**要点取舍的依据没有**。
   要「看得懂」必须新增可核对的依据数据，不能靠现有 payload 拼。
3. **替代方案更差**。不改，只把 `evidence` 塞进现有响应让用户自己看原始数据——
   那是把黑盒换成更难读的原始数据，不解决问题。
4. **方向没被排除**。PRD §4「粘贴 JD，生成一版定向简历」在本版范围内。

**但要诚实**：缩短等待与降低成本**本身不直接增加投递数**——它们降低的是第 6 步的流失与第 7 步的犹豫。
真正直接影响投递的是「看得懂」。三个目标里，**「看得懂」是主，「等待更短」与「成本更低」是辅**。

## 7. 对用户的帮助

用户能感知的差别（都能观察，不是功能清单）：

1. 版本详情页多一个「这一版是怎么来的」入口。打开后，用户能逐条读：JD 里的 N 条要求各自命中了简历里
   哪几点；简历里的 M 条要点里，哪几条进了这一版、哪几条被删了、删的理由是什么；哪些句子是模型改写的、
   哪几句没通过事实校验被换回规则产出；哪几条 JD 要求在简历里没有对应事实、为什么。
2. 用户不用再猜「为什么这条不见了」「为什么这条是强覆盖」——依据在面板里，且能点回原文核对。
3. 生成等待时间变短，而且更容易在超时前拿到结果——模型看到的要点少了，超时撞上的概率下降
   （`.env.example` 实测：超时撞上就整版回落规则引擎，等了十分钟拿到的还是规则写的）。
4. 每次生成用掉多少内容、哪个模型、哪版提示词，在面板里可查。

**风险**：面板会明确写出「这次只比对了 N 条要点」。用户可能因此觉得覆盖判断不完整——这是实话，
比含混过去强。
