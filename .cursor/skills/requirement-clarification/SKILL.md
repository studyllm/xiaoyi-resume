# 需求澄清

把一条还模糊的需求问清楚，产出一份**能据此决定做不做、做多大**的澄清文档。
不改代码、不建 OpenSpec 变更——澄清的结论是决策依据，落地是下一步的事。

---

## 何时用 / 何时不用

**用**：

- 新需求刚提上来，还只有一句话或一个想法。
- 要决定做不做、做多大范围、值不值得占一个阶段。
- 一个想法可能落进已有能力域，需要先看它跟现有行为是什么关系。
- 产品侧问「这个功能对用户到底有什么用」，需要一份能对得上的回答。

**不用**：

- 需求已经定死、只是要实现 → 直接 `/opsx:propose`。
- 实现跑偏了已有 spec → 走 AGENTS.md §2.2 的 bug 流程。
- 只是措辞、注释、样式调整 → 直接改。

---

## 输入

用户给一句需求描述、一个变更名、一段用户反馈或一个想法都可以。

**没有输入就先问**（AskUserQuestion）：「这次要澄清的是哪条需求？用一两句话说清你想让用户能做什么。」

---

## 七问

澄清文档固定这七段，顺序不变。每段都要落到本仓库的既有口径上，不给通用套话。

| # | 问题 | 答什么 |
| --- | --- | --- |
| 1 | **作用** | 这个需求在产品里扮演什么角色。用一句话复述「用户能做什么」——AGENTS.md §2 要求实现前先得到这句确认。 |
| 2 | **解决什么问题** | 用户现在卡在哪一步，现有路径为什么不够用。对到漏斗的哪一步流失（`docs/success-metrics.md`）。 |
| 3 | **覆盖哪些功能范围** | 范围内做什么、明确不做什么、与相邻能力的边界在哪（哪个能力域新增、哪个 MODIFIED、哪个不动）。 |
| 4 | **有哪些影响** | 分四类：规格影响、工程影响、产品与文案影响、用户影响。 |
| 5 | **实现难度** | 轻重判据（要不要 design.md）、工作量档位、风险点、冻结点冲突检查。 |
| 6 | **是否有必要实现** | 对北极星指标与护栏指标的贡献、替代方案、结论（做 / 缓做 / 不做）与理由。 |
| 7 | **对用户有哪些帮助** | 用户从哪句话能感觉到、少了什么成本、有没有风险。必须可观察。 |

---

## 流程

### 第 1 步 · 先读现状，再问问题

**先查仓库，再问人。**仓库里已经答了的问题不要拿去问用户。

```bash
openspec list --json          # 有没有在途变更，避免重复
```

按需读：

| 要回答 | 去哪读 |
| --- | --- |
| 这个行为现在是什么样 | `openspec/specs/<能力域>/spec.md` 的 Purpose 与 Requirement |
| 本版做不做这件事 | `docs/v0.1-产品需求文档.md` 的范围表（§4）与功能需求（§7） |
| 值不值得做 | `docs/success-metrics.md` 的北极星指标、护栏指标、漏斗七步 |
| 排在什么位置、能不能现在做 | `docs/产品开发计划-v1.0.md` 的阶段总览与冻结点登记簿（F1–F10） |
| 术语、禁用词、架构约束 | `AGENTS.md`（§3 样式、§6 架构、§7 用词） |

代码侧用 Grep 定位实现落点：`packages/shared/src/engines/`（解析、诊断、JD、版本生成）、
`frontend/src/views/` 与 `components/`（界面）、`server/src/routes/`（接口与错误码）。

**关键**：现有 spec 已经规定的行为，就是「已有能力」，澄清时按复用或改行为处理，不当新需求从零设计。

### 第 2 步 · 补齐只有用户知道的缺口

一次 AskUserQuestion 最多 4 个问题，**只问仓库里查不到的**：

- 谁、在什么场景下用（目标用户与触发时机）
- 期望的用户可见结果长什么样
- 优先级：不做会怎样，有没有替代路径
- 硬约束：时间窗、依赖的外部系统、不能碰的东西

仓库里能查到的（已有的能力、现有约束、指标口径）**不要问**。

### 第 3 步 · 按七问分析

每一问都要有依据，引用到具体文件或行。判据速查：

**第 3 问 · 功能范围** —— 边界按能力域切。判断三件事：
新增能力域、修改已有能力域、明确不碰的能力域。说不清边界的需求，
说明范围还没定，**先别给实现结论**。

**第 4 问 · 影响** —— 四类分开写：

| 类别 | 看什么 |
| --- | --- |
| 规格 | 动哪几个 `openspec/specs/` 能力域，delta spec 怎么开 |
| 工程 | 共享包引擎 / 服务端接口与错误码 / 数据库与迁移 / 前端视图 / 指标埋点 |
| 产品与文案 | 界面用词（「我的简历」「多 JD 版本」）、禁用词、新状态文案 |
| 用户 | 已有用户的行为变化、快照语义、不编造底线是否被触碰 |

**第 5 问 · 难度** —— 轻重判据照抄 AGENTS.md §2.0 那张表（`packages/shared` 引擎与领域类型、
服务端接口与错误码、数据库与迁移、前后端契约 = 重；样式布局、单页交互与文案、单组件局部逻辑 = 轻）。
重 → 要 design.md。拿不准当重的。

**这一问要给出 `重量：重` 或 `重量：轻` 的明确结论**——AGENTS.md §2.0.2 要求 proposal.md 里写这一行，
它决定后面要不要系统设计。结论写进澄清文档的「实现难度」段，也写进交棒摘要。

工作量用 P 阶段的人日口径给档位（轻 ≤0.5 人日 / 中 1–3 人日 / 重 4+ 人日），
并对照冻结点：F1（引擎异步化）、F3（数据模型）、F4（事实账本）、F5（账号标识）、
F6（指标口径）、F7（错误码）、F8（隐私结论）——**撞上冻结点先说清楚**。

**第 6 问 · 要不要做** —— 三档结论：

- **做**：直接服务北极星指标「成功投递的版本数」或其护栏指标，且现有能力拼不出来。
- **缓做**：有价值但当前漏斗上不是瓶颈，或要先解前置（先出设计不改代码）。
- **不做**：能用现有能力拼出来，或服务的是已被明确排除的方向（PRD §4「不在本版」）。

给不出「做」的充分理由时，诚实写「缓做」——这不是否定需求，是把它排到正确的位置上。
每条结论后面必须跟**理由**，理由要指向指标、漏斗或已有能力，不能是「用户可能会喜欢」。

**第 7 问 · 对用户的帮助** —— 写用户能感知的差别，不是功能清单。
「用户在版本详情页一眼看到哪些 JD 要求没被覆盖」是帮助；
「版本页增加覆盖情况展示」不是。

### 第 4 步 · 写文档

写到 `docs/clarifications/<kebab-case>.md`（目录不存在就建）。
文件名用**字母开头**的 kebab-case，日期写进正文，不写进文件名。

固定结构：

```markdown
# <需求名> · 需求澄清

- 日期：YYYY-MM-DD
- 状态：待决策 / 已确认做 / 缓做 / 不做

## 1. 作用
（用户能做什么，一句话）

## 2. 解决什么问题
（用户卡在哪，现有路径为什么不够；对应漏斗哪一步）

## 3. 功能范围
### 在范围内
### 明确不做
### 与相邻能力的边界

## 4. 影响
### 规格影响
### 工程影响
### 产品与文案影响
### 用户影响

## 5. 实现难度
（轻重判据、人日档位、风险点、冻结点检查）

**重量：重 | 轻**   ← 这一行要明确写出来，proposal.md 要用

## 6. 是否有必要实现
（结论 + 理由 + 替代方案）

## 7. 对用户的帮助
（用户可感知的变化）

## 未决问题
（需要产品侧拍板的点）

## 下一步
（做 → /opsx:propose <name>；缓做 → 缺什么；不做 → 什么条件下重启）
```

文档内部可以用「底稿」「版本」等内部术语，但**必须给出与界面用词的对照说明**（AGENTS.md §7）。
不写禁用词。

### 第 5 步 · 交棒

聊天里给摘要：七问各一句 + 结论 + 重量 + 未决问题。

- 结论是「做」→ 提示下一步 `/opsx:propose <kebab-case>`，并说明澄清文档的哪些段可以直接进 proposal 的 Why 与范围。
- 结论是「做」且范围已定 → 提示可以先走 `system-design` skill 出设计（架构、UI、前端、后端、数据库、测试、任务拆分），再进 `/opsx:propose`。
- 结论是「缓做」或「不做」→ 说清缺什么条件、什么信号出现时重启。
- 用户明确要落地 → 才建 OpenSpec 变更，**不要主动建**。

**关卡提示**：进 `/opsx:propose` 时，proposal.md 的 `## Why` 段开头要有 AGENTS.md §2.0.2 的三行。
本 skill 的产物填其中的「澄清文档」一行，路径就是这份澄清文档；「重量」一行取第 5 问的结论；
「系统设计」一行等设计做完再填。

---

## 护栏

- **不改代码、不建变更。** 澄清阶段唯一的产物是文档。
- **先读后问。** 仓库里有的答案不要拿去问用户；反过来，用户才知道的（场景、优先级、硬约束）不要自己编。
- **每条结论有依据。** 引用到具体文件、行或指标条目。找不到依据就写「未知」并列入未决问题。
- **不编数字。** 工作量、覆盖率、用户量这些没有实测来源的不写死数字，写档位与依据。
- **范围没定不给实现结论。** 第 3 问答不上来就先回「范围待定」。
- **守术语与禁用词。** 文档用内部术语要给界面用词对照；界面文案建议必须是「我的简历」「多 JD 版本」。
- **不替产品拍板。** 结论给建议，决策权在用户；「缓做」和「不做」都要写清重启条件。
